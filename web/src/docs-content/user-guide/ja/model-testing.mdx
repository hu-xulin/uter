# モデルテスト

Uter にモデルを接続する前に、「接続できるか」「使えるか」「安定しているか」「課金は正確か」を順に検証し、本番後のトラブルを避けます。

まずコンソールの**プレイグラウンド**で試し、その後に API で再確認します。この二段階で「モデル側の問題」と「リクエストの誤り」を素早く切り分けられます。

## 前提

| 項目 | 内容 | 入手場所 |
| --- | --- | --- |
| **ベース URL** | API 専用エンドポイント `https://api.uter.ai/v1`。使用中のコンソールサイトのアドレス + `/v1` も利用可。他のドメインは公式エンドポイントではない | API リファレンスのトップ；またはコンソールサイトのアドレス + `/v1` |
| **API キー** | 例 `sk-xxxxxxxx`。パスワード同等の資格情報。外部に漏らさず、フロントエンドに埋め込まず、Git にコミットしない | 一般 → APIキー → APIキーを作成 |
| **クォータ** | 内部課金単位：**既定で 500,000 クォータ = 1 USD**。この比率は「システム設定 → 請求」で変更可能。モデルごとに各自の課金規則で換算され、ウォレット／利用履歴ではサイト設定通貨で表示。不足すると呼び出しは拒否される | 個人 → ウォレット；一般 → 利用履歴 |
| **モデル名** | Uter に登録された名前（ベンダー公式名とは限らない） | 公開価格ページ `/pricing`；または `GET /v1/models` の `id` |

### チャネルとグループは別の軸

- **グループ**：課金倍率とルーティング可能範囲を決める。API キーは所属グループの倍率とモデルで課金・ルーティングされる。
- **チャネル**：モデルを実際に提供する上流（Uter チャネル、集約チャネル、共有チャネルなど）。1 つのモデルを複数の有効チャネルが提供することも、1 つだけの場合もある。

同じモデルでもグループや時期によって可用性・価格が変わります。「利用可能なチャネルがありません」は、そのグループに有効な提供チャネルがないという意味で、リクエスト形式の誤りではありません。

<Callout type="warn">
  API キーはパスワードです。サーバー側またはシークレット管理でのみ使用し、ブラウザへ渡さず、平文でログに残さず、Git にコミットしないでください。
</Callout>

### キーの状態と制限を確認

状態は **有効・無効・期限切れ・クォータ枯渇** の 4 種類。作成・編集時には次も設定できます。

- **グループ**：課金倍率とルーティング可能なモデルを決定。「自動グループ順序」と「グループ間再試行」も設定可能。
- **有効期限**：既定は「無期限」。期限後は 401。
- **クォータ上限**：サイト設定通貨（既定 USD）で入力、「無制限」も可。使い切ると「枯渇」。
- **モデル制限**：指定モデルのみ許可。未選択ならどのモデルも呼べない。
- **IP 許可リスト**：CIDR 対応（例 `203.0.113.0/24`）。対象外は拒否。
- **ユーザークォータ照会の許可**：`/v1/dashboard/billing/*` を許可するか。
- **作成数**：一度に複数のキーを作成可能。テストにはそのうち 1 つだけ残せばよい。

<Callout type="info">
  テスト用キーでは対象モデルのみを選択し、グループ間再試行をオフにしてください。予期しないチャネルへルーティングされ、接続性や課金の結論が歪みます。
</Callout>

## 最短の確認：プレイグラウンド

チャット → プレイグラウンドは API と同じ呼び出し経路です。

1. モデルセレクタを開き、ポップアップの左側で**チャネル**、右側でそのチャネルのモデルを選択。既定ではリストの最初のチャネルが選択されています。
2. メッセージを送信（既定はストリーミング応答）。
3. パラメータ設定で `temperature`・`top_p`・`max_tokens`・`frequency_penalty`・`presence_penalty`・`seed` を必要な分だけ有効化。**有効なものだけが送信されます**（`max_tokens` と `seed` は既定で無効）。
4. 生成の停止・再生成・メッセージの編集／コピー・原文の表示・個別メッセージの削除・会話の消去（確認ダイアログあり）が可能。
5. 入力欄の**添付と Web 検索ボタンは開発中のプレースホルダー**で、クリックしても未対応と表示されるだけです。マルチモーダルは Step 6 の API の `image_url`、Web 検索は `POST /v1/tools/search` を使用してください。

プレイグラウンドも同じ課金規則でクォータを消費します。反復確認に便利ですが、最終確認は API で行います。

## モデルと価格の確認

公開価格ページ `/pricing` では：

- モデル名で検索；
- **チャネル・ベンダー・モデルタグ・価格タイプ・エンドポイントタイプ**の 5 種類で絞り込み、どのチャネルが提供するか確認。価格タイプは従量・従リクエスト・タスク課金・動的価格、エンドポイントタイプは Chat / Response / Anthropic / Gemini / Rerank / Image / Embeddings / Video；
- 課金方式、コンテキスト、対応エンドポイントを確認し、**標準価格／チャージ価格**、**1M トークン単位／1K トークン単位**、7 種類の並び替え、カード／テーブル表示を切り替え；
- **優特価格**と**公式価格**および割引／上乗せを比較。秒単位課金のモデル（一部の動画・音声モデルなど）は `/ second` 単価と公式参考価格を表示；
- 左のチャネルサイドバーは既定で **Claude-Basic** が選択され、そのチャネルのモデルのみ表示。「すべてのチャネル」をクリックするか `?channel=all` にアクセスするとすべて表示されます。

<Callout type="warn">
  カードに「価格未設定」と表示されたり、課金式の原文がそのまま出たり、公式価格がない場合は、プラットフォーム側の価格データの問題でありリクエストの誤りではありません。モデル名とチャネルを控えてプラットフォームに連絡し、式をクライアント側で解析しないでください。
</Callout>

## テスト観点

11 項目。前半 4 つが「使えるか」、続く 5 つが「安定性と課金」、最後の 2 つが非同期タスクと可観測性です。

1. **接続と認証** — URL、キー、IP 許可リスト。
2. **モデル一覧と可用性** — モデルの存在と、グループに提供チャネルがあるか。
3. **基本対話** — 最小リクエストで正常応答。
4. **パラメータと応用機能** — ストリーミング、`temperature`、`max_tokens`、tools/function calling、視覚、JSON モード、システムプロンプト。
5. **ストリーミング（SSE）** — 逐次受信と解析。
6. **性能** — 初回トークン（TTFT）、総時間、長文脈。
7. **安定性と制限** — 並列、再試行、429、上流飽和。
8. **クォータと課金** — 控除額が利用履歴と一致するか。
9. **エラーと境界** — 不正入力やモデル不在時の明確なエラー。
10. **非同期タスク型モデル** — 画像／動画／音楽の投入・ポーリング・成果物取得。
11. **可観測性** — 利用履歴／タスク履歴でモデル・チャネル・時間・クォータ・失敗理由を追えるか。

## 手順（API）

- `BASE=https://あなたのドメイン/v1`（実際の値に置換）
- `TOKEN=sk-your-token-here`（コンソールの完全なキー）

例は `curl`。ローカルにプロキシがある場合は `--noproxy '*'` を付けます。

### Step 1 · 接続と認証

```bash
BASE=https://あなたのドメイン/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

`object: "list"` と複数の `id` が返れば OK。401「無効なトークン」はキーの誤り／無効化、「いかなるモデルにもアクセスできません」はモデル制限の不足です。

<Callout type="info">
  ベンダー原生認証にも対応：Claude は `POST /v1/messages` + `x-api-key` と `anthropic-version: 2023-06-01`、Gemini は `GET /v1beta/models` + `x-goog-api-key`（または `?key=`）。OpenAI 互換は `Authorization: Bearer`。
</Callout>

### Step 2 · モデル一覧と詳細

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40

curl --noproxy '*' -s "$BASE/models/モデルID" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

<Callout type="warn">
  対象がない場合は、まず価格ページ `/pricing` でチャネル別に確認し、プラットフォームへ問い合わせてください。左のチャネルサイドバーは既定で Claude-Basic のみ表示されるため、「すべてのチャネル」をクリックするか特定のチャネルを選んで確認してください。名前を推測すると 404 や「利用可能なチャネルがありません」になります。
</Callout>

### Step 3 · 最小の対話（非ストリーミング）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "モデルID",
    "messages": [{"role": "user", "content": "一文で自己紹介してください。"}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

`choices[0].message.content` に本文、`usage` に `prompt_tokens` / `completion_tokens` があれば OK。

### Step 4 · ストリーミング（SSE）

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "モデルID",
    "messages": [{"role": "user", "content": "10 まで数えて。"}],
    "stream": true
  }'
```

`data: {...}` が逐次届き、最後に `data: [DONE]` で終われば OK。curl では `-N` が必須、SDK では `stream: true` とバッファ無効化を確認します。

### Step 5 · Function calling

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "モデルID",
    "messages": [{"role": "user", "content": "北京の天気は？"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "都市の天気を取得",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

`choices[0].message.tool_calls` が返れば OK。応用機能は個別に検証し、「会話できる＝すべて使える」と仮定しないでください。

### Step 6 · 視覚（画像対応モデルのみ）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "視覚対応モデルID",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "この画像には何がありますか？"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

画像は公開 URL である必要があります（ローカルファイルは読みません）。

### Step 7 · レイテンシ基準

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "第$i回 ttfb=%{time_starttransfer}s total=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"モデルID","messages":[{"role":"user","content":"こんにちは"}],"max_tokens":128}'
done
```

TTFT と総時間を SLA と比較。長文脈（8k / 32k トークン）でも一度測定してください。

### Step 8 · クォータと課金

`/v1/dashboard/billing/usage` は**累計使用量**（`total_usage`）を返し、残高ではありません（残高は「個人 → ウォレット」）。`total_usage` はサイト表示通貨に換算され、その通貨の **1/100** 単位（USD サイトなら米セント）で表されるため、呼び出し前後の差を 100 で割るとドル金額になります。呼び出し前後を比較します。

```bash
# 呼び出し前
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# （ここで Step 3 の対話を実行）

# 呼び出し後
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

単一応答の `usage` と「一般 → 利用履歴／タスク履歴」の課金明細でも照合できます。

`/v1/dashboard/billing/subscription` は OpenAI 互換の**クォータ上限**照会です。フィールド名は `_usd` ですが、値はサイト表示通貨（USD / CNY / tokens）に従い、実際の支払いサブスクリプションではありません。`access_until` はトークン統計モードのときだけ値が入ります。

### Step 9 · エラーの可読性

```bash
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"モデルID","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

`{"error":{"message":...,"type":...,"code":...}}` と 4xx が返れば、クライアントで扱えます。

## 非同期タスク型モデル（画像／動画／音楽）

**投入 → ポーリング → 取得** の流れです。

1. **投入**：「管理者 → チャネルプラグイン」（`/task-plugins`、スーパー管理者のみ）で有効なプラグインを確認し、そのインターフェースから送信。汎用 `POST /v1/tasks/<プラグインkey>`、動画 `POST /v1/video/generations` または OpenAI スタイル `POST /v1/videos`。OpenAI 互換の `POST /v1/images/generations` は対応チャネル／プラグインが処理。
2. **照会**：返された `task_id` で `GET /v1/tasks/<task_id>`、`GET /v1/video/generations/<task_id>` または `GET /v1/videos/<task_id>`。完了までは待機中／処理中。
3. **成果物**：`GET /v1/tasks/<task_id>/artifacts` で一覧、`GET /v1/tasks/<task_id>/artifacts/<artifact_key>/content` で取得（署名付きアクセスパラメータでもトークンなしでダウンロード可）。動画は `GET /v1/videos/<task_id>/content`。
4. **確認**：「一般 → タスク履歴」で状態・進捗・所要時間・失敗理由を確認。**返金はタスク履歴に載りません**、「一般 → 利用履歴」に「非同期タスク返金」タイプとして記録されます。
5. **境界**：タイムアウトや不正パラメータで、タスクが停止せず失敗状態へ遷移することを確認。

## トラブルシューティング

| # | 症状 | HTTP | 原因の候補 | 対処 |
| --- | --- | --- | --- | --- |
| **A1** | 無効なトークン | 401 | キーの欠落・誤記・無効化 | 「一般 → APIキー」から完全なキーを再取得し「有効」を確認。空白に注意 |
| **A2** | このトークンは期限切れです | 401 | 有効期限切れ | 新しいキーを作成、または無期限に設定 |
| **A3** | クォータが枯渇しています | 401 | キー自体のクォータ切れ | 「一般 → APIキー」でクォータを補充、または新規作成 |
| **A4** | Your IP address is not on this token's allowlist | 403 | IP 許可リスト（CIDR）外 | 送信元 IP／範囲を追加、テスト環境では制限を一時解除 |
| **A5** | いかなるモデルにもアクセスできません | 403 | モデル制限が空 | キーを編集しモデルを選択 |
| **A6** | モデル「xxx」にアクセスできません | 403 | モデルが許可リスト外 | 制限を更新、または許可されたキーを使用 |
| **A7** | 接続不可／タイムアウト | — | URL 誤り、証明書、閉域網 | API 専用エンドポイント `https://api.uter.ai/v1` またはコンソールサイトのアドレス + `/v1` を確認。プロキシ時は `--noproxy '*'` |
| **B1** | クォータ不足 | 403 | アカウント／キーのクォータ不足 | 「個人 → ウォレット」でチャージ、または「一般 → APIキー」でキーに補充。Step 8 で確認 |
| **B2** | グループ「default」配下のモデル「xxx」の利用可能なチャネルがありません | 503（条件により 400） | 有効チャネルなし | 価格ページ `/pricing` でチャネル別に確認（左のサイドバーは既定で Claude-Basic のみ、「すべてのチャネル」をクリック）。プラットフォームへ連絡し、名前を推測しない |
| **B3** | 404／モデル不在 | 404 | 名前の誤り、未開放 | Step 2 で一覧から `id` を厳密にコピー |
| **C1** | リクエスト制限に達しました | 429 | キー／プラットフォーム制限 | 並列を下げ、指数バックオフ、RPM/TPM を確認 |
| **C2** | グループ／上流が飽和 | 429 / 503 | 一時的な容量不足 | バックオフして再試行、必要ならプラットフォームへ連絡 |
| **C3** | 5xx／上流タイムアウト（再試行で成功） | 5xx | 上流の不安定 | バックオフ再試行。プラットフォームも限定的に再試行するがクライアント側も必要 |
| **D1** | ストリーミングが一括で届く | — | クライアントのバッファ | curl は `-N`、SDK は `stream: true` とバッファ無効を確認 |
| **D2** | 文字化け | — | エンコーディング／解析 | UTF-8 を両側で使用。`json.tool` が正常なら端末側の問題 |
| **D3** | 出力が途中で切れる | — | `max_tokens` 不足／モデル上限 | `max_tokens` を増やす、長文はストリーミング |
| **E1** | 課金が想定と違う | — | 推論・キャッシュ・ツール等の隠れトークン、倍率差 | `usage` と「一般 → 利用履歴」の課金明細で照合 |
| **E2** | Function calling／JSON モードが動かない | — | モデルが非対応 | Step 5 で確認し、業務側でフォールバック |
| **E3** | 価格カードに「価格未設定」・課金式の原文・公式価格なしと表示 | — | プラットフォーム側の価格／公式価格データの問題 | モデル名とチャネルを控えてプラットフォームへ連絡。式を自分で解析したり倍率を変更したりしない |
| **F1** | 400＋告知風メッセージ | 400 | 上流供給の告知 | リクエストを確認後、原文を添えてプラットフォームへ連絡 |

<Callout type="idea">
  「チャネルなし／モデル不在」は `GET /v1/models` と価格ページ `/pricing` のチャネル表示を確認してから問い合わせる。「401/403」はキー状態・モデル制限・IP 許可リスト、その後にベース URL を確認する。
</Callout>

## 400（Bad Request）の対処

`400` はリクエスト内容／パラメータが不正という意味で、401（認証）、403（権限・クォータ）、429（制限）とは異なります。

| メッセージの傾向 | 発生元 | 対処 |
| --- | --- | --- |
| 中国語・プラットフォーム風 | 転送前の検証 | 指示どおり修正 |
| 英語・ベンダー風（OpenAI/Claude/Gemini） | 上流の検証 | パラメータ修正（messages 不足、範囲外の値など） |
| 告知風 | 上流供給の変更 | プラットフォームへ原文を添えて連絡 |

プラットフォーム側の例：

| メッセージ | 意味 | 対処 |
| --- | --- | --- |
| `無効なリクエスト: <詳細>` | ボディ検証失敗 | コロン以降の詳細に従う |
| `無効なリクエスト、使用するモデルを特定できません。` | モデル不明 | `"model"` の記載と綴りを確認 |
| `Please specify a model name.` | `model` 欠落 | `model` を追加 |
| `無効なリクエスト: invalid JSON request body` | JSON 不正 | 引用符・カンマ・エスケープを確認 |

モデル設定や価格未設定のメッセージはプラットフォーム側の話題です。リクエストを変えずに問い合わせてください。

上流の例：`messages is required`、`temperature must be between 0 and 2`、`max_tokens too large`、`Unknown parameter: 'xxx'`、`1 validation error for ...`。

30 秒診断（`curl -i` で全体確認）：

```bash
curl -i https://あなたのドメイン/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<モデル名>","messages":[{"role":"user","content":"hi"}]}'
```

まず `message` を読みます。

## 利用履歴での照合

「一般 → 利用履歴」には時刻、チャネル／ユーザー（管理者のみ表示）、キー（グループ付き）、モデル、ストリーミング／TPS、入力／出力／キャッシュ トークン、クォータ、レイテンシ／TTFT、詳細（エラーは詳細ダイアログ内）が記録されます。「一般 → タスク履歴」には送信時刻、プラグイン、タスク ID、所要時間、ステータス、進捗、成果物、詳細（失敗理由）が記録されます。連携中は：

- モデル名・グループ／チャネル・クォータが想定どおりか確認；
- 失敗時は原文を保存し、プラットフォーム側／上流側を切り分け；
- キー・完全なヘッダー・個人情報を自分のログに残さない。

### エラー形式

OpenAI 互換エンドポイントのエラーは既定で OpenAI 形式です：

```json
{
  "error": {
    "message": "人が読める理由",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "任意のコード",
    "param": "任意のパラメータ名",
    "metadata": "任意の追加コンテキスト"
  }
}
```

ただしクライアントで個別に扱う必要がある例外があります：

| シナリオ | 実際の応答 |
| --- | --- |
| Claude 原生 `POST /v1/messages` | Anthropic 形状 `{"type":"error","error":{"type":...,"message":...}}` |
| WebSocket（Responses / Realtime） | エラーはイベントフレームで送られ、HTTP ステータスには出ない |
| 課金系エンドポイントのエラー | 多くは HTTP 200 + `{"error":{"message":...,"type":"uter_error"}}` |
| ミドルウェアの認証／レート制限エラー | `type` が `new_api_error` のことがあり、`param` がない |
| `GET /v1/models/:model` でモデル不明 | HTTP 200 + `error.code = "model_not_found"` |

HTTP ステータス（401 認証／403 権限またはクォータ／404 ルート不在／429 制限／501 未実装の互換エンドポイント／5xx 上流）と組み合わせて処理します。**HTTP ステータスだけに依存しないでください**：課金とモデル取得では「HTTP 200 + error」があり得るため、まず body を解析する必要があります。

### セキュリティ

- **キー＝パスワード**：サーバー側またはシークレット管理のみ。
- **ログの秘匿**：`Authorization` を自分のログに残さない。
- **制限と再試行**：必ずバックオフ。再試行の嵐は障害を拡大します。
