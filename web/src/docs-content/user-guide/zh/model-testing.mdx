# 模型测试

准备把某个大模型接入 Uter 时，按本章逐项验证「能不能连、能不能用、用得稳不稳、算得准不准」，避免上线后才发现问题。

建议先在控制台的**游乐场**里点一遍，再用 API 复测；两步走能最快区分「模型本身不可用」和「你的调用写错了」。

## 测试前置

开始前先确认已经拿到下面这些信息。缺任何一项，第一步就会失败。

| 项目 | 说明 | 在哪里拿 |
| --- | --- | --- |
| **API 接入地址（Base URL）** | 推荐 `https://api.uter.ai/v1`；国内可换 `https://api.uter.cc/v1`，海外可换 `https://api.uter.pro/v1` | 平台访问地址 + `/v1` |
| **API 密钥（API Key）** | 形如 `sk-xxxxxxxx`。这是鉴权凭证，等同于密码，不要外泄、不要写进前端代码、不要提交到代码仓库 | 管理 → API 密钥 → 创建 API 密钥 |
| **额度（Quota）** | 平台内部计费单位：**500,000 额度 = 1 美元**；不同模型按倍率折算，钱包/用量页按站点币种显示金额。额度不足会被拒 | 管理 → 钱包；管理 → 使用日志 |
| **模型名称** | 模型在平台里的注册名（不一定等于官方原名） | 管理 → 定价；或接口 `GET /v1/models` 返回的 `id` |

### 渠道与分组：先弄清两个概念

- **分组（Group）**：决定计费倍率与可路由范围。你的 API 密钥属于哪个分组，就按该分组的倍率和可用模型计费、路由。
- **渠道（Channel）**：真正承载模型的上游提供方（如优特渠道、聚合渠道、共享渠道等）。一个模型可以同时由多条启用渠道提供，也可以只由某一条提供。

因此同一个模型在不同时间、不同分组下，可用性和价格可能不同。如果平台提示「没有可用渠道」，说明该模型当前没有启用渠道能服务你的分组，不是你的请求格式写错。

<Callout type="warn">
  密钥等同于密码：只在服务端或密钥管理系统里使用，绝不下发到浏览器、绝不明文写入日志、绝不提交 Git。
</Callout>

### 先确认密钥的可用性与限制

API 密钥在控制台有四种状态：**已启用、已禁用、已过期、已耗尽**。创建或编辑密钥时还可以施加以下限制，测试前先核对：

- **过期时间**：默认「永不过期」，设置过则到期后调用返回 401。
- **额度上限**：可设置专用额度或「无限额度」；用尽后状态变为「已耗尽」。
- **模型限制**：只允许调用部分模型。未勾选任何模型时该密钥无法调用任何模型。
- **IP 白名单**：支持 CIDR（如 `203.0.113.0/24`）；不在名单内的来源会被拒绝。
- **允许查询用户额度**：控制是否可用该密钥查询 `/v1/dashboard/billing/*`。

## 最快的验证：先在游乐场里点一遍

管理 → 游乐场提供与 API 相同的模型调用链路，适合先排除「模型是否可用、参数是否生效」。

1. 左侧选择**渠道**，右侧列出该渠道承载的模型；选中要测的模型。
2. 直接发一条消息，观察是否正常回复；回复过程默认按流式返回。
3. 打开「参数设置」，按需启用 `temperature`、`top_p`、`max_tokens`、`frequency_penalty`、`presence_penalty`、`seed`——只有启用的参数才会随请求发送。
4. 需要验证多模态或联网能力时，可用输入框的附件/搜索工具（受模型支持情况限制）。
5. 支持随时停止生成、重新生成、编辑历史消息或清空会话。

游乐场同样按平台的计费规则扣减额度，适合反复调试；正式联调仍以 API 为准。

## 核对模型与价格

管理 → 定价里可以：

- 搜索模型名称；
- 按**渠道、厂商、类型、标签**筛选，确认目标模型由哪些渠道提供；
- 查看每个模型的计费方式（按量 / 按次 / 任务计费）、上下文与支持的端点；
- 对比不同模型的公开价格，避免选到计费口径不符合预期的模型。

## 测试维度

正式接入前，建议按以下十一个维度逐项验证。前 4 项是「能不能用」，中间 5 项是「用得稳不稳、算得准不准」，最后 2 项覆盖异步任务与可观测性。

1. **连通性与鉴权** —— 地址对不对、密钥有没有效、IP 白名单有没有拦。
2. **模型列表与可用性** —— 目标模型是否真实存在、当前分组是否有渠道。
3. **基础对话能力** —— 一次最简请求能否正常返回。
4. **参数与高级能力** —— 流式、`temperature`、`max_tokens`、tools/function calling、视觉多模态、JSON 模式、系统提示词。
5. **流式输出（SSE）** —— 是否逐字返回、能否正确解析。
6. **性能与延迟** —— 首字延迟（TTFT）、整句耗时、长上下文表现。
7. **稳定性与限流** —— 并发、重试、429 限流与上游饱和下的表现。
8. **配额与计费校验** —— 调用后扣费是否准确、使用日志是否对得上。
9. **错误与边界** —— 参数非法、超长输入、模型不可用时的错误是否清晰、可被代码处理。
10. **异步任务型模型** —— 绘图 / 视频 / 音乐等任务型模型的提交、轮询与产物下载。
11. **可观测性** —— 使用日志 / 任务日志能否定位每次调用的模型、渠道、耗时、额度与失败原因。

## 分步操作（API）

以下示例统一约定：

- 接入地址 `BASE=https://api.uter.ai/v1`（请替换成你实际的地址）
- 密钥 `TOKEN=sk-your-token-here`（请替换成你控制台拿到的完整密钥）

所有示例用 `curl`。本机若配置了代理，请加 `--noproxy '*'` 绕过代理。

### Step 1 · 最小连通性 + 鉴权测试

```bash
BASE=https://api.uter.ai/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

判定标准：

- 返回一段 JSON（含 `object: "list"` 与若干 `id`）→ 连通 + 鉴权 OK。
- 返回 `{"error":{"message":"该令牌无效。",...}}` 且 HTTP 401 → 密钥错了或被禁用。
- 返回「该令牌没有任何模型访问权限。」或「该令牌无权访问模型「xxx」。」→ 密钥的模型限制没有放行目标模型。
- 完全连不上 / 超时 → 地址错了或网络不通。

<Callout type="info">
  平台同时兼容各厂商原生鉴权：Claude 用 `POST /v1/messages` 加 `x-api-key: $TOKEN` 与 `anthropic-version: 2023-06-01`；Gemini 用 `GET /v1beta/models` 加 `x-goog-api-key: $TOKEN`（或在 URL 后带 `?key=$TOKEN`）。OpenAI 兼容端点统一用 `Authorization: Bearer`。
</Callout>

### Step 2 · 列出模型并查看单个模型

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40

curl --noproxy '*' -s "$BASE/models/替换为你的模型id" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

找到你要测的模型 `id`（例如 `gpt-4o`、`claude-3-5-sonnet-20241022` 或平台自定义名）。

<Callout type="warn">
  如果列表里没有目标模型，先到「管理 → 定价」按渠道确认该模型是否由当前可用的渠道提供，再联系平台。不要自己猜名字硬调，通常会得到 404 或「没有可用渠道」。
</Callout>

### Step 3 · 一次最简对话（非流式）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替换为你的模型id",
    "messages": [{"role": "user", "content": "用一句话介绍你自己。"}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

判定标准：`choices[0].message.content` 有正常文本、`usage` 字段有 `prompt_tokens` / `completion_tokens` → 基础对话能力 OK。

### Step 4 · 流式输出（SSE）测试

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替换为你的模型id",
    "messages": [{"role": "user", "content": "数到 10。"}],
    "stream": true
  }'
```

判定标准：控制台应逐行滚动 `data: {...}` 片段，最后以 `data: [DONE]` 结束。能正确逐字返回 = 流式 OK。

<Callout type="info">
  用 `curl` 必须加 `-N`（禁用缓冲）才能看到逐字效果；SDK 侧要确认已开启 `stream: true` 且没有做整体缓冲。
</Callout>

### Step 5 · 高级能力：工具调用（Function Calling）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替换为你的模型id",
    "messages": [{"role": "user", "content": "北京现在天气怎么样？"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询城市天气",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

判定标准：返回里出现 `choices[0].message.tool_calls`（模型决定调用 `get_weather`），而不是自己编答案 → 工具调用 OK。

<Callout type="warn">
  若业务依赖 function calling、JSON 模式或视觉输入，请务必单独测，不要假设「能聊天就都能用」。
</Callout>

### Step 6 · 多模态（视觉）测试（仅当模型支持图片）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替换为支持视觉的模型id",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "这张图里有什么？"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

判定标准：返回对图片内容的正确描述 → 视觉 OK。图片必须是公网可访问 URL，平台不会读取你本地的文件。

### Step 7 · 延迟与性能基线（建议跑 3~5 次取均值）

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "第$i次 首字节=%{time_starttransfer}s 总耗时=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"替换为你的模型id","messages":[{"role":"user","content":"你好"}],"max_tokens":128}'
done
```

关注首字节时间（TTFT）与总耗时，与业务 SLA 比对。长上下文场景建议再测一次长 prompt（例如 8k / 32k tokens），观察是否线性变慢。

### Step 8 · 配额与计费校验

`/v1/dashboard/billing/usage` 返回的是**已用额度累计**（`total_usage`，按站点显示币种折算），不是剩余余额；余额请看「管理 → 钱包」。校验时对比调用前后的差值：

```bash
# 调用前
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# （中间跑一次 Step 3 的对话）

# 调用后
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

也可以直接看单次响应的 `usage`（`prompt_tokens` + `completion_tokens` 或任务用量），再与「管理 → 使用日志 / 任务日志」中的额度消耗核对。

### Step 9 · 边界与错误可读性

故意制造一次错误，确认错误信息清晰、可被代码捕获：

```bash
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"替换为你的模型id","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

判定标准：返回结构化的 `{"error":{"message":...,"type":...,"code":...}}` 和明确的 HTTP 状态码（4xx），而不是空白或 500 栈信息 → 错误可被正常处理。

## 异步任务型模型（绘图 / 视频 / 音乐）

任务型模型不是「发一条消息就出结果」，而是**提交任务 → 轮询状态 → 下载产物**。测试要点：

1. **提交**：按平台「任务插件」页面给出的接口提交，如通用任务入口 `POST /v1/tasks/<插件key>`、视频 `POST /v1/video/generations`；OpenAI 兼容的 `POST /v1/images/generations` 由对应渠道/插件承接。
2. **轮询**：用返回的 `task_id` 查询，如 `GET /v1/tasks/<task_id>`、`GET /v1/video/generations/<task_id>`；任务完成前状态会是排队 / 处理中。
3. **产物**：`GET /v1/tasks/<task_id>/artifacts` 列出产物，`GET /v1/tasks/<task_id>/artifacts/<artifact_key>/content` 下载内容。
4. **核对**：到「管理 → 使用日志 → 任务日志」确认状态、进度、耗时与扣费；失败任务应显示失败原因，必要时有退款记录。
5. **边界**：测一次超时或非法参数，确认任务会进入失败态而不是一直挂起。

## 常见问题排查表

| # | 现象（你看到的） | HTTP | 可能原因 | 解决方案 |
| --- | --- | --- | --- | --- |
| **A1** | `该令牌无效。` | 401 | 密钥复制不全 / 拼错 / 已被禁用 | 从「管理 → API 密钥」重新复制完整密钥；确认状态为「已启用」，复制时不要截断、不要带多余空格 |
| **A2** | `该令牌已过期，请重新创建一个。` | 401 | 密钥设置了过期时间且已到期 | 新建密钥，或把过期时间设为「永不过期」 |
| **A3** | `该令牌（sk-***）额度已用尽，请补充额度。` | 401 | 密钥自身额度耗尽 | 在「管理 → API 密钥」给该密钥补充额度，或新建密钥 / 改用户额度 |
| **A4** | `您的 IP 不在令牌允许访问的列表中` | 403 | 密钥配置了 IP 白名单（支持 CIDR），当前出口 IP 不在名单内 | 把出口公网 IP / 网段加入白名单；或临时关闭 IP 限制（仅测试环境） |
| **A5** | `该令牌没有任何模型访问权限。` | 403 | 密钥的「模型限制」为空 | 编辑密钥并勾选要使用的模型 |
| **A6** | `该令牌无权访问模型「xxx」。` | 403 | 目标模型不在该密钥的模型限制内 | 编辑密钥的模型限制，或改用允许该模型的密钥 |
| **A7** | 完全连不上 / `Could not resolve host` / 长时间超时 | — | Base URL 写错、自签证书、内网访问 | 核对 Base URL（应为 `https://api.uter.ai/v1`）；本地若走代理需加 `--noproxy '*'`；确认网络可达 |
| **B1** | `您的额度不足。` | 403 | 账号或密钥可用额度不足 | 在「管理 → 钱包」充值，或在「管理 → API 密钥」补额度；用 Step 8 核对已用额度 |
| **B2** | `分组「default」下模型「xxx」没有可用渠道。` | 503（个别过滤条件为 400） | 该模型在当前分组下没有启用渠道 | 到「管理 → 定价」按渠道确认该模型由哪些渠道提供；联系平台确认可用性，不要猜模型名硬调 |
| **B3** | `404` / 模型不存在 | 404 | 模型名写错，或该模型未对你开通 | 用 Step 2 列模型，严格复制返回的 `id` |
| **C1** | `您已触发限流：每 N 分钟最多 X 次请求。` / `您已触发总限流…` | 429 | 触发了密钥级或平台级限流 | 降低并发 / 加退避重试（指数退避）；确认密钥的 RPM/TPM 限额；批量任务错峰 |
| **C2** | 当前分组负载 / 上游已饱和 | 429 / 503 | 上游或分组的并发容量暂时不足 | 稍后重试 + 退避；必要时联系平台扩容或更换分组 |
| **C3** | 偶发 `5xx` / 上游超时，重试后成功 | 5xx | 上游模型波动 | 实现失败重试 + 退避；平台侧也会做有限重试，但客户端仍应兜底 |
| **D1** | 流式输出一次全出来、不是逐字 | — | 客户端缓冲（curl 没加 `-N`，或 SDK 没开 stream） | curl 加 `-N`；SDK 确认 `stream: true` 且未做整体缓冲 |
| **D2** | 中文 / 特殊字符乱码 | — | 未声明编码或解析出错 | 请求与响应均按 UTF-8；`python3 -m json.tool` 正常显示即服务端 OK，问题在本地终端编码 |
| **D3** | 返回内容被截断 | — | `max_tokens` 设太小，或模型达到输出上限 | 调大 `max_tokens`；长文改用流式分段接收 |
| **E1** | 扣费与预期不符（多扣 / 少扣） | — | 计费口径含思维链、缓存命中、工具调用等 token，或不同模型倍率不同 | 以单次响应 `usage` 与「使用日志」中的计费明细为准；有疑问联系平台 |
| **E2** | function calling 不触发 / JSON 模式不生效 | — | 该模型未开放对应能力 | 用 Step 5 单独验证；不支持的能力不要强依赖，需在业务层降级 |
| **F1** | `400` + 中文「公告式」提示 | 400 | 上游供应商在报错里发通知，不是你请求写错 | 确认请求格式无误后，联系平台并附上报错原文 |

<Callout type="idea">
  两条最值得记住的经验：凡是报「没有可用渠道 / 模型找不到」，先 `GET /v1/models` 与「定价」页核对真实模型名和渠道，再联系平台——**多数「模型用不了」都是这两个原因**，不是代码问题。凡是 `401/403`，先核对密钥状态、模型限制与 IP 白名单，再核对 Base URL——**鉴权类问题几乎都出在「复制不全 / 限制没放行 / 地址错」**。
</Callout>

## 遇到 400 报错怎么办（Bad Request）

`400` 表示「请求本身有问题」：服务器收到了你的请求，但请求内容或参数不合法，被直接拒绝。它和鉴权（401）、权限 / 额度（403）、限流（429）不是一类。

先按错误文案判断来源：

| 你看到的提示 | 通常来源 | 该怎么做 |
| --- | --- | --- |
| 中文、像平台提示 | 平台在转发前校验请求 | 按提示修改请求参数 |
| 英文、像 OpenAI / Claude / Gemini 的报错 | 上游模型商返回（参数不符合该模型要求） | 按提示修改参数（如补充 messages、调整越界值） |
| 中文、像「通知 / 公告」 | 上游模型供应临时变动 | 不是你写错，直接联系平台并提供报错原文 |

平台侧常见的 400 提示：

| 你看到的提示 | 含义 | 解决 |
| --- | --- | --- |
| `请求不合法：<具体错误>` | 平台校验请求体失败 | 看冒号后的具体说明，照着改 |
| `请求不合法，无法识别您要使用哪个模型。` | 没解析出要用的模型 | 确认请求里 `"model": "模型名"` 已填写且拼写正确 |
| `请指定模型名称。` | 没传 `model` 字段 | 补上 `model` 参数 |
| `请求不合法：invalid JSON request body` | 请求体 JSON 格式有误 | 检查引号、逗号、转义，尤其是中文与换行 |

<Callout type="info">
  如果你看到类似「模型配置」「价格未配置」这类提示，属于平台侧问题，直接联系平台处理即可，无需修改请求。
</Callout>

上游模型常见的 400 提示：

- `messages is required` / `messages must be a non-empty array` —— 漏了 `messages` 或为空
- `temperature must be between 0 and 2` / `max_tokens too large` —— 参数越界
- `Unknown parameter: 'xxx'` —— 传了该模型不支持的字段
- `1 validation error for ...` —— 字段类型或必填项不符

30 秒定位（curl 加 `-i` 看完整响应）：

```bash
curl -i https://api.uter.ai/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<模型名>","messages":[{"role":"user","content":"hi"}]}'
```

重点看响应里的 `message`——它通常已写明直接原因。

## 用日志核对每次调用

「管理 → 使用日志」会记录每次请求的时间、模型、令牌、渠道（管理员可见）、耗时、额度消耗与错误信息；「任务日志」记录异步任务的状态、进度与产物。联调阶段建议：

- 每次测试后核对日志中的模型名、分组 / 渠道和额度是否与预期一致；
- 失败请求保留原始错误信息，便于区分平台侧与上游侧问题；
- 不要把密钥、完整请求头或用户隐私写入你自己的日志。

### 错误响应统一格式

平台 API 错误为 OpenAI 风格结构，便于统一处理：

```json
{
  "error": {
    "message": "人类可读的错误原因",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "可选的错误码",
    "param": "可选的问题参数名"
  }
}
```

配合 HTTP 状态码（401 鉴权 / 403 权限或额度 / 404 模型 / 429 限流 / 5xx 上游）即可覆盖绝大多数客户端处理逻辑。

### 安全提醒（务必遵守）

- **密钥 = 密码**：只在服务端 / 密钥管理里使用，绝不下发到浏览器、绝不明文进日志、绝不提交 Git。
- **日志脱敏**：平台审计不会记录你的密钥明文；客户端打印响应时，也要避免把 `Authorization` 头写进日志。
- **限流与重试**：务必实现退避重试，避免雪崩式重试把限流打成全面不可用。
