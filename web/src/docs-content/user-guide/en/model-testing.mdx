# Model Testing

Before wiring a model into Uter, verify it step by step — can it connect, can it answer, is it stable, is it billed correctly — so problems surface before production.

Start with the **Playground** in the console, then re-check over the API. That split quickly separates “the model is unavailable” from “my request is wrong”.

## Before you start

Confirm you have the items below. Missing any one of them makes step 1 fail.

| Item | What it is | Where to get it |
| --- | --- | --- |
| **API Base URL** | e.g. `https://your-domain/v1`; use the domain this console is served from (your dedicated domain may differ) | Site address + `/v1` |
| **API Key** | e.g. `sk-xxxxxxxx`. This is a credential equal to a password: never expose it, never ship it to the browser, never commit it | Console → API Keys → Create API Key |
| **Quota** | Internal billing unit: **500,000 quota = US$1**; each model applies its own ratio and the wallet/usage screens show the site currency. Calls are rejected when quota runs out | Console → Wallet; Console → Usage Logs |
| **Model name** | The registered name in Uter (not necessarily the vendor's original name) | Console → Pricing; or the `id` from `GET /v1/models` |

### Channels and groups: two different dimensions

- **Group**: determines billing ratio and the routable model set. A key bills and routes according to its group.
- **Channel**: the upstream provider that actually serves a model (e.g. Uter channel, aggregate channel, shared channel). One model can be served by several enabled channels, or by a single one.

The same model can therefore differ in availability and price across groups and over time. “No available channel” means no enabled channel currently serves that model for your group — not that your request is malformed.

<Callout type="warn">
  An API key is a password: use it only server-side or in a secret manager. Never send it to a browser, never log it in plaintext, never commit it.
</Callout>

### Check key status and limits first

API keys have four states: **Enabled, Disabled, Expired, Exhausted**. Creating or editing a key can also apply:

- **Expiry**: “Never expires” by default; after expiry calls return 401.
- **Quota cap**: a dedicated allowance or “Unlimited”. When used up the key becomes Exhausted.
- **Model limits**: allow only selected models. With no model selected the key cannot call anything.
- **IP allowlist**: supports CIDR (e.g. `203.0.113.0/24`); other sources are rejected.
- **Allow querying user quota**: whether this key may call `/v1/dashboard/billing/*`.

## Fastest check: try it in the Playground

Console → Playground exercises the same model path as the API.

1. Pick a **channel** on the left; the right pane lists that channel's models. Select the model to test.
2. Send a message and watch the reply (streamed by default).
3. Open Parameter settings and enable what you need: `temperature`, `top_p`, `max_tokens`, `frequency_penalty`, `presence_penalty`, `seed`. Only enabled parameters are sent.
4. To test multimodal or web-search behaviour, use the composer's attach / search tools (subject to model support).
5. Stop, regenerate, edit history, or clear the conversation at any time.

The Playground bills quota under the same rules, which makes it ideal for iteration; still confirm over the API before shipping.

## Check the model and its price

Console → Pricing lets you:

- search by model name;
- filter by **channel, vendor, type, tag** to see which channels serve a model;
- inspect billing mode (per token / per request / per task), context limits and supported endpoints;
- compare public prices before choosing a model.

## Test dimensions

Verify these eleven dimensions before going live. The first four answer “can it be used”, the next five “is it stable and billed correctly”, and the last two cover async tasks and observability.

1. **Connectivity and auth** — right URL, valid key, IP allowlist not blocking.
2. **Model list and availability** — the model exists and your group has a serving channel.
3. **Basic chat** — one minimal request returns a real answer.
4. **Parameters and advanced abilities** — streaming, `temperature`, `max_tokens`, tools/function calling, vision, JSON mode, system prompts.
5. **Streaming (SSE)** — token-by-token output that parses correctly.
6. **Performance** — time to first token (TTFT), total latency, long-context behaviour.
7. **Stability and rate limits** — concurrency, retries, 429s and upstream saturation.
8. **Quota and billing** — correct deductions that match the usage logs.
9. **Errors and boundaries** — clear, machine-readable failures for bad input or unavailable models.
10. **Async task models** — submit, poll and download for image / video / music tasks.
11. **Observability** — usage/task logs identify model, channel, latency, quota and failure reason per call.

## Step by step (API)

Shared conventions:

- `BASE=https://your-domain/v1` (replace with your own)
- `TOKEN=sk-your-token-here` (the full key from the console)

Examples use `curl`. If a proxy is configured locally, add `--noproxy '*'`.

### Step 1 · Minimal connectivity + auth

```bash
BASE=https://your-domain/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

What to look for:

- JSON with `object: "list"` and several `id`s → connectivity and auth are fine.
- HTTP 401 with `That token isn’t valid.` → wrong or disabled key.
- `This token doesn’t have access to any models.` or `This token can’t access the model «xxx».` → the key's model limits exclude the target.
- Connection failure / timeout → wrong URL or network issue.

<Callout type="info">
  Native vendor auth is supported too: Claude via `POST /v1/messages` with `x-api-key: $TOKEN` and `anthropic-version: 2023-06-01`; Gemini via `GET /v1beta/models` with `x-goog-api-key: $TOKEN` (or `?key=$TOKEN`). OpenAI-compatible endpoints use `Authorization: Bearer`.
</Callout>

### Step 2 · List models and inspect one

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40

curl --noproxy '*' -s "$BASE/models/your-model-id" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

Copy the exact `id` you want to test (e.g. `gpt-4o`, `claude-3-5-sonnet-20241022`, or a custom name).

<Callout type="warn">
  If the model is missing, check Console → Pricing by channel first, then contact the platform. Do not guess names: that usually yields 404 or “no available channel”.
</Callout>

### Step 3 · One minimal chat call (non-streaming)

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-model-id",
    "messages": [{"role": "user", "content": "Introduce yourself in one sentence."}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

Pass when `choices[0].message.content` contains text and `usage` reports `prompt_tokens` / `completion_tokens`.

### Step 4 · Streaming (SSE)

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-model-id",
    "messages": [{"role": "user", "content": "Count to 10."}],
    "stream": true
  }'
```

Pass when `data: {...}` chunks keep arriving and end with `data: [DONE]`.

<Callout type="info">
  With `curl` you must pass `-N` to disable buffering; SDKs must send `stream: true` and not buffer the whole body.
</Callout>

### Step 5 · Advanced ability: function calling

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-model-id",
    "messages": [{"role": "user", "content": "What is the weather in Beijing right now?"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Look up city weather",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

Pass when the response contains `choices[0].message.tool_calls` (the model asks for `get_weather`) instead of inventing an answer.

<Callout type="warn">
  If your product depends on function calling, JSON mode or vision, test each one separately — “it can chat” does not imply them.
</Callout>

### Step 6 · Multimodal (vision), only for models that accept images

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-vision-model-id",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "What is in this image?"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

Pass when the reply describes the image correctly. The image must be publicly reachable; the platform will not read local files.

### Step 7 · Latency baseline (run 3–5 times, average)

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "run $i ttfb=%{time_starttransfer}s total=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"your-model-id","messages":[{"role":"user","content":"hello"}],"max_tokens":128}'
done
```

Compare TTFT and total time with your SLA. Also test a long prompt (e.g. 8k / 32k tokens) to see whether latency grows linearly.

### Step 8 · Quota and billing check

`GET /v1/dashboard/billing/usage` returns **cumulative usage** (`total_usage`, in the site display currency), not the remaining balance — see Console → Wallet for the balance. Compare before/after:

```bash
# Before
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# (run Step 3 here)

# After
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

You can also read `usage` from a single response (`prompt_tokens` + `completion_tokens`, or task usage) and cross-check it with the quota shown in Console → Usage Logs / Task Logs.

### Step 9 · Boundaries and readable errors

Produce one bad request and confirm the error is clear and machine-readable:

```bash
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"your-model-id","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

Pass when the answer is a structured `{"error":{"message":...,"type":...,"code":...}}` with a 4xx status, not an empty body or a 500 stack trace.

## Async task models (image / video / music)

Task models are **submit → poll → download**, not one request → one answer:

1. **Submit** via the endpoint shown on the platform's task-plugin page — the generic `POST /v1/tasks/<plugin-key>`, video `POST /v1/video/generations`, or the OpenAI-compatible `POST /v1/images/generations` handled by the matching channel/plugin.
2. **Poll** with the returned `task_id`: `GET /v1/tasks/<task_id>` or `GET /v1/video/generations/<task_id>`. Until completion the status is queued / processing.
3. **Artifacts**: `GET /v1/tasks/<task_id>/artifacts` lists outputs; `GET /v1/tasks/<task_id>/artifacts/<artifact_key>/content` downloads one.
4. **Verify** in Console → Usage Logs → Task Logs: status, progress, duration and quota; failed tasks should show a reason, with an async-task refund where applicable.
5. **Edge cases**: trigger one timeout or invalid parameter and confirm the task ends in a failed state instead of hanging forever.

## Troubleshooting

| # | What you see | HTTP | Likely cause | Fix |
| --- | --- | --- | --- | --- |
| **A1** | `That token isn’t valid.` | 401 | Key truncated, mistyped or disabled | Copy the full key again from Console → API Keys; confirm it is Enabled; no leading/trailing spaces |
| **A2** | `This token has expired. Please create a new one.` | 401 | Expiry passed | Create a new key, or set expiry to never |
| **A3** | `This token (sk-***) has run out of quota. Please add more.` | 401 | Key's own quota exhausted | Add quota to the key in Console → API Keys, or create a new key / raise user quota |
| **A4** | `Your IP address is not on this token's allowlist` | 403 | IP allowlist (CIDR supported) excludes your egress IP | Add the egress IP/range, or disable the restriction in a test environment |
| **A5** | `This token doesn’t have access to any models.` | 403 | Key's model limit list is empty | Edit the key and select the models to allow |
| **A6** | `This token can’t access the model «xxx».` | 403 | Model not in the key's allowlist | Update the model limits, or use a key that allows it |
| **A7** | Connection failure / `Could not resolve host` / timeouts | — | Wrong base URL, self-signed cert, private network | Verify `https://your-domain/v1`; use `--noproxy '*'` when a local proxy is configured; confirm reachability |
| **B1** | `You don’t have enough quota.` | 403 | Account/key quota exhausted | Top up in Console → Wallet or add key quota; verify with Step 8 |
| **B2** | `There’s no available channel for model «xxx» in group «default».` | 503 (400 for some filter cases) | No enabled channel serves the model in this group | Check Console → Pricing by channel; contact the platform; do not guess names |
| **B3** | `404` / model not found | 404 | Wrong model name or no access | List models with Step 2 and copy the `id` exactly |
| **C1** | `You’ve hit the limit: at most X requests every N minutes.` / total-limit variant | 429 | Key or platform rate limit | Lower concurrency, add exponential backoff, check RPM/TPM, stagger batches |
| **C2** | Current group / upstream at capacity | 429 / 503 | Temporary upstream or group saturation | Retry later with backoff; contact the platform or switch group |
| **C3** | Occasional `5xx` / upstream timeout that succeeds on retry | 5xx | Upstream model instability | Retry with backoff; the platform retries a limited number of times, but clients must too |
| **D1** | Streaming arrives all at once | — | Client buffering (`curl` without `-N`, SDK buffering) | Add `-N`; ensure `stream: true` and no whole-body buffering |
| **D2** | Mojibake in Chinese / special characters | — | Encoding or parsing issue | Keep UTF-8 both ways; if `python3 -m json.tool` renders fine, the server is fine and the terminal encoding is at fault |
| **D3** | Output truncated | — | `max_tokens` too small or model output cap | Raise `max_tokens`; stream long answers |
| **E1** | Deduction differs from expectation | — | Hidden tokens (reasoning, cache hits, tools) or model ratio differences | Reconcile with the response `usage` and the billing detail in Usage Logs; ask the platform |
| **E2** | Function calling / JSON mode does nothing | — | The model does not expose it | Verify with Step 5; degrade gracefully in your product |
| **F1** | `400` with an announcement-style message | 400 | Upstream provider notice, not your request | Validate your request format, then contact the platform with the raw error |

<Callout type="idea">
  Two rules worth memorising: for “no available channel / model not found”, list models with `GET /v1/models` and check the Pricing page by channel before contacting the platform — most “the model doesn’t work” reports come from these two. For `401/403`, check key status, model limits and the IP allowlist, then the base URL — auth problems are nearly always truncated keys, unopened limits or a wrong address.
</Callout>

## When you get a 400 (Bad Request)

`400` means the request itself is invalid — the server received it and rejected its content. It differs from auth (401), permission/quota (403) and rate limits (429).

Identify the source from the message:

| Message style | Source | Action |
| --- | --- | --- |
| English/Chinese, platform-style | Uter validated before forwarding | Fix the request as instructed |
| English, vendor-style (OpenAI / Claude / Gemini) | Upstream rejected the parameters | Fix parameters (missing messages, out-of-range values) |
| Announcement-style notice | Upstream supply change | Not your bug; contact the platform with the raw message |

Common platform-side 400s:

| Message | Meaning | Fix |
| --- | --- | --- |
| `The request isn’t valid: <detail>` | Body validation failed | Read the detail after the colon |
| `The request isn’t valid and the model could not be determined.` | No usable model in the request | Ensure `"model": "..."` is present and spelled correctly |
| `Please specify a model name.` | `model` missing | Add the `model` field |
| `The request isn’t valid: invalid JSON request body` | Malformed JSON | Check quotes, commas and escapes, especially with CJK text and newlines |

<Callout type="info">
  Messages about model configuration or missing prices are platform-side; contact the platform instead of editing your request.
</Callout>

Common upstream 400s:

- `messages is required` / `messages must be a non-empty array`
- `temperature must be between 0 and 2` / `max_tokens too large`
- `Unknown parameter: 'xxx'`
- `1 validation error for ...`

30-second diagnosis (`curl -i` for the full response):

```bash
curl -i https://your-domain/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<model-name>","messages":[{"role":"user","content":"hi"}]}'
```

Read `message` first — it usually names the direct cause.

## Reconcile every call in the logs

Console → Usage Logs records time, model, key, channel (admins), latency, quota and error for each request; Task Logs record async task status, progress and artifacts. During integration:

- compare the model, group/channel and quota in the log with what you expected;
- keep the raw error for failures so platform-side and upstream-side issues stay distinguishable;
- never write keys, full request headers or user privacy into your own logs.

## Pre-launch checklist

- [ ] **Base URL** lives in configuration (env / config service), not hard-coded in the frontend.
- [ ] **Key** copied in full, status Enabled, not expired, enough quota.
- [ ] The key's **model limits** include every model the product uses.
- [ ] If the **IP allowlist** is on, production egress IPs/CIDRs are added.
- [ ] `GET /v1/models` lists the target model and the `id` matches the code.
- [ ] Non-streaming chat works and returns `content` and `usage`.
- [ ] Streaming (SSE) works and parses `data:` chunks and `[DONE]`.
- [ ] Required **advanced abilities** (tools / JSON / vision / long context) are verified individually.
- [ ] **Async task models** are verified end to end: submit, poll, download, failure state.
- [ ] Latency baseline (TTFT / total) meets the SLA.
- [ ] The client implements **rate-limit backoff** and **upstream 5xx retries**.
- [ ] Errors are handled structurally via `error.message` / `error.code` / HTTP status, with credentials kept out of logs.
- [ ] Quota deductions reconcile with `usage` and the Usage Logs.
- [ ] Production never prints or commits keys (secret manager / env vars in place).
- [ ] Availability and billing rules for the target model are confirmed with the platform.

### Unified error envelope

API errors use the OpenAI shape:

```json
{
  "error": {
    "message": "Human-readable reason",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "optional code",
    "param": "optional offending parameter"
  }
}
```

Combine it with the HTTP status (401 auth / 403 permission or quota / 404 model / 429 rate limit / 5xx upstream) to cover most client handling.

### Security reminders

- **A key is a password**: server-side or secret manager only; never to a browser, never plaintext in logs, never in Git.
- **Redact logs**: the platform never stores your key in plaintext; your own client must also keep `Authorization` out of its logs.
- **Rate limits and retries**: always back off — a retry storm turns a limit into a full outage.
