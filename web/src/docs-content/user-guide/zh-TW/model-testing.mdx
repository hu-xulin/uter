# 模型測試

準備把某個大模型接入 Uter 時，請依本章逐項驗證「能不能連、能不能用、用得穩不穩、算得準不準」，避免上線後才發現問題。

建議先在控制台的**遊樂場**裡點一遍，再用 API 複測；兩步走能最快區分「模型本身不可用」和「你的呼叫寫錯了」。

## 測試前置

開始前請先確認已取得下列資訊。缺任何一項，第一步就會失敗。

| 項目 | 說明 | 在哪裡拿 |
| --- | --- | --- |
| **API 接入網址（Base URL）** | 形如 `https://你的網域/v1`，以平台實際部署的網域為準（可能是你的專屬網域） | 平台存取位址 + `/v1` |
| **API 金鑰（API Key）** | 形如 `sk-xxxxxxxx`。這是驗證憑證，等同密碼，請勿外洩、勿寫進前端程式碼、勿提交到程式碼倉庫 | 管理 → API 金鑰 → 建立 API 金鑰 |
| **額度（Quota）** | 平台內部計費單位：**500,000 額度 = 1 美元**；不同模型按倍率折算，錢包／用量頁按站台幣別顯示金額。額度不足會被拒絕 | 管理 → 錢包；管理 → 使用日誌 |
| **模型名稱** | 模型在平台裡的註冊名稱（不一定等於官方原名） | 管理 → 定價；或介面 `GET /v1/models` 回傳的 `id` |

### 管道與分組：先釐清兩個概念

- **分組（Group）**：決定計費倍率與可路由範圍。你的 API 金鑰屬於哪個分組，就按該分組的倍率與可用模型計費、路由。
- **管道（Channel）**：真正承載模型的上游提供方（如優特管道、聚合管道、共享管道等）。一個模型可以同時由多條啟用管道提供，也可以只由某一條提供。

因此同一個模型在不同時間、不同分組下，可用性與價格可能不同。若平台提示「沒有可用管道」，代表該模型目前沒有啟用管道能服務你的分組，不是你的請求格式寫錯。

<Callout type="warn">
  金鑰等同密碼：只在伺服器端或金鑰管理系統中使用，絕不下發到瀏覽器、絕不明文寫入日誌、絕不提交 Git。
</Callout>

### 先確認金鑰的可用性與限制

API 金鑰在控制台有四種狀態：**已啟用、已停用、已過期、已耗盡**。建立或編輯金鑰時還可施加以下限制，測試前請先核對：

- **到期時間**：預設「永不過期」，設定過則到期後呼叫回傳 401。
- **額度上限**：可設定專用額度或「無限額度」；用盡後狀態變為「已耗盡」。
- **模型限制**：只允許呼叫部分模型。未勾選任何模型時該金鑰無法呼叫任何模型。
- **IP 白名單**：支援 CIDR（如 `203.0.113.0/24`）；不在名單內的來源會被拒絕。
- **允許查詢使用者額度**：控制是否可用該金鑰查詢 `/v1/dashboard/billing/*`。

## 最快的驗證：先在遊樂場裡點一遍

管理 → 遊樂場提供與 API 相同的模型呼叫鏈路，適合先排除「模型是否可用、參數是否生效」。

1. 左側選擇**管道**，右側列出該管道承載的模型；選中要測的模型。
2. 直接送出一則訊息，觀察是否正常回覆；回覆過程預設以串流返回。
3. 打開「參數設定」，按需啟用 `temperature`、`top_p`、`max_tokens`、`frequency_penalty`、`presence_penalty`、`seed`——只有啟用的參數才會隨請求送出。
4. 需要驗證多模態或聯網能力時，可使用輸入框的附件／搜尋工具（受模型支援情況限制）。
5. 可隨時停止生成、重新生成、編輯歷史訊息或清空會話。

遊樂場同樣按平台計費規則扣減額度，適合反覆除錯；正式聯調仍以 API 為準。

## 核對模型與價格

管理 → 定價可以：

- 搜尋模型名稱；
- 按**管道、廠商、類型、標籤**篩選，確認目標模型由哪些管道提供；
- 查看每個模型的計費方式（按量／按次／任務計費）、上下文與支援的端點；
- 比較不同模型的公開價格，避免選到計費口徑不符預期的模型。

## 測試維度

正式接入前，建議依下列十一個維度逐項驗證。前 4 項是「能不能用」，中間 5 項是「用得穩不穩、算得準不準」，最後 2 項涵蓋非同步任務與可觀測性。

1. **連線與驗證** —— 網址對不對、金鑰有沒有效、IP 白名單有沒有攔。
2. **模型列表與可用性** —— 目標模型是否真實存在、目前分組是否有管道。
3. **基礎對話能力** —— 一次最簡請求能否正常回傳。
4. **參數與進階能力** —— 串流、`temperature`、`max_tokens`、tools/function calling、視覺多模態、JSON 模式、系統提示詞。
5. **串流輸出（SSE）** —— 是否逐字回傳、能否正確解析。
6. **效能與延遲** —— 首字延遲（TTFT）、整句耗時、長上下文表現。
7. **穩定性與限流** —— 併發、重試、429 限流與上游飽和下的表現。
8. **配額與計費校驗** —— 呼叫後扣費是否準確、使用日誌是否對得上。
9. **錯誤與邊界** —— 參數非法、超長輸入、模型不可用時的錯誤是否清晰、可被程式碼處理。
10. **非同步任務型模型** —— 繪圖／影片／音樂等任務型模型的提交、輪詢與產物下載。
11. **可觀測性** —— 使用日誌／任務日誌能否定位每次呼叫的模型、管道、耗時、額度與失敗原因。

## 分步操作（API）

以下範例統一約定：

- 接入網址 `BASE=https://你的網域/v1`（請替換成你實際的網址）
- 金鑰 `TOKEN=sk-your-token-here`（請替換成你在控制台取得的完整金鑰）

所有範例使用 `curl`。本機若設有代理，請加 `--noproxy '*'` 繞過代理。

### Step 1 · 最小連通性 + 驗證測試

```bash
BASE=https://你的網域/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

判定標準：

- 回傳一段 JSON（含 `object: "list"` 與若干 `id`）→ 連通 + 驗證 OK。
- 回傳 `{"error":{"message":"該令牌無效。",...}}` 且 HTTP 401 → 金鑰錯了或被停用。
- 回傳「該令牌沒有任何模型存取權限。」或「該令牌無權存取模型「xxx」。」→ 金鑰的模型限制沒有放行目標模型。
- 完全連不上／逾時 → 網址錯了或網路不通。

<Callout type="info">
  平台同時相容各廠商原生驗證：Claude 用 `POST /v1/messages` 加 `x-api-key: $TOKEN` 與 `anthropic-version: 2023-06-01`；Gemini 用 `GET /v1beta/models` 加 `x-goog-api-key: $TOKEN`（或在 URL 後帶 `?key=$TOKEN`）。OpenAI 相容端點統一用 `Authorization: Bearer`。
</Callout>

### Step 2 · 列出模型並查看單一模型

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40

curl --noproxy '*' -s "$BASE/models/替換為你的模型id" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

找到你要測的模型 `id`（例如 `gpt-4o`、`claude-3-5-sonnet-20241022` 或平台自訂名稱）。

<Callout type="warn">
  若列表裡沒有目標模型，先到「管理 → 定價」按管道確認該模型是否由目前可用的管道提供，再聯絡平台。不要自己猜名稱硬呼叫，通常會得到 404 或「沒有可用管道」。
</Callout>

### Step 3 · 一次最簡對話（非串流）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替換為你的模型id",
    "messages": [{"role": "user", "content": "用一句話介紹你自己。"}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

判定標準：`choices[0].message.content` 有正常文字、`usage` 欄位有 `prompt_tokens`／`completion_tokens` → 基礎對話能力 OK。

### Step 4 · 串流輸出（SSE）測試

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替換為你的模型id",
    "messages": [{"role": "user", "content": "數到 10。"}],
    "stream": true
  }'
```

判定標準：主控台應逐行滾動 `data: {...}` 片段，最後以 `data: [DONE]` 結束。能正確逐字回傳 = 串流 OK。

<Callout type="info">
  用 `curl` 必須加 `-N`（停用緩衝）才能看到逐字效果；SDK 端要確認已開啟 `stream: true` 且沒有做整體緩衝。
</Callout>

### Step 5 · 進階能力：工具呼叫（Function Calling）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替換為你的模型id",
    "messages": [{"role": "user", "content": "北京現在天氣怎麼樣？"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查詢城市天氣",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

判定標準：回傳中出現 `choices[0].message.tool_calls`（模型決定呼叫 `get_weather`），而不是自己編答案 → 工具呼叫 OK。

<Callout type="warn">
  若業務依賴 function calling、JSON 模式或視覺輸入，請務必單獨測試，不要假設「能聊天就都能用」。
</Callout>

### Step 6 · 多模態（視覺）測試（僅當模型支援圖片）

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "替換為支援視覺的模型id",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "這張圖裡有什麼？"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

判定標準：回傳對圖片內容的正確描述 → 視覺 OK。圖片必須是公網可存取的 URL，平台不會讀取你本地的檔案。

### Step 7 · 延遲與效能基線（建議跑 3~5 次取平均）

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "第$i次 首位元組=%{time_starttransfer}s 總耗時=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"替換為你的模型id","messages":[{"role":"user","content":"你好"}],"max_tokens":128}'
done
```

關注首位元組時間（TTFT）與總耗時，與業務 SLA 比對。長上下文場景建議再測一次長 prompt（例如 8k／32k tokens），觀察是否線性變慢。

### Step 8 · 配額與計費校驗

`/v1/dashboard/billing/usage` 回傳的是**已用額度累計**（`total_usage`，按站台顯示幣別折算），不是剩餘餘額；餘額請看「管理 → 錢包」。校驗時比對呼叫前後的差值：

```bash
# 呼叫前
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# （中間跑一次 Step 3 的對話）

# 呼叫後
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

也可以直接看單次回應的 `usage`（`prompt_tokens` + `completion_tokens` 或任務用量），再與「管理 → 使用日誌／任務日誌」中的額度消耗核對。

### Step 9 · 邊界與錯誤可讀性

故意製造一次錯誤，確認錯誤資訊清晰、可被程式碼捕捉：

```bash
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"替換為你的模型id","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

判定標準：回傳結構化的 `{"error":{"message":...,"type":...,"code":...}}` 與明確的 HTTP 狀態碼（4xx），而不是空白或 500 堆疊資訊 → 錯誤可被正常處理。

## 非同步任務型模型（繪圖／影片／音樂）

任務型模型不是「送一則訊息就出結果」，而是**提交任務 → 輪詢狀態 → 下載產物**。測試要點：

1. **提交**：依平台「任務外掛」頁面提供的介面提交，如通用任務入口 `POST /v1/tasks/<外掛key>`、影片 `POST /v1/video/generations`；OpenAI 相容的 `POST /v1/images/generations` 由對應管道／外掛承接。
2. **輪詢**：用回傳的 `task_id` 查詢，如 `GET /v1/tasks/<task_id>`、`GET /v1/video/generations/<task_id>`；任務完成前狀態會是排隊／處理中。
3. **產物**：`GET /v1/tasks/<task_id>/artifacts` 列出產物，`GET /v1/tasks/<task_id>/artifacts/<artifact_key>/content` 下載內容。
4. **核對**：到「管理 → 使用日誌 → 任務日誌」確認狀態、進度、耗時與扣費；失敗任務應顯示失敗原因，必要時有退款紀錄。
5. **邊界**：測一次逾時或非法參數，確認任務會進入失敗狀態而不是一直掛起。

## 常見問題排查表

| # | 現象（你看到的） | HTTP | 可能原因 | 解決方案 |
| --- | --- | --- | --- | --- |
| **A1** | `該令牌無效。` | 401 | 金鑰複製不全／拼錯／已被停用 | 從「管理 → API 金鑰」重新複製完整金鑰；確認狀態為「已啟用」，複製時不要截斷、不要帶多餘空格 |
| **A2** | `該令牌已過期，請重新建立一個。` | 401 | 金鑰設定了到期時間且已到期 | 建立新金鑰，或把到期時間設為「永不過期」 |
| **A3** | `該令牌（sk-***）額度已用盡，請補充額度。` | 401 | 金鑰自身額度耗盡 | 在「管理 → API 金鑰」為該金鑰補充額度，或建立新金鑰／調整使用者額度 |
| **A4** | `您的 IP 不在令牌允許存取的清單中` | 403 | 金鑰設定了 IP 白名單（支援 CIDR），目前出口 IP 不在名單內 | 把出口公網 IP／網段加入白名單；或暫時關閉 IP 限制（僅測試環境） |
| **A5** | `該令牌沒有任何模型存取權限。` | 403 | 金鑰的「模型限制」為空 | 編輯金鑰並勾選要使用的模型 |
| **A6** | `該令牌無權存取模型「xxx」。` | 403 | 目標模型不在該金鑰的模型限制內 | 編輯金鑰的模型限制，或改用允許該模型的金鑰 |
| **A7** | 完全連不上／`Could not resolve host`／長時間逾時 | — | Base URL 寫錯、自簽憑證、內網存取 | 核對 Base URL（應為 `https://你的網域/v1`）；本機若走代理需加 `--noproxy '*'`；確認網路可達 |
| **B1** | `您的額度不足。` | 403 | 帳號或金鑰可用額度不足 | 在「管理 → 錢包」儲值，或在「管理 → API 金鑰」補額度；用 Step 8 核對已用額度 |
| **B2** | `分組「default」下模型「xxx」沒有可用管道。` | 503（個別篩選條件為 400） | 該模型在目前分組下沒有啟用管道 | 到「管理 → 定價」按管道確認該模型由哪些管道提供；聯絡平台確認可用性，不要猜模型名稱硬呼叫 |
| **B3** | `404`／模型不存在 | 404 | 模型名稱寫錯，或該模型未對你開通 | 用 Step 2 列模型，嚴格複製回傳的 `id` |
| **C1** | `您已觸發限流：每 N 分鐘最多 X 次請求。`／`您已觸發總限流…` | 429 | 觸發了金鑰級或平台級限流 | 降低併發／加入退避重試（指數退避）；確認金鑰的 RPM/TPM 限額；批次任務錯峰 |
| **C2** | 目前分組負載／上游已飽和 | 429／503 | 上游或分組的併發容量暫時不足 | 稍後重試 + 退避；必要時聯絡平台擴容或更換分組 |
| **C3** | 偶發 `5xx`／上游逾時，重試後成功 | 5xx | 上游模型波動 | 實作失敗重試 + 退避；平台端也會做有限重試，但用戶端仍應兜底 |
| **D1** | 串流輸出一次全出來、不是逐字 | — | 用戶端緩衝（curl 沒加 `-N`，或 SDK 沒開 stream） | curl 加 `-N`；SDK 確認 `stream: true` 且未做整體緩衝 |
| **D2** | 中文／特殊字元亂碼 | — | 未宣告編碼或解析出錯 | 請求與回應均按 UTF-8；`python3 -m json.tool` 正常顯示即伺服器端 OK，問題在本機終端編碼 |
| **D3** | 回傳內容被截斷 | — | `max_tokens` 設太小，或模型達到輸出上限 | 調大 `max_tokens`；長文改用串流分段接收 |
| **E1** | 扣費與預期不符（多扣／少扣） | — | 計費口徑含思維鏈、快取命中、工具呼叫等 token，或不同模型倍率不同 | 以單次回應 `usage` 與「使用日誌」中的計費明細為準；有疑問聯絡平台 |
| **E2** | function calling 不觸發／JSON 模式不生效 | — | 該模型未開放對應能力 | 用 Step 5 單獨驗證；不支援的能力不要強依賴，需在業務層降級 |
| **F1** | `400` + 中文「公告式」提示 | 400 | 上游供應商在報錯裡發通知，不是你請求寫錯 | 確認請求格式無誤後，聯絡平台並附上報錯原文 |

<Callout type="idea">
  兩條最值得記住的經驗：凡是報「沒有可用管道／模型找不到」，先 `GET /v1/models` 與「定價」頁核對真實模型名稱和管道，再聯絡平台——**多數「模型用不了」都是這兩個原因**，不是程式碼問題。凡是 `401/403`，先核對金鑰狀態、模型限制與 IP 白名單，再核對 Base URL——**驗證類問題幾乎都出在「複製不全／限制沒放行／網址錯」**。
</Callout>

## 遇到 400 報錯怎麼辦（Bad Request）

`400` 表示「請求本身有問題」：伺服器收到了你的請求，但請求內容或參數不合法，被直接拒絕。它和驗證（401）、權限／額度（403）、限流（429）不是一類。

先依錯誤文案判斷來源：

| 你看到的提示 | 通常來源 | 該怎麼做 |
| --- | --- | --- |
| 中文、像平台提示 | 平台在轉發前校驗請求 | 依提示修改請求參數 |
| 英文、像 OpenAI／Claude／Gemini 的報錯 | 上游模型商回傳（參數不符合該模型要求） | 依提示修改參數（如補充 messages、調整越界值） |
| 中文、像「通知／公告」 | 上游模型供應臨時變動 | 不是你寫錯，直接聯絡平台並提供報錯原文 |

平台端常見的 400 提示：

| 你看到的提示 | 含義 | 解決 |
| --- | --- | --- |
| `請求不合法：<具體錯誤>` | 平台校驗請求體失敗 | 看冒號後的具體說明，照著改 |
| `請求不合法，無法識別您要使用哪個模型。` | 沒解析出要用的模型 | 確認請求裡 `"model": "模型名"` 已填寫且拼寫正確 |
| `請指定模型名稱。` | 沒傳 `model` 欄位 | 補上 `model` 參數 |
| `請求不合法：invalid JSON request body` | 請求體 JSON 格式有誤 | 檢查引號、逗號、跳脫，尤其是中文與換行 |

<Callout type="info">
  如果你看到類似「模型設定」「價格未設定」這類提示，屬於平台端問題，直接聯絡平台處理即可，無需修改請求。
</Callout>

上游模型常見的 400 提示：

- `messages is required`／`messages must be a non-empty array` —— 漏了 `messages` 或為空
- `temperature must be between 0 and 2`／`max_tokens too large` —— 參數越界
- `Unknown parameter: 'xxx'` —— 傳了該模型不支援的欄位
- `1 validation error for ...` —— 欄位類型或必填項不符

30 秒定位（curl 加 `-i` 看完整回應）：

```bash
curl -i https://你的網域/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<模型名>","messages":[{"role":"user","content":"hi"}]}'
```

重點看回應裡的 `message`——它通常已寫明直接原因。

## 用日誌核對每次呼叫

「管理 → 使用日誌」會記錄每次請求的時間、模型、金鑰、管道（管理員可見）、耗時、額度消耗與錯誤訊息；「任務日誌」記錄非同步任務的狀態、進度與產物。聯調階段建議：

- 每次測試後核對日誌中的模型名稱、分組／管道與額度是否與預期一致；
- 失敗請求保留原始錯誤訊息，便於區分平台端與上游端問題；
- 不要把金鑰、完整請求標頭或使用者隱私寫入你自己的日誌。

### 錯誤回應統一格式

平台 API 錯誤為 OpenAI 風格結構，便於統一處理：

```json
{
  "error": {
    "message": "人類可讀的錯誤原因",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "可選的錯誤碼",
    "param": "可選的問題參數名稱"
  }
}
```

搭配 HTTP 狀態碼（401 驗證／403 權限或額度／404 模型／429 限流／5xx 上游）即可覆蓋絕大多數用戶端處理邏輯。

### 安全提醒（務必遵守）

- **金鑰 = 密碼**：只在伺服器端／金鑰管理裡使用，絕不下發到瀏覽器、絕不明文進日誌、絕不提交 Git。
- **日誌脫敏**：平台稽核不會記錄你的金鑰明文；用戶端列印回應時，也要避免把 `Authorization` 標頭寫進日誌。
- **限流與重試**：務必實作退避重試，避免雪崩式重試把限流打成全面不可用。
