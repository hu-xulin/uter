# Test des modèles

Avant d'intégrer un modèle dans Uter, vérifiez étape par étape : connexion, fonctionnement, stabilité et facturation. On évite ainsi les mauvaises surprises en production.

Commencez par l'**Aire de jeux** de la console, puis recontrôlez via l'API : ce double passage distingue vite « le modèle n'est pas disponible » de « ma requête est incorrecte ».

## Prérequis

| Élément | Description | Où l'obtenir |
| --- | --- | --- |
| **URL de base (Base URL)** | Par ex. `https://votre-domaine/v1`, selon le domaine réellement servi (le vôtre peut différer) | Adresse du site + `/v1` |
| **Clé d'API** | Par ex. `sk-xxxxxxxx`. C'est un secret équivalent à un mot de passe : ne jamais l'exposer, ne jamais l'envoyer au navigateur, ne jamais le committer | Console → Clés API → Créer une clé API |
| **Quota** | Unité interne : **500 000 quota = 1 USD** ; chaque modèle applique son ratio, le portefeuille et les journaux affichent la devise du site. Les appels sont refusés quand le quota est épuisé | Console → Portefeuille ; Console → Journaux d'utilisation |
| **Nom du modèle** | Le nom enregistré dans Uter (pas forcément le nom d'origine du fournisseur) | Console → Tarification ; ou l'`id` de `GET /v1/models` |

### Canal et groupe : deux dimensions distinctes

- **Groupe** : détermine le ratio de facturation et l'ensemble des modèles routables. Une clé est facturée et routée selon son groupe.
- **Canal** : le fournisseur amont qui sert réellement le modèle (canal Uter, canal agrégé, canal partagé…). Un modèle peut être servi par plusieurs canaux activés, ou par un seul.

Un même modèle peut donc varier en disponibilité et en prix selon le groupe et le temps. « Aucun canal disponible » signifie qu'aucun canal activé ne sert ce modèle pour votre groupe — pas que votre requête est mal formée.

<Callout type="warn">
  Une clé est un mot de passe : côté serveur ou gestionnaire de secrets uniquement. Jamais dans un navigateur, jamais en clair dans les journaux, jamais dans Git.
</Callout>

### Vérifier l'état et les restrictions de la clé

Quatre états : **activée, désactivée, expirée, épuisée**. À la création ou à l'édition :

- **Expiration** : « n'expire jamais » par défaut ; après expiration, les appels renvoient 401.
- **Plafond de quota** : quota dédié ou « illimité ». Une fois épuisé, la clé passe à « épuisée ».
- **Limites de modèles** : n'autoriser que certains modèles. Sans aucun modèle coché, la clé ne peut rien appeler.
- **Liste d'IP autorisées** : prend en charge le CIDR (ex. `203.0.113.0/24`) ; les autres sources sont rejetées.
- **Autoriser la consultation du quota utilisateur** : accès à `/v1/dashboard/billing/*`.

## Vérification la plus rapide : l'Aire de jeux

Console → Aire de jeux utilise le même chemin d'appel que l'API.

1. Choisissez un **canal** à gauche ; la liste de droite affiche ses modèles. Sélectionnez celui à tester.
2. Envoyez un message et observez la réponse (en streaming par défaut).
3. Ouvrez les paramètres et activez ce dont vous avez besoin : `temperature`, `top_p`, `max_tokens`, `frequency_penalty`, `presence_penalty`, `seed`. Seuls les paramètres activés sont envoyés.
4. Pour le multimodal ou la recherche web, utilisez les outils de pièce jointe / recherche (selon le support du modèle).
5. Arrêtez, régénérez, éditez l'historique ou effacez la conversation à tout moment.

L'Aire de jeux débite le quota selon les mêmes règles : idéale pour itérer, mais confirmez ensuite via l'API.

## Vérifier le modèle et son prix

Console → Tarification permet de :

- rechercher un modèle ;
- filtrer par **canal, fournisseur, type, tag** pour voir quels canaux le servent ;
- consulter le mode de facturation (au token / à la requête / à la tâche), le contexte et les endpoints pris en charge ;
- comparer les prix publics avant de choisir.

## Dimensions de test

Onze dimensions. Les quatre premières répondent à « utilisable ? », les cinq suivantes à « stable et bien facturé ? », les deux dernières couvrent les tâches asynchrones et l'observabilité.

1. **Connectivité et authentification** — bonne URL, clé valide, liste d'IP non bloquante.
2. **Liste et disponibilité** — le modèle existe et un canal le sert pour votre groupe.
3. **Dialogue de base** — une requête minimale répond correctement.
4. **Paramètres et capacités avancées** — streaming, `temperature`, `max_tokens`, tools/function calling, vision, mode JSON, prompt système.
5. **Streaming (SSE)** — sortie token par token correctement analysée.
6. **Performance** — TTFT, latence totale, comportement en contexte long.
7. **Stabilité et limites** — concurrence, retries, 429 et saturation amont.
8. **Quota et facturation** — débits corrects, cohérents avec les journaux.
9. **Erreurs et limites d'entrée** — échecs lisibles et exploitables par le code.
10. **Modèles en tâche asynchrone** — soumission, polling et téléchargement (image / vidéo / musique).
11. **Observabilité** — les journaux identifient modèle, canal, latence, quota et cause d'échec.

## Pas à pas (API)

- `BASE=https://votre-domaine/v1` (à remplacer)
- `TOKEN=sk-your-token-here` (clé complète de la console)

Exemples en `curl`. Derrière un proxy local, ajoutez `--noproxy '*'`.

### Étape 1 · Connectivité + authentification

```bash
BASE=https://votre-domaine/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

Attendu : JSON avec `object: "list"` et plusieurs `id` → connexion et authentification OK. Un 401 « Jeton invalide » indique une clé erronée ou désactivée ; « aucun accès aux modèles » indique que les limites de modèles excluent la cible.

<Callout type="info">
  L'authentification native est aussi prise en charge : Claude via `POST /v1/messages` avec `x-api-key` et `anthropic-version: 2023-06-01` ; Gemini via `GET /v1beta/models` avec `x-goog-api-key` (ou `?key=`). Les endpoints compatibles OpenAI utilisent `Authorization: Bearer`.
</Callout>

### Étape 2 · Lister les modèles

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40

curl --noproxy '*' -s "$BASE/models/votre-modele" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

<Callout type="warn">
  Modèle absent ? Vérifiez d'abord Console → Tarification par canal, puis contactez la plateforme. Ne devinez pas les noms : 404 ou « aucun canal disponible » en général.
</Callout>

### Étape 3 · Dialogue minimal (non streaming)

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "votre-modele",
    "messages": [{"role": "user", "content": "Présente-toi en une phrase."}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

OK si `choices[0].message.content` contient du texte et `usage` fournit `prompt_tokens` / `completion_tokens`.

### Étape 4 · Streaming (SSE)

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "votre-modele",
    "messages": [{"role": "user", "content": "Compte jusqu’à 10."}],
    "stream": true
  }'
```

OK si les blocs `data: {...}` arrivent progressivement et se terminent par `data: [DONE]`. `-N` est indispensable avec curl ; côté SDK, activez `stream: true` sans mise en tampon globale.

### Étape 5 · Function calling

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "votre-modele",
    "messages": [{"role": "user", "content": "Quel temps fait-il à Pékin ?"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Consulter la météo d’une ville",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

OK si `choices[0].message.tool_calls` apparaît (le modèle demande `get_weather`). Testez séparément chaque capacité avancée dont dépend votre produit.

### Étape 6 · Vision (modèles acceptant les images)

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "votre-modele-vision",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "Que montre cette image ?"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

L'image doit être accessible publiquement ; la plateforme ne lit pas les fichiers locaux.

### Étape 7 · Latence de référence

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "essai $i ttfb=%{time_starttransfer}s total=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"votre-modele","messages":[{"role":"user","content":"bonjour"}],"max_tokens":128}'
done
```

Comparez TTFT et durée totale au SLA. Testez aussi un prompt long (8k / 32k tokens) pour vérifier la croissance de la latence.

### Étape 8 · Quota et facturation

`/v1/dashboard/billing/usage` renvoie l'**usage cumulé** (`total_usage`, dans la devise affichée), pas le solde restant (voir Console → Portefeuille). Comparez avant/après un appel :

```bash
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

Recoupez ensuite avec l'`usage` d'une réponse et le détail de facturation dans Console → Journaux d'utilisation / Journaux de tâches.

### Étape 9 · Erreurs lisibles

```bash
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"votre-modele","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

Attendu : enveloppe `{"error":{"message":...,"type":...,"code":...}}` et statut 4xx, pas de corps vide ni de trace 500.

## Modèles asynchrones (image / vidéo / musique)

Ces modèles suivent **soumission → polling → téléchargement** :

1. **Soumettre** via l'endpoint indiqué par la page des plugins de tâches : `POST /v1/tasks/<clé-plugin>`, vidéo `POST /v1/video/generations`, ou `POST /v1/images/generations` (compatible OpenAI) servi par le canal/plugin correspondant.
2. **Interroger** avec le `task_id` : `GET /v1/tasks/<task_id>` ou `GET /v1/video/generations/<task_id>`. Tant que ce n'est pas fini : en file / en cours.
3. **Artefacts** : `GET /v1/tasks/<task_id>/artifacts` liste les sorties ; `GET /v1/tasks/<task_id>/artifacts/<artifact_key>/content` en télécharge une.
4. **Vérifier** dans Console → Journaux d'utilisation → Journaux de tâches : état, progression, durée, quota ; en cas d'échec, la raison (et un remboursement le cas échéant).
5. **Cas limites** : provoquez un timeout ou un paramètre invalide et vérifiez que la tâche échoue proprement au lieu de rester bloquée.

## Dépannage

| # | Message observé | HTTP | Cause probable | Solution |
| --- | --- | --- | --- | --- |
| **A1** | Jeton invalide | 401 | Clé tronquée, mal saisie ou désactivée | Recopiez la clé complète dans Console → Clés API ; état « activée » ; sans espaces |
| **A2** | Ce jeton a expiré | 401 | Date d'expiration dépassée | Créez une clé, ou mettez « n'expire jamais » |
| **A3** | Quota du jeton épuisé | 401 | Quota propre à la clé épuisé | Rechargez la clé dans Console → Clés API, ou créez-en une autre |
| **A4** | Votre IP n'est pas dans la liste autorisée | 403 | Liste d'IP (CIDR) exclut votre sortie | Ajoutez l'IP/plage de sortie, ou désactivez la restriction en test |
| **A5** | Ce jeton n'a accès à aucun modèle | 403 | Limites de modèles vides | Éditez la clé et cochez les modèles |
| **A6** | Ce jeton n'a pas accès au modèle « xxx » | 403 | Modèle absent des limites | Mettez à jour les limites ou changez de clé |
| **A7** | Connexion impossible / timeout | — | URL erronée, certificat, réseau privé | Vérifiez `https://votre-domaine/v1` ; `--noproxy '*'` si proxy local |
| **B1** | Quota insuffisant | 403 | Quota compte/clé épuisé | Rechargez dans Console → Portefeuille ou sur la clé ; vérifiez via l'étape 8 |
| **B2** | Aucun canal disponible pour le modèle « xxx » sous le groupe « default » | 503 (400 selon les filtres) | Aucun canal activé pour ce groupe | Vérifiez Console → Tarification par canal ; contactez la plateforme |
| **B3** | 404 / modèle introuvable | 404 | Nom erroné ou accès absent | Listez via l'étape 2 et copiez l'`id` |
| **C1** | Limite de requêtes atteinte | 429 | Limite clé ou plateforme | Réduisez la concurrence, backoff exponentiel, vérifiez RPM/TPM |
| **C2** | Groupe / amont saturé | 429 / 503 | Capacité temporairement insuffisante | Réessayez plus tard avec backoff ; contactez la plateforme |
| **C3** | 5xx / timeout amont, succès au retry | 5xx | Instabilité amont | Retry avec backoff ; la plateforme retente aussi, mais le client doit assurer |
| **D1** | Streaming d'un coup | — | Tampon client (`curl` sans `-N`, SDK) | `-N` ; `stream: true` sans tampon global |
| **D2** | Caractères mal affichés | — | Encodage/parsing | UTF-8 des deux côtés ; si `json.tool` s'affiche bien, le serveur est OK |
| **D3** | Sortie tronquée | — | `max_tokens` trop petit ou plafond modèle | Augmentez `max_tokens` ; streamez les longues réponses |
| **E1** | Débit inattendu | — | Tokens cachés (raisonnement, cache, outils) ou ratios différents | Recoupez avec `usage` et le détail des journaux |
| **E2** | Function calling / mode JSON inactif | — | Capacité non exposée par le modèle | Vérifiez à l'étape 5 ; prévoyez une dégradation |
| **F1** | 400 avec message « annonce » | 400 | Notification du fournisseur amont | Validez votre requête puis contactez la plateforme avec le message |

<Callout type="idea">
  Deux réflexes : « aucun canal / modèle introuvable » → listez `GET /v1/models` et vérifiez la page Tarification par canal avant de contacter la plateforme. « 401/403 » → contrôlez l'état de la clé, les limites de modèles et la liste d'IP, puis l'URL de base.
</Callout>

## Que faire d'un 400 (Bad Request)

`400` signifie que la requête elle-même est invalide (contenu ou paramètres), distinct de 401 (authentification), 403 (permission/quota) et 429 (limite de débit).

| Style du message | Source | Action |
| --- | --- | --- |
| Anglais/chinois, style plateforme | Uter a rejeté avant transmission | Corrigez la requête |
| Anglais, style fournisseur (OpenAI/Claude/Gemini) | L'amont rejette les paramètres | Corrigez les paramètres |
| Message « annonce » | Changement d'approvisionnement amont | Contactez la plateforme avec le message |

Messages plateforme fréquents :

| Message | Sens | Correction |
| --- | --- | --- |
| `Requête invalide : <détail>` | Validation du corps échouée | Lisez le détail après les deux-points |
| `Requête invalide, impossible d'identifier le modèle demandé.` | Aucun modèle exploitable | Vérifiez `"model": "..."` |
| `Please specify a model name.` | Champ `model` absent | Ajoutez `model` |
| `Requête invalide : invalid JSON request body` | JSON mal formé | Vérifiez guillemets, virgules, échappements |

Les messages sur la configuration du modèle ou l'absence de prix sont côté plateforme : contactez-la sans modifier votre requête.

Erreurs amont courantes : `messages is required`, `messages must be a non-empty array`, `temperature must be between 0 and 2`, `max_tokens too large`, `Unknown parameter: 'xxx'`, `1 validation error for ...`.

Diagnostic en 30 s (`curl -i`) :

```bash
curl -i https://votre-domaine/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<modèle>","messages":[{"role":"user","content":"hi"}]}'
```

Lisez d'abord `message`.

## Recouper chaque appel dans les journaux

Console → Journaux d'utilisation enregistre heure, modèle, clé, canal (admin), latence, quota et erreur ; les Journaux de tâches couvrent l'asynchrone. Pendant l'intégration :

- comparez modèle, groupe/canal et quota avec l'attendu ;
- conservez l'erreur brute pour distinguer plateforme et amont ;
- ne journalisez jamais clés, en-têtes complets ou données personnelles.

## Checklist avant mise en production

- [ ] **URL de base** en configuration (env / config service), pas en dur dans le front.
- [ ] **Clé** complète, état activé, non expirée, quota suffisant.
- [ ] **Limites de modèles** de la clé couvrent les modèles utilisés.
- [ ] **Liste d'IP** : IP/CIDR de sortie de production ajoutés si activée.
- [ ] `GET /v1/models` liste le modèle et l'`id` correspond au code.
- [ ] Dialogue non streaming OK (`content`, `usage`).
- [ ] Streaming OK (`data:` et `[DONE]`).
- [ ] Capacités avancées requises (tools / JSON / vision / contexte long) vérifiées.
- [ ] **Modèles asynchrones** vérifiés de bout en bout (soumission, polling, téléchargement, échec).
- [ ] Latence (TTFT / total) conforme au SLA.
- [ ] Backoff sur les limites et retry sur les 5xx amont.
- [ ] Erreurs traitées via `error.message` / `error.code` / statut HTTP, sans credentials dans les logs.
- [ ] Débits recoupés avec `usage` et les journaux.
- [ ] Aucun secret journalisé ou commité en production.
- [ ] Disponibilité et règles de facturation confirmées avec la plateforme.

### Enveloppe d'erreur unifiée

```json
{
  "error": {
    "message": "Raison lisible",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "code optionnel",
    "param": "paramètre fautif optionnel"
  }
}
```

Avec le statut HTTP (401 / 403 / 404 / 429 / 5xx), cela couvre la plupart des traitements client.

### Rappels de sécurité

- **Clé = mot de passe** : serveur ou gestionnaire de secrets seulement.
- **Journaux expurgés** : ne journalisez jamais l'en-tête `Authorization`.
- **Limites et retries** : toujours avec backoff, sinon une tempête de retries transforme la limite en panne totale.
