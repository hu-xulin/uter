# UAP 1.0 规范基线（生成输入，不是交付规范）

> 本文件是 32 份正式规范的**机器可校验基线输入**，记录用户指令中每份规范的最低正式要求。
> 正式交付规范是 `.uap/{domain}/UAP-xx-xxx-*.md`。生成脚本/代理必须逐条覆盖本文件的内容，
> 并补上与 Uter 真实代码、命令、目录、业务模块对应的「落地细则」。
> 每份正式规范的「强制性要求」与「验收条件」不得删减本文件中的任何条目。

---

## UAP-00-001 | CORE-ARCHITECTURE | UAP 核心架构规范
- 目标：定义 UAP 的分层、模块边界、接口与可追溯性，使其成为 Uter 内部唯一自主工程治理与执行平台。
- 强制性要求：
  1. UAP 是 Uter 内部唯一的 AI 自主工程治理和执行平台。
  2. UAP 由规范层、配置层、运行时层、执行引擎层、验证层、证据层组成。
  3. 规范层定义工程规则；配置层将规则映射到机器执行对象；运行时层负责调度；执行引擎负责实际操作；验证层负责判定；证据层负责记录。
  4. 任何规范不得只有文字要求而没有执行映射。
  5. 任何强制性规范必须对应至少一个执行器和一个验证器。
  6. 任何执行器必须声明输入、输出、权限、失败状态和可恢复策略。
  7. 任何验证器必须返回机器可读结果。
  8. 系统模块之间通过稳定接口通信，禁止通过隐式全局状态传递任务。
  9. 所有任务必须有唯一 ID、执行状态、执行时间、责任 Agent 和证据引用。
  10. 配置、规范、代码和验证结果必须可追溯。
  11. UAP 必须支持独立运行，不得要求外部治理平台提供必要能力。
  12. UAP 内部组件应遵循单一职责、可替换、可测试和可恢复原则。
- 验收条件：核心组件真实存在；模块依赖关系可解析；规范、执行器、验证器能够映射；Runtime 能启动并返回健康状态；不存在无法解释的循环依赖；所有关键接口均有自动化测试。

## UAP-00-002 | AUTONOMOUS-EXECUTION | 自主执行规范
- 目标：把用户任务变成可执行、可调度、可恢复的结构化任务图，禁止以计划或报告代替实际执行。
- 强制性要求：
  1. 用户任务必须转换为结构化任务。
  2. 任务必须拆分为可执行子任务。
  3. 每个子任务必须包含目标、输入、输出、依赖、权限、验收标准。
  4. 系统必须自动计算可执行顺序。
  5. 无依赖任务允许并行执行；有依赖任务必须等待前置任务完成。
  6. 并行执行必须受资源限制和文件冲突检测约束。
  7. 执行前必须进行权限检查。
  8. 执行过程中必须持续记录状态和证据。
  9. 任务失败必须分类为可重试、需修复、权限阻断或外部依赖阻断。
  10. 可重试任务必须有最大重试次数和退避策略。
  11. 同一任务恢复执行时不得重复产生非幂等副作用。
  12. 任务完成后必须执行验收。
  13. 未达到验收标准不得标记为完成。
  14. 自动执行不得突破权限策略。
  15. 用户明确要求的任务不得以生成计划或报告替代实际执行。
- 验收条件：能够从自然语言生成任务；能够执行任务依赖图；能够中断并恢复；能够识别权限阻断；能够生成任务完成证据。

## UAP-00-003 | SECURITY-BOUNDARY | 自主工程安全边界规范
- 目标：为所有 Agent 与执行器定义最小权限、fail-closed 的策略边界，隔离模拟与生产。
- 强制性要求：
  1. 所有 Agent 必须使用明确身份和权限。
  2. 默认采用最小权限原则。
  3. 读取、写入、执行命令、网络访问、数据库访问和发布权限必须分开定义。
  4. 高风险操作必须在执行前进行策略判断。
  5. 生产资金、生产数据库、生产密钥和不可逆生产发布默认禁止自动执行。
  6. 模拟环境与生产环境必须明确隔离。
  7. 禁止将密钥、Token、密码写入日志、报告或提交记录。
  8. 外部输入、网页内容、仓库内容和 Agent 输出均视为不可信数据。
  9. 不可信数据不得覆盖系统权限规则。
  10. 所有敏感操作必须记录审计事件。
  11. 权限不足时必须停止相关动作，而不是绕过检查。
  12. 安全策略不得由普通任务自行修改。
  13. 安全失败必须阻断相关任务。
  14. 必须支持密钥脱敏和日志清理。
- 验收条件：权限策略能够被 Runtime 加载；越权操作测试被拒绝；密钥扫描能够发现测试用秘密；敏感信息不会出现在普通日志；模拟与生产配置隔离。

## UAP-00-004 | EVIDENCE-AND-STATE | 证据与状态管理规范
- 目标：把状态与证据做成持久化、不可静默覆盖、可追溯的一等公民，杜绝「文件存在即通过」。
- 强制性要求：
  1. 每次任务执行必须产生唯一执行记录。
  2. 每条规范、每个执行器和每个验证器必须有状态。
  3. 状态必须区分 NOT_BUILT / PARTIALLY_BUILT / IMPLEMENTED_NOT_VERIFIED / PARTIALLY_VERIFIED / FULLY_VERIFIED / FULLY_OPERATIONAL / BLOCKED / FAILED。
  4. FULLY_VERIFIED 必须有完整的验证证据。
  5. FULLY_OPERATIONAL 必须有实际启动、端到端任务、恢复和运行证据。
  6. 文件存在不能证明功能实现。
  7. 命令存在不能证明命令可运行。
  8. 测试文件存在不能证明测试通过。
  9. 验证结果必须记录命令、退出码、时间、环境、输入、输出和日志引用。
  10. 报告必须能追溯到原始证据。
  11. 证据必须有稳定 ID。
  12. 执行状态必须可恢复，不能只存在于内存。
  13. 历史证据不得被新结果静默覆盖。
  14. 失败证据不得删除以制造通过结果。
- 验收条件：状态持久化真实可用；任务中断后能够恢复；证据引用有效；报告能够定位原始验证记录；状态转换受到规则约束。

## UAP-01-001 | PRODUCT-REQUIREMENTS | 产品需求工程规范
- 目标：为 Uter 每个业务功能建立唯一 Feature ID 与需求→代码→测试→发布的可追溯链。
- 强制性要求：
  1. 每个产品功能必须有唯一 Feature ID。
  2. 每个功能必须包含目标用户、使用场景、业务价值和验收标准。
  3. 功能需求必须区分用户需求、系统需求和技术约束。
  4. 必须识别功能前置条件、异常流程和边界条件。
  5. 必须维护 Feature Registry。
  6. 每个 Feature 必须关联 PRD、原型、代码模块、测试和发布记录。
  7. 不允许出现没有需求来源的重大业务功能。
  8. 需求变更必须触发影响分析。
  9. 影响分析必须覆盖 API、数据库、前端、后端、测试和文档。
  10. 需求状态必须包括 Draft、Approved、In Progress、Verified、Released、Deprecated。
  11. 不得将未经确认的业务假设标记为已批准需求。
  12. 需求验收必须有测试或其他可验证证据。
- 验收条件：已有功能可以追溯到需求；关键功能不存在无来源、无验收标准的孤立实现；需求变更能够产生影响分析记录。

## UAP-01-002 | PRD-PROTOTYPE-SYNC | PRD 与原型双向同步规范
- 目标：以稳定 Feature ID 建立 PRD 与原型双向映射、影响清单和差异记录。
- 强制性要求：
  1. 每个功能必须有唯一 Feature ID。
  2. PRD 与原型必须使用相同 Feature ID 和页面/组件标识。
  3. 产品展示界面采用左侧原型、右侧 PRD 的对应关系。
  4. PRD 修改后必须生成原型影响清单。
  5. 原型修改后必须生成 PRD 影响清单。
  6. 双向同步必须保留变更历史。
  7. 必须支持页面、组件、交互、状态、字段、校验和异常流程的对应。
  8. 同步不能仅依赖文件名或页面标题，必须使用稳定 ID。
  9. 不一致时必须产生差异记录。
  10. 未解决的差异不得标记为同步完成。
  11. 自动同步不得擅自改变已批准的业务规则。
  12. 必须支持人工确认有歧义的需求，但不应要求人工重复确认确定性机械变更。
- 验收条件：每个页面能够定位对应 PRD；PRD 和原型能够双向发现变化；差异有记录；自动同步有测试；变更历史可追溯。

## UAP-01-003 | BUSINESS-RULES | 业务规则工程规范
- 目标：把计费、额度、订单、退款等 Uter 关键业务规则集中登记并绑定到代码与测试。
- 强制性要求：
  1. 业务规则必须集中登记。
  2. 每条规则必须有唯一 Rule ID。
  3. 规则必须包含条件、行为、结果、异常、优先级和适用范围。
  4. 业务规则必须与代码实现、API、数据库和测试关联。
  5. 相互冲突的规则必须被检测。
  6. 规则修改必须执行影响分析。
  7. 关键资金规则必须采用精确金额类型和明确舍入策略。
  8. 权限、额度、计费、退款和订单状态必须具有明确状态转换。
  9. 状态转换必须禁止非法回退和非法跳转。
  10. 业务规则不得只存在于前端。
  11. 后端必须执行关键业务约束。
  12. 关键规则必须有正向、反向、边界和并发测试。
- 验收条件：核心业务规则有唯一 ID；代码与规则可追溯；关键规则具有自动化验证；冲突规则可以被发现。

## UAP-02-001 | SYSTEM-ARCHITECTURE | 系统架构规范
- 目标：识别 Uter 系统边界、模块依赖与关键链路，并以 ADR 记录架构变更。
- 强制性要求：
  1. 必须识别系统边界、模块边界和外部依赖。
  2. 必须维护系统架构图和模块依赖图。
  3. 模块必须遵循明确的职责划分。
  4. 禁止未经论证的跨模块直接耦合。
  5. 模块间通信必须使用明确接口。
  6. 架构变更必须记录 ADR。
  7. 架构分析必须包含可扩展性、可靠性、安全性和维护成本。
  8. 关键业务链路必须有端到端架构说明。
  9. 必须识别单点故障和关键依赖。
  10. 不得为了形式化而无理由引入微服务或复杂基础设施。
  11. 架构图必须与实际代码保持一致。
  12. 架构变更必须执行依赖影响验证。
- 验收条件：架构图与代码结构一致；模块依赖可分析；关键业务链路可追溯；架构变更有 ADR。

## UAP-02-002 | API-AND-DATABASE | API 与数据库规范
- 目标：约束 Uter 的 API 契约、数据库模型与三方言迁移安全，禁止触碰生产库。
- 强制性要求：
  1. API 必须定义路径、方法、参数、响应、错误码和权限。
  2. API 必须进行输入验证和输出约束。
  3. API 必须考虑兼容性、幂等性和限流。
  4. 数据库表必须定义字段类型、约束、索引和关联关系。
  5. 金额字段必须采用适合精确计算的类型。
  6. 数据库迁移必须可追踪、可验证。
  7. 迁移不得静默删除生产数据。
  8. 破坏性迁移必须有备份和回滚方案。
  9. 数据库访问必须遵循事务边界。
  10. 关键业务操作必须检查并发竞争。
  11. API 变更必须执行兼容性检查。
  12. 数据库模型变更必须同步更新相关测试和文档。
  13. 数据库迁移必须在隔离测试数据库中验证。
  14. 禁止在本次 UAP 建设中擅自连接生产数据库执行写入。
- 验收条件：API 定义与实现一致；数据模型与迁移一致；迁移测试通过；幂等和并发测试覆盖关键接口。

## UAP-02-003 | TECHNICAL-DECISIONS | 技术决策规范
- 目标：以 ADR 记录 Uter 重大技术选择，避免无理由的技术栈替换。
- 强制性要求：
  1. 重要技术决策必须记录 ADR。
  2. ADR 包含背景、问题、备选方案、决策、理由、影响和状态。
  3. 决策必须说明成本和风险。
  4. 已废弃决策必须记录替代方案。
  5. 不得仅因为某项技术流行就引入。
  6. 不得在没有必要时替换现有成熟技术栈。
  7. 技术决策必须考虑 Uter 现有架构和部署环境。
  8. 重大依赖变更必须进行兼容性和安全性评估。
  9. 决策实施后必须验证其实际效果。
  10. 发现原决策不再成立时，必须提出 ADR 修订。
- 验收条件：重大技术选择可追溯；不存在无理由的大规模技术栈替换；决策与实际代码一致。

## UAP-03-001 | AGENT-ARCHITECTURE | Agent 架构规范
- 目标：所有 Agent 以唯一 ID 登记，声明输入输出、工具、权限、超时与可观测性。
- 强制性要求：
  1. 每个 Agent 必须有唯一 ID、名称、职责和版本。
  2. 每个 Agent 必须声明输入、输出、工具、权限和依赖。
  3. Agent 必须有明确的任务范围。
  4. Agent 不得自行扩大权限。
  5. Agent 必须支持结构化输入和输出。
  6. Agent 必须具有超时和失败处理机制。
  7. Agent 必须支持可观测性。
  8. Agent 不得将未经验证的推断作为事实输出。
  9. Agent 之间通过明确消息协议协作。
  10. Agent 版本变更必须执行兼容性验证。
- 验收条件：所有 Agent 已登记；所有 Agent 权限可解析；Agent 能通过 Runtime 被调用；Agent 接口有测试。

## UAP-03-002 | AGENT-EXECUTION | Agent 执行规范
- 目标：Agent 只能在权限边界内执行分配任务，输出结构化并接受独立验证。
- 强制性要求：
  1. Agent 只能执行分配给自己的任务。
  2. 任务必须包含目标、上下文、约束和验收标准。
  3. Agent 执行前必须进行权限校验。
  4. Agent 执行结果必须结构化。
  5. 执行结果必须包含状态、摘要、修改文件、测试和证据。
  6. Agent 不得伪造工具运行结果。
  7. Agent 不得将模型推理结果冒充真实测试。
  8. 工具调用必须记录参数摘要和结果。
  9. 失败必须返回标准错误分类。
  10. Agent 必须遵守任务超时、Token 和资源限制。
  11. 关键修改必须由独立验证器复验。
  12. Agent 输出必须经过结果校验后才能进入下一阶段。
- 验收条件：Agent 执行有权限边界；输出可解析；失败可识别；结果有独立验证。

## UAP-03-003 | AGENT-COLLABORATION | Agent 协作规范
- 目标：Orchestrator 统一分配，DAG 顺序、冲突检测、去重与结果一致性检查。
- 强制性要求：
  1. 任务由 Orchestrator 统一分配。
  2. 多 Agent 必须通过任务 ID 和消息 ID 关联。
  3. 必须明确任务负责人。
  4. 并行任务必须检查文件修改冲突。
  5. 共享资源必须有锁或等效并发控制。
  6. Agent 之间不得通过非结构化文本暗中传递关键状态。
  7. 冲突必须交由协调器处理。
  8. 依赖任务必须按 DAG 顺序执行。
  9. 重复任务必须识别并去重。
  10. 多 Agent 结果必须进行汇总和一致性检查。
  11. 关键业务决策必须记录来源。
  12. 协作失败必须支持重新分配或恢复。
- 验收条件：任务 DAG 可执行；冲突能够检测；重复任务能够识别；协作结果可追溯。

## UAP-03-004 | AGENT-RECOVERY | Agent 恢复规范
- 目标：任务状态持久化，中断可恢复，非幂等副作用不重放。
- 强制性要求：
  1. Agent 任务必须持久化状态。
  2. Runtime 中断后必须能够恢复任务。
  3. 恢复时必须检查任务是否已经产生副作用。
  4. 非幂等操作不得直接重复执行。
  5. 任务恢复必须校验上下文版本。
  6. 失败任务必须记录失败原因。
  7. 超时任务必须进入明确的恢复状态。
  8. 不可恢复任务必须标记 BLOCKED 或 FAILED。
  9. 必须支持任务取消。
  10. 必须支持任务暂停和续跑。
  11. 恢复后必须进行必要的状态一致性检查。
  12. 不得通过重置状态隐藏失败历史。
- 验收条件：能够模拟进程中断；能够恢复任务；重复副作用得到防护；恢复证据完整。

## UAP-04-001 | CODING-STANDARD | 编码规范
- 目标：遵循 Uter 现有 Go/TypeScript 约定，格式化、静态检查与关键逻辑测试纳入自动执行。
- 强制性要求：
  1. 遵循项目现有语言和框架约定。
  2. 优先复用现有模块和基础设施。
  3. 避免无必要重复实现。
  4. 类型、命名、异常和日志必须保持一致。
  5. 禁止提交无效代码、死代码和无用依赖。
  6. 不得通过忽略类型错误或关闭 Lint 规则规避问题。
  7. 关键逻辑必须有测试。
  8. 敏感数据不得写入普通日志。
  9. API、数据库和业务规则变更必须同步更新文档。
  10. 复杂逻辑必须有必要的注释和说明。
  11. 代码修改必须遵守现有架构边界。
  12. 格式化和静态检查必须纳入自动执行。
- 验收条件：格式化通过；Lint 通过；类型检查通过；关键逻辑测试通过；无新增无效代码。

## UAP-04-002 | CODE-REVIEW | 自动代码审查规范
- 目标：每次变更自动审查正确性、安全、性能、兼容性与业务逻辑，结构化发现可阻断门禁。
- 强制性要求：
  1. 每次代码变更必须自动审查。
  2. 审查范围包含正确性、安全性、性能、可维护性、兼容性和业务逻辑。
  3. 审查必须结合实际上下文，不得只做文本匹配。
  4. 必须识别空指针、异常吞噬、权限绕过、注入、竞态和资源泄漏。
  5. 必须识别金额计算、重复扣费、重复退款和状态不一致风险。
  6. 必须检查 API 兼容性和数据库迁移风险。
  7. 必须检查测试是否覆盖修改行为。
  8. 每个发现必须包含严重程度、文件位置、问题描述、根因和建议。
  9. 严重问题必须阻断质量门禁。
  10. 不得把风格偏好伪装为严重缺陷。
  11. 修复后必须重新审查。
  12. 审查结果必须保存证据。
- 验收条件：自动审查引擎可执行；审查结果结构化；关键风险规则有测试；阻断问题能够阻止任务通过。

## UAP-04-003 | DEPENDENCY-MANAGEMENT | 依赖管理规范
- 目标：依赖受锁文件管理，识别未使用/过时/漏洞依赖，禁止未经评估的全量升级。
- 强制性要求：
  1. 依赖必须有明确用途。
  2. 依赖版本必须受锁文件管理。
  3. 必须识别未使用、重复和过时依赖。
  4. 必须扫描已知安全漏洞。
  5. 依赖升级必须评估兼容性。
  6. 禁止未经评估自动升级全部依赖。
  7. 依赖许可证必须满足项目使用要求。
  8. 不得引入来源不明的二进制和脚本。
  9. 依赖变更必须执行构建和测试。
  10. 关键依赖必须记录替代方案。
  11. 禁止通过删除安全检查来消除扫描结果。
  12. 必须保存依赖审计报告。
- 验收条件：锁文件有效；依赖清单可生成；漏洞扫描可执行；依赖变更经过测试。

## UAP-05-001 | QUALITY-ENGINEERING | 质量工程总规范
- 目标：代码审查、自动化测试、自动修复、质量门禁四项能力协同且质量系统自身被测。
- 强制性要求：
  1. 质量工程由代码审查、自动化测试、自动修复和质量门禁组成。
  2. 四项能力必须协同工作。
  3. 质量检查必须覆盖代码、业务、架构、安全、数据和用户体验。
  4. 每次变更必须确定影响范围。
  5. 质量结果必须基于真实工具执行。
  6. 必须区分单元、集成、端到端和回归测试。
  7. 测试范围必须与修改风险匹配。
  8. 关键业务路径必须有端到端测试。
  9. 失败必须分类并关联缺陷。
  10. 不得通过降低门禁制造通过结果。
  11. 质量状态必须有证据。
  12. 质量系统自身也必须经过测试。
- 验收条件：四项能力均真实运行；能够执行完整质量工作流；质量结果可以追溯；关键业务路径有自动化验证。

## UAP-05-002 | AUTOMATED-TESTING | 自动化测试规范
- 目标：单元/集成/E2E/回归分层，覆盖正常异常边界权限与并发幂等，结果带命令与退出码。
- 强制性要求：
  1. 测试必须与实际功能对应。
  2. 单元测试验证独立逻辑。
  3. 集成测试验证模块和外部接口边界。
  4. 端到端测试验证完整用户流程。
  5. 回归测试验证既有功能不被破坏。
  6. 必须覆盖正常、异常、边界和权限场景。
  7. 必须覆盖关键并发和幂等场景。
  8. 测试必须可重复执行。
  9. 测试数据必须隔离。
  10. 测试不得依赖真实资金交易。
  11. 测试失败不得被静默忽略。
  12. 测试结果必须记录命令、退出码和证据。
  13. 覆盖率必须按实际结果报告，不得伪造。
  14. 不能只用覆盖率数字代替测试有效性。
- 验收条件：测试套件可执行；关键业务测试通过；测试失败能正确阻断；测试结果有证据。

## UAP-05-003 | AUTO-REPAIR | 自动修复规范
- 目标：从已确认缺陷出发，根因优先、最多三次实质不同修复、闭环复验且不破坏门禁。
- 强制性要求：
  1. 自动修复必须从已确认缺陷开始。
  2. 必须分析根因和影响范围。
  3. 必须生成修复计划。
  4. 必须优先修复根因，不得只掩盖症状。
  5. 修复必须符合代码规范和安全边界。
  6. 每个根因最多尝试 3 种实质不同的修复方案。
  7. 修复失败必须保留证据。
  8. 修复后必须执行相关测试。
  9. 关键修改必须重新审查。
  10. 失败后不得无限循环。
  11. 自动修复不得删除失败测试或降低质量门禁。
  12. 修复必须生成前后差异和验证报告。
  13. 修复涉及用户未提交内容时必须保护原始内容。
  14. 无法安全自动修复时必须标记 BLOCKED。
- 验收条件：能够自动识别、修复和复验缺陷；能够停止无效重试；修复前后差异可追溯；不会通过破坏测试制造成功。

## UAP-05-004 | QUALITY-GATES | 质量门禁规范
- 目标：全部门禁机器可执行、版本控制、真实阻断，豁免需范围理由期限且不得由被审任务自建。
- 强制性要求：
  1. 所有质量门禁必须机器可执行。
  2. 门禁必须定义输入、执行器、阈值、失败条件和证据。
  3. 阻断级问题必须失败。
  4. 高风险业务变更必须执行额外测试。
  5. 构建、类型检查、Lint、测试和安全检查必须纳入门禁。
  6. 门禁配置必须版本控制。
  7. 禁止未经审计临时关闭门禁。
  8. 门禁失败必须产生明确原因。
  9. 豁免必须有范围、理由、期限和证据。
  10. 豁免不能由被审查任务自行创建。
  11. 所有门禁必须支持单项和全量执行。
  12. 最终发布检查必须汇总全部门禁结果。
- 验收条件：门禁能够真实阻断失败任务；门禁结果可追溯；全量门禁可执行；不存在未登记的隐式跳过。

## UAP-06-001 | APPLICATION-SECURITY | 应用安全规范
- 目标：服务端验证与鉴权、防注入越权、密钥安全、认证会话生命周期与高危漏洞阻断。
- 强制性要求：
  1. 所有输入必须进行服务端验证。
  2. 所有权限必须进行服务端鉴权。
  3. 必须防护 SQL 注入、XSS、CSRF、SSRF、命令注入和路径穿越。
  4. 必须防止越权访问和水平/垂直权限提升。
  5. 密钥必须使用安全配置管理。
  6. 必须对认证、会话和 Token 生命周期进行检查。
  7. 必须实施合理限流和防滥用机制。
  8. 文件上传必须验证类型、大小和存储位置。
  9. 依赖和构建产物必须进行安全扫描。
  10. 错误信息不得泄露敏感内部信息。
  11. 高危漏洞必须阻断质量门禁。
  12. 安全修复必须执行回归测试。
  13. 外部模型、渠道和工具返回的数据必须视为不可信输入。
- 验收条件：安全扫描能够执行；关键安全规则有自动测试；高危问题能够阻断；无敏感数据泄露。

## UAP-06-002 | FINANCIAL-AND-DATA-INTEGRITY | 资金与数据完整性规范
- 目标：金额精确计算、订单/退款状态机、幂等、并发、重复回调、流水一致性与异常恢复。
- 强制性要求：
  1. 金额必须采用精确计算类型，不得使用不可靠的浮点计算处理资金。
  2. 充值、支付、退款、扣费、余额和订单必须具有明确状态机。
  3. 关键资金操作必须保证幂等。
  4. 必须防止重复回调导致重复入账。
  5. 必须防止并发请求造成余额超扣或重复扣费。
  6. 必须验证订单金额、用户、订单状态和支付渠道的一致性。
  7. 支付成功通知必须进行签名验证。
  8. 退款必须关联原订单和原支付记录。
  9. 必须记录资金流水，不得只依赖余额字段。
  10. 余额变更必须具备可追溯的业务来源。
  11. 关键操作必须考虑事务边界和失败补偿。
  12. 必须设计异常恢复、对账和重复通知处理。
  13. 支付成功但本地订单未保存、通知延迟、通知重复和退款失败必须有处理策略。
  14. Outbox、任务恢复和补偿机制应根据现有架构实现。
  15. 数据迁移不得破坏历史订单和资金流水。
  16. 测试必须使用模拟支付渠道、模拟回调和隔离数据库。
  17. 不得使用真实支付、真实退款或真实资金账户进行测试。
  18. 任何资金差异都必须阻断相关验收。
- 验收条件：充值和退款状态机可验证；幂等测试通过；并发测试通过；重复回调测试通过；异常恢复测试通过；流水与余额一致性验证通过；所有测试均不触碰真实资金。

## UAP-06-003 | RELIABILITY-AND-RECOVERY | 可靠性与恢复规范
- 目标：健康检查、超时重试退避熔断、关键任务恢复、重启后状态与降级行为验证。
- 强制性要求：
  1. 关键服务必须有健康检查。
  2. 必须定义超时、重试、退避和熔断策略。
  3. 必须识别关键依赖故障。
  4. 关键任务必须能够恢复。
  5. 必须防止重复执行造成数据损坏。
  6. 必须记录错误、异常和恢复事件。
  7. 数据库迁移必须有恢复方案。
  8. 后台任务必须有失败队列或等效机制。
  9. 必须验证进程重启后的任务状态。
  10. 必须验证外部服务不可用时的降级行为。
  11. 必须记录备份和恢复能力的验证状态。
  12. 不得声称已经验证生产恢复，除非实际完成了授权的生产恢复演练。
- 验收条件：关键任务能够恢复；服务异常能够被检测；重试策略有上限；失败恢复有测试证据。

## UAP-07-001 | WEB-ENGINEERING | Web 工程规范
- 目标：Web 功能对应需求、页面状态完整、表单校验、可访问性与 Uter Design System 3.0 一致性。
- 强制性要求：
  1. Web 功能必须与产品需求对应。
  2. 页面必须覆盖加载、成功、空状态、失败和权限不足状态。
  3. 表单必须有字段校验和错误提示。
  4. 交互必须具有明确反馈。
  5. 页面必须满足可访问性基本要求。
  6. 必须检查路由、状态管理和接口错误处理。
  7. 必须检查性能和资源加载。
  8. 关键业务流程必须有自动化测试。
  9. Web 修改必须执行类型检查、Lint、测试和构建。
  10. UI 必须遵循 Uter 当前有效设计系统；当前设计基线为 UTER Design System 3.0，除非仓库中存在更高版本且已明确生效的正式基线。
  11. 不得以视觉样式修改破坏业务交互。
  12. 必须检查不同屏幕尺寸。
- 验收条件：Web 构建通过；关键路由和流程测试通过；页面状态完整；设计规范一致性有验证结果。

## UAP-07-002 | H5-ENGINEERING | H5 工程规范
- 目标：移动视口、触摸、软键盘安全区、弱网与加载失败、防重复提交与模拟支付回跳验证。
- 强制性要求：
  1. H5 必须适配移动端视口。
  2. 必须检查触摸交互和点击区域。
  3. 必须处理软键盘、滚动和安全区域。
  4. 必须检查弱网和加载失败状态。
  5. 必须检查移动端浏览器兼容性。
  6. 关键业务操作必须避免重复提交。
  7. 支付相关 H5 必须验证跳转和返回状态，但只能使用模拟交易。
  8. 页面必须处理网络中断和接口异常。
  9. 必须检查不同设备尺寸。
  10. H5 必须与 Web 共享业务规则。
  11. H5 必须执行构建、测试和必要的端到端验证。
  12. 不得只根据桌面浏览器截图判断 H5 合格。
- 验收条件：H5 构建通过；移动端关键流程通过；弱网和异常状态得到验证；触摸和布局行为正确。

## UAP-07-003 | CROSS-PLATFORM-CONSISTENCY | 跨平台一致性规范
- 目标：Web 与 H5 共享业务定义、权限、金额订单逻辑与统一 API/错误码，差异需登记。
- 强制性要求：
  1. Web 与 H5 必须共享一致的业务定义。
  2. 相同功能必须有相同的权限规则。
  3. 相同金额、计费和订单逻辑必须保持一致。
  4. 平台差异必须有明确记录。
  5. API 结构和错误码必须统一。
  6. 必须检查页面、交互、字段、校验和状态差异。
  7. 必须建立跨平台功能映射。
  8. 新增功能必须检查所有目标平台。
  9. 不得将某个平台的功能缺失误判为平台设计差异。
  10. 必须有跨平台回归测试。
  11. 差异必须区分合理差异和不合规差异。
  12. 重大不一致必须阻断验收。
- 验收条件：跨平台功能映射完整；核心业务行为一致；不合理差异能够被检测；回归测试通过。

## UAP-08-001 | CI-CD | CI/CD 规范
- 目标：CI 真实执行检查/类型/测试/构建/安全扫描，失败阻断，本地有等效全量验证。
- 强制性要求：
  1. CI 必须执行代码检查、类型检查、测试、构建和安全扫描。
  2. 检查必须使用真实命令和真实退出码。
  3. CI 失败必须能够阻断后续发布步骤。
  4. CI 配置必须纳入版本管理。
  5. 必须区分本地验证、CI 验证和部署验证。
  6. 依赖缓存不得导致错误地复用过期产物。
  7. 构建产物必须可追溯。
  8. 不得通过跳过工作流步骤伪造通过。
  9. 必须检查必要的环境变量是否存在，但不得输出密钥。
  10. 本次 UAP 建设不得擅自触发生产发布。
  11. 必须支持本地全量验证。
  12. 必须生成 CI 验证报告。
- 验收条件：CI 工作流可解析；本地等效验证可执行；失败能够阻断；构建和测试证据完整。

## UAP-08-002 | DEPLOYMENT-AND-ROLLBACK | 部署与回滚规范
- 目标：部署前门禁、配置与迁移兼容检查、回滚方案与部署后健康检查；生产需明确授权。
- 强制性要求：
  1. 部署必须定义环境、版本和依赖。
  2. 部署前必须执行质量门禁。
  3. 必须检查配置和环境变量。
  4. 必须验证数据库迁移兼容性。
  5. 必须有回滚方案。
  6. 必须明确回滚对数据库和数据的影响。
  7. 必须区分代码回滚与数据回滚。
  8. 部署后必须执行健康检查。
  9. 必须记录部署版本和执行证据。
  10. 生产部署必须经过明确授权。
  11. 本次建设只能在本地或隔离测试环境验证部署流程。
  12. 不得将部署脚本存在标记为部署已验证。
- 验收条件：部署流程可执行；测试环境部署可验证；回滚方案有测试证据；生产操作权限得到限制。

## UAP-08-003 | OBSERVABILITY | 可观测性规范
- 目标：结构化日志、Trace ID、错误分类、按任务 ID 查询、敏感信息脱敏与运行证据留存。
- 强制性要求：
  1. 关键服务必须提供健康状态。
  2. 日志必须结构化。
  3. 关键任务必须有 Trace ID 或等效关联 ID。
  4. 错误必须有分类和严重程度。
  5. 关键业务事件必须可查询。
  6. 必须监控任务失败、超时和重试。
  7. 必须监控关键业务链路异常。
  8. 日志不得包含明文密钥和敏感信息。
  9. 必须区分业务错误、系统错误和外部依赖错误。
  10. 必须支持按任务 ID 查询执行记录。
  11. 必须保存关键运行证据。
  12. 不得将日志系统存在误判为完整可观测性。
- 验收条件：关键事件可追踪；任务日志可关联；敏感信息脱敏；故障可定位。

## UAP-09-001 | KNOWLEDGE-MANAGEMENT | 知识管理规范
- 目标：项目知识有来源、适用范围、更新时间，可检索，可发现过时冲突与实现差异。
- 强制性要求：
  1. 项目知识必须有明确来源。
  2. 知识必须包含适用范围和更新时间。
  3. 代码、架构、需求和业务规则必须可关联。
  4. 必须识别过时、冲突和重复知识。
  5. 知识更新必须有变更记录。
  6. Agent 使用知识时必须能够追溯来源。
  7. 不得将推测作为已确认事实存储。
  8. 重要决策必须有证据。
  9. 必须支持知识检索。
  10. 必须避免将敏感信息写入知识库。
  11. 知识与实际代码不一致时必须产生差异记录。
  12. 过时知识必须标记或归档，不能静默继续使用。
- 验收条件：关键项目知识可检索；知识来源可追溯；过时知识可识别；知识与实现差异可发现。

## UAP-09-002 | CONTINUOUS-EVOLUTION | 持续进化规范
- 目标：定期检查规范/配置/执行器/验证器一致性，基于真实失败数据提出可验证改进并防自授权。
- 强制性要求：
  1. UAP 必须定期检查规范、配置、执行器和验证器的一致性。
  2. 必须收集真实运行失败和质量数据。
  3. 必须识别重复缺陷和系统性根因。
  4. 必须提出可验证的改进方案。
  5. 改进必须经过影响分析。
  6. 不得自行降低安全和质量标准。
  7. 不得以自动进化为理由绕过权限策略。
  8. 规范升级必须维护版本和兼容性。
  9. 旧规范废弃必须记录替代关系。
  10. 每次进化必须运行相关回归测试。
  11. 进化失败必须能够恢复原配置。
  12. 必须记录进化前后指标和证据。
  13. 必须防止自动修改规范导致循环放宽标准。
  14. UAP 不得自行授予自己更高权限。
- 验收条件：能够发现规范与执行偏差；能够提出改进方案；改进过程有验证和回滚；安全和质量门禁不可被自动弱化。
