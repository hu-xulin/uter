# Тестирование моделей

Прежде чем подключить большую языковую модель в Uter, пройдите шаги этой главы, чтобы проверить, «соединяется ли, работает ли, стабильна ли и корректно ли считается стоимость» — это поможет избежать проблем после запуска в продакшене.

## Что нужно подготовить

Перед началом тестирования убедитесь, что у вас есть все перечисленное. Отсутствие любого пункта приведёт к сбою на первом шаге.

| Пункт | Описание | Где взять |
| --- | --- | --- |
| **Базовый URL (Base URL)** | Вида `https://uter.ai/v1`; используйте адрес из консоли (возможно, вам выделен отдельный домен) | Консоль → Профиль / документация по подключению |
| **API-ключ (токен)** | Вида `sk-xxxxxxxx`. Это учётные данные, эквивалентные паролю: не раскрывайте их, не пишите во фронтенд-коде, не коммитьте в репозиторий | Консоль → Управление токенами → Создать токен |
| **Квота аккаунта** | Единица тарификации: 500 000 токенов ≈ 1 доллар США. Каждый вызов списывает квоту; при её исчерпании запрос отклоняется | Консоль → Расход / баланс; или `GET /v1/dashboard/billing/usage` |
| **Название модели** | Зарегистрированное имя модели, которую вы тестируете (оно может отличаться от официального названия) | Идентификатор `id` в ответе `GET /v1/models` |

<Callout type="warn">
  Ключ эквивалентен паролю: используйте его только на сервере или в менеджере секретов, никогда не передавайте в браузер, не пишите в открытом виде в логи и не коммитьте в Git.
</Callout>

У токена в консоли четыре состояния: активен, отключён, истёк и исчерпан. Когда квота закончилась, токен считается исчерпанным, и любой вызов вернёт сообщение о недостатке средств. Перед тестированием проверьте состояние на странице управления токенами.

## Что проверяем

Перед использованием модели в продакшене рекомендуем проверить следующие девять аспектов. Первые четыре отвечают на вопрос «работает ли вообще», остальные пять — «стабильно ли и корректно ли считается стоимость».

1. **Связность и аутентификация** — верный ли адрес, действителен ли ключ, не блокирует ли ограничение по IP.
2. **Список моделей и доступность** — существует ли целевая модель и работает ли она.
3. **Базовый диалог** — возвращает ли минимальный запрос нормальный ответ.
4. **Параметры и расширенные возможности** — потоковая передача, temperature, max_tokens, tools/function calling, vision, режим JSON, системный промпт.
5. **Потоковый вывод (SSE)** — идёт ли вывод по токенам и корректно ли он разбирается.
6. **Производительность и задержка** — время до первого токена (TTFT), полное время ответа, поведение на длинном контексте.
7. **Стабильность и лимиты** — поведение при параллельных запросах, повторных попытках и ответах 429.
8. **Квота и тарификация** — корректно ли списывается и уменьшается ли баланс.
9. **Ошибки и граничные случаи** — понятны ли ошибки при неверных параметрах, слишком длинном вводе и недоступной модели, и можно ли обработать их в коде.

## Пошаговая инструкция

В примерах ниже приняты соглашения:

- Базовый URL `BASE=https://uter.ai/v1` (замените на ваш реальный адрес)
- Ключ `TOKEN=sk-your-token-here` (замените на полный ключ из консоли)

Все примеры используют `curl` — после подстановки их можно вставить в терминал и выполнить. Если на вашей машине настроен прокси, добавьте `--noproxy '*'`, чтобы обойти его.

### Шаг 1 · Минимальная связность и аутентификация

```bash
BASE=https://uter.ai/v1
TOKEN=sk-your-token-here

curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" | head -c 800
echo
```

Критерии проверки:

- Вернулся JSON с `object: "list"` и несколькими значениями `id` → связность и аутентификация в порядке.
- Вернулся `{"error":{"message":"That token isn't valid.","type":"...","code":"..."}}` с HTTP 401 → ключ ошибочен или отключён (см. таблицу типовых проблем ниже).
- Соединение не устанавливается / истекает таймаут → адрес неверен или сеть недоступна (см. таблицу типовых проблем ниже).

<Callout type="info">
  Некоторые нативные API производителей используют собственную аутентификацию — она нужна только при работе с их официальным SDK. Claude использует `POST /v1/messages` с заголовками `x-api-key: $TOKEN` и `anthropic-version: 2023-06-01`; Gemini использует `GET /v1beta/models` с заголовком `x-goog-api-key: $TOKEN` либо параметром `?key=$TOKEN` в URL.
</Callout>

### Шаг 2 · Список доступных моделей и подтверждение целевой

```bash
curl --noproxy '*' -s "$BASE/models" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool | grep '"id"' | head -40
```

Найдите идентификатор `id` модели, которую нужно протестировать (например, `gpt-4o`, `claude-3-5-sonnet-20241022` или имя, заданное платформой).

<Callout type="warn">
  Если нужной модели нет в списке, она не включена для вашего аккаунта — свяжитесь с платформой. Угадывать имя и вызывать наугад бессмысленно: вы получите 404 или сообщение об отсутствии доступных каналов.
</Callout>

### Шаг 3 · Минимальный диалог (без потоковой передачи)

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "замените на ваш id модели",
    "messages": [{"role": "user", "content": "Представьте себя в одном предложении."}],
    "max_tokens": 200
  }' | python3 -m json.tool
```

Критерий проверки: в `choices[0].message.content` есть обычный текст, а в `usage` присутствуют `prompt_tokens` / `completion_tokens` → базовый диалог работает.

### Шаг 4 · Потоковый вывод (SSE)

```bash
curl --noproxy '*' -N -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "замените на ваш id модели",
    "messages": [{"role": "user", "content": "Посчитайте до 10."}],
    "stream": true
  }'
```

Критерий проверки: в терминале должны по одному фрагменты `data: {...}`, а в конце — `data: [DONE]`. Корректный поток по токенам означает, что стриминг работает.

<Callout type="info">
  Чтобы увидеть построчный вывод, `curl` требует флага `-N` (отключение буферизации). Со стороны SDK убедитесь, что включён `stream: true` и ответ не буферизуется целиком.
</Callout>

### Шаг 5 · Расширенная возможность: вызов функций (Function Calling)

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "замените на ваш id модели",
    "messages": [{"role": "user", "content": "Какая сейчас погода в Пекине?"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Получить погоду в городе",
        "parameters": {
          "type": "object",
          "properties": {"city": {"type": "string"}},
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

Критерий проверки: в ответе появляется `choices[0].message.tool_calls` (модель решила вызвать `get_weather`), а не выдуманный ею ответ → вызов функций работает.

<Callout type="warn">
  Если ваш продукт зависит от function calling, режима JSON или работы с изображениями, обязательно тестируйте каждую возможность отдельно и не предполагайте, что «если чат работает, то всё работает».
</Callout>

### Шаг 6 · Мультимодальность (зрение) — только для моделей с поддержкой изображений

```bash
curl --noproxy '*' -s "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "замените на id модели со зрением",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "Что изображено на картинке?"},
        {"type": "image_url", "image_url": {"url": "https://example.com/demo.png"}}
      ]
    }]
  }' | python3 -m json.tool
```

Критерий проверки: ответ корректно описывает содержимое изображения → зрение работает. Изображение должно быть доступно по публичному URL: платформа не читает локальные файлы.

### Шаг 7 · Задержка и базовые показатели производительности (запустите 3–5 раз и возьмите среднее)

```bash
for i in 1 2 3; do
  curl --noproxy '*' -s -o /dev/null -w "запуск $i first_byte=%{time_starttransfer}s total=%{time_total}s HTTP=%{http_code}\n" \
    "$BASE/chat/completions" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model":"замените на ваш id модели","messages":[{"role":"user","content":"привет"}],"max_tokens":128}'
done
```

Следите за временем до первого токена (TTFT) и полным временем ответа и сопоставляйте их с вашим SLA. Для длинного контекста дополнительно проверьте длинный промпт (например, 8k / 32k токенов) и убедитесь, что задержка растёт линейно.

### Шаг 8 · Проверка квоты и тарификации

Зафиксируйте баланс до вызова и после него: разница должна примерно соответствовать фактическому расходу.

```bash
# до вызова
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# (между вызовами выполните диалог из шага 3)

# после вызова
curl --noproxy '*' -s "$BASE/dashboard/billing/usage" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
```

Также можно сверить поле `usage` в ответе (`prompt_tokens` + `completion_tokens`) с правилами тарификации.

### Шаг 9 · Граничные случаи и читаемость ошибок

Намеренно вызовите ошибку и убедитесь, что сообщение понятно и его можно обработать в коде:

```bash
# слишком большой max_tokens / некорректный параметр
curl --noproxy '*' -s -w "\nHTTP=%{http_code}\n" "$BASE/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"замените на ваш id модели","messages":[{"role":"user","content":"hi"}],"max_tokens":999999}'
```

Критерий проверки: возвращается структурированная ошибка `{"error":{"message":...,"type":...,"code":...}}` с явным кодом 4xx, а не пустой ответ или стек 500 → ошибки обрабатываются корректно.

## Таблица типовых проблем

| № | Симптом | Вероятная причина | Решение |
| --- | --- | --- | --- |
| **A1** | `401` + `That token isn't valid.` | Ключ скопирован не полностью, с опечаткой или отключён | Скопируйте ключ заново из консоли; убедитесь, что состояние — «активен», ключ не обрезан и в нём нет лишних пробелов |
| **A2** | `401` + `This token has expired. Please create a new one.` | У ключа задан срок действия, который истёк | Создайте новый ключ в консоли; для долгоживущих ключей выставьте срок действия «никогда не истекает» |
| **A3** | `403` + `Your IP is not in the token's allowed list` | У ключа задан белый список IP, и ваш текущий исходящий IP в него не входит | Добавьте ваш публичный исходящий IP в белый список ключа в консоле либо временно отключите ограничение по IP (только для тестовых сред) |
| **A4** | Нет соединения / `Could not resolve host` / долгий таймаут | Ошибочный Base URL, самоподписанный сертификат, обращение из внутренней сети | Проверьте Base URL (должен быть `https://ваш-домен/v1`); при отладке через прокси добавьте `--noproxy '*'`; убедитесь, что сеть доступна |
| **B1** | `Your quota is insufficient.` HTTP 403 | Исчерпана квота аккаунта или ключа | Пополните или увеличьте квоту в консоли; проверьте остаток через `GET /v1/dashboard/billing/usage` |
| **B2** | `No available channel for model "xxx" in group "default".` | Для этой модели в вашем аккаунте не настроен доступный канал | Уточните у платформы доступность модели либо выберите имя из списка `/v1/models`. Не угадывайте имена моделей |
| **B3** | `404` / `model not found` | Ошибка в имени модели либо модель не включена для вас | Выполните шаг 2 и скопируйте полученный `id` дословно |
| **C1** | `429` + запрос ограничен | Сработал лимит на уровне ключа или платформы | Снизьте параллелизм / добавьте повторы с задержкой (экспоненциальный backoff); проверьте лимиты RPM/TPM у ключа; разнесите пакетные задачи по времени |
| **C2** | Периодические `5xx` / таймаут апстрима, успех после повтора | Нестабильность апстрим-модели | Реализуйте повторы с задержкой; платформа повторяет автоматически, но клиенту тоже нужна подстраховка |
| **D1** | Потоковый вывод приходит целиком, а не по токенам | Буферизация на клиенте (например, `curl` без `-N` или SDK без стриминга) | Добавьте `-N` к curl; в SDK убедитесь, что `stream: true` включён и нет буферизации всего ответа |
| **D2** | Китайские и спецсимволы отображаются некорректно | Не указана кодировка или ошибка разбора | Используйте UTF-8 и в запросе, и в ответе; если `python3 -m json.tool` отображает корректно, сервер исправен, а проблема в кодировке терминала |
| **D3** | Ответ обрывается | Слишком малый `max_tokens` либо достигнут лимит вывода модели | Увеличьте `max_tokens`; длинные тексты принимайте потоком по частям |
| **E1** | Списание не совпадает с ожиданием (больше или меньше) | В расчёт могут входить скрытые токены (рассуждения, вызовы инструментов), либо у моделей разные коэффициенты | Сверяйтесь по полю `usage` в ответе; при сомнениях уточните правила тарификации у платформы |
| **E2** | function calling не срабатывает / режим JSON не действует | Модель не поддерживает эту возможность | Проверьте её отдельно на шаге 5; не закладывайтесь на неподдерживаемые возможности — предусмотрите запасной вариант в продукте |
| **F1** | `400` с «объявлением» на китайском языке | Временное изменение поставки апстрим-модели (поставщик вложил уведомление в ошибку), а не ошибка вашего запроса | Убедившись, что формат запроса корректен, свяжитесь с платформой и приложите исходный текст ошибки |

<Callout type="idea">
  Два правила, которые стоит запомнить. Если приходит «нет доступных каналов / модель не найдена», сначала сверьтесь с реальным именем модели через `GET /v1/models`, затем обратитесь в поддержку — **в 90 % случаев «модель не работает» причина именно в этом, а не в коде**. При `401` / `403` сначала проверьте состояние ключа и белый список IP, и только потом Base URL — **проблемы с аутентификацией почти всегда сводятся к «скопировано не полностью / неверный адрес / ограничение не отключено»**.
</Callout>

### Что делать с ошибкой 400 (Bad Request)

`400` означает «сами запрос неверны»: сервер получил запрос, но его содержимое или параметры некорректны, поэтому он отклонил его. Это другой класс, чем аутентификация (401), квота (403) и лимиты (429).

Сначала определите источник по формулировке сообщения:

| Что вы видите | Обычный источник | Что делать |
| --- | --- | --- |
| На китайском, похоже на сообщение платформы | Платформа проверяет запрос перед пересылкой | Измените параметры согласно сообщению |
| На английском, похоже на ошибку OpenAI / Claude / Gemini | Апстрим-провайдер (параметры не отвечают требованиям этой модели) | Измените параметры согласно сообщению (например, добавьте messages, приведите значения к допустимым) |
| На китайском, похоже на уведомление или объявление | Временное изменение поставки апстрим-модели | Это не ваша ошибка — свяжитесь с платформой, приложив текст ошибки |

Частые 400 от самой платформы:

| Что вы видите | Значение | Решение |
| --- | --- | --- |
| `Invalid request: <подробности>` | Платформа не прошла проверку тела запроса | Прочитайте текст после двоеточия и исправьте по нему |
| `Invalid request: unable to determine which model you want to use.` | Не удалось определить модель | Убедитесь, что в запросе корректно указано `"model": "<имя модели>"` |
| `model field is required` | Отсутствует поле `model` | Добавьте параметр `model` |
| Сообщение о том, что это «не корректный JSON» | Некорректный синтаксис JSON в теле запроса | Проверьте кавычки, запятые и экранирование, особенно с не-ASCII символами и переносами строк |

<Callout type="info">
  Если вы видите сообщения вроде «конфигурация модели» или «цена не настроена», это проблема на стороне платформы — свяжитесь с ней, менять запрос не нужно.
</Callout>

Частые 400 от апстрим-моделей:

- `messages is required` / `messages must be a non-empty array` — поле `messages` отсутствует или пустое
- `temperature must be between 0 and 2` / `max_tokens too large` — значение параметра вне допустимого диапазона
- `Unknown parameter: 'xxx'` — передан поле, которое модель не поддерживает
- `1 validation error for ...` — тип поля или обязательное поле не совпадает с ожидаемым

Диагностика за 30 секунд (добавьте `-i` к curl, чтобы увидеть полный ответ):

```bash
curl -i https://uter.ai/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"<имя модели>","messages":[{"role":"user","content":"hi"}]}'
```

Обратите внимание на поле `message` в ответе — обычно в нём сразу указана непосредственная причина.

## Чек-лист перед выводом в продакшен

Скопируйте этот список и отметьте каждый пункт, прежде чем переключать продакшен-трафик.

- [ ] **Базовый URL** зафиксирован в конфигурации (переменные окружения или конфигурационный сервис) и не зашит во фронтенд-код.
- [ ] **Ключ** полностью скопирован из консоли, находится в состоянии «активен», не истёк и имеет достаточную квоту.
- [ ] Если на ключе задан белый список IP, исходящий IP боевого сервера в него добавлен.
- [ ] `GET /v1/models` возвращает целевую модель, и её `id` совпадает с указанным в коде.
- [ ] Диалог без стриминга проходит: удаётся получить `content` и `usage`.
- [ ] Стриминг (SSE) проходит: удаётся разобрать фрагменты `data:` и `[DONE]`.
- [ ] Все **расширенные возможности**, от которых зависит продукт (tools / JSON / зрение / длинный контекст), проверены по отдельности.
- [ ] Зафиксированы базовые показатели задержки (TTFT / полное время), соответствующие вашему SLA.
- [ ] В клиенте реализованы **повторы с задержкой при лимитах** и **запасной повтор при 5xx от апстрима**.
- [ ] Ошибки обрабатываются структурированно по `error.message` / `error.code` / HTTP-коду, а учётные данные не попадают в логи.
- [ ] Списание квоты сверено с полем `usage` и совпадает с ожидаемым.
- [ ] В продакшене ключ не выводится в логи и не коммитится (используется менеджер секретов или переменные окружения).
- [ ] С платформой подтверждены **доступность и правила тарификации** целевой модели.

### Единый формат ошибок

Все ошибки API платформы имеют структуру в стиле OpenAI, что упрощает единообразную обработку на клиенте:

```json
{
  "error": {
    "message": "причина ошибки в понятной человеку форме",
    "type": "invalid_request_error | authentication_error | ...",
    "code": "необязательный код ошибки",
    "param": "необязательное имя проблемного параметра"
  }
}
```

Вместе с HTTP-кодом (401 аутентификация / 403 квота или права / 404 модель / 429 лимит / 5xx апстрим) это покрывает подавляющее большинство клиентской логики.

### Напоминания по безопасности (обязательно)

- **Ключ — это пароль**: используйте его только на сервере или в менеджере секретов, никогда не передавайте в браузер, не пишите в открытом виде в логи и не коммитьте в Git.
- **Маскирование в логах**: аудит платформы не записывает ваш ключ в открытом виде; но когда ваш клиент сам выводит ответы, избегайте записи заголовка `Authorization` в лог.
- **Лимиты и повторы**: обязательно реализуйте повторы с задержкой, иначе лавина повторов может превратить ограничение в полную недоступность сервиса.
