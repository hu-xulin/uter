# ログと非同期タスク

* Uter は、リクエストの詳細、描画の記録、および動画や音楽などの非同期タスクを、それぞれ分けて保存します。
* ログイン後、左ナビゲーションから「Usage Logs」または「Task Logs」にアクセスできます。
* このページでは、3 つのデータ区分、タスクの状態、および API によるクエリ方法をまとめて説明します。

3 つの区分は、次のパスに対応します：

* `/usage-logs/common`：一般的な API 利用ログと課金明細
* `/usage-logs/drawing`：Midjourney の描画タスク
* `/usage-logs/task`：Suno や動画などの一般的な非同期タスク

<Callout type="info">
  一般ユーザーは自分の記録のみを表示できます。Admin と Root は、ページ右上で「All」と「Only Mine」を切り替えられます。「Only Mine」に切り替えた場合、ページは一般ユーザーのフィールドと権限に基づいてデータを返します。
</Callout>

## 利用ログ

* 左サイドバーの「Usage Logs」をクリックするか、`/usage-logs/common` にアクセスすると、API リクエストと課金明細を表示できます。

### レコードの絞り込み

利用ログのレコードクエリで使用できるフィルターオプションは次のとおりです：

| フィルターオプション | 説明 |
|---|---|
| 期間範囲 | レコードの作成時刻で絞り込みます。開始時刻と終了時刻の双方がクエリ範囲に含まれます。 |
| モデル名 | モデル名で絞り込みます。 |
| グループ | リクエストで使用されたグループで絞り込みます。 |
| ログタイプ | All Types、Recharge、Consumption、Management、System、Error、Refund、Login。 |
| API キー名 | API キー名で絞り込みます。 |
| リクエスト ID | Uter リクエスト ID でリクエストを特定します。 |
| 上流リクエスト ID | 上流サービスが返した、または記録したリクエスト ID でリクエストを特定します。 |
| ユーザー名（Admin/Root のみ） | 管理者画面でユーザー名で絞り込みます。 |
| チャネル ID（Admin/Root のみ） | 管理者画面でチャネル ID で絞り込みます。 |

### ページ統計

フィルターバーの統計値は、現在の権限と絞り込み条件に関連しています：

* **使用量**：消費レコードのクォータを集計します。時刻、モデル、グループ、キー、チャネル、ユーザーの条件で絞り込めます。
* **RPM**：過去 60 秒間の消費リクエスト数です。
* **TPM**：過去 60 秒間の入力トークンと出力トークンの合計数です。

### 一覧と詳細

* 一般ユーザーには、時刻とタイプ、トークン、モデル、ストリーム、トークン数、コスト、所要時間、詳細の列が表示されます。
* Admin/Root 画面では、チャネルとユーザーの列も表示されます。

<img alt="利用ログページ" src="01-usage-logs.webp" />

<Callout type="info">
  1. **トークン数**：入力トークン／出力トークンを表示します。キャッシュを使用している場合は、キャッシュの読み取り量と書き込み量も表示されることがあります。
  2. **コスト**：このレコードのクォータ消費または返金結果を表示します。実際の形式は、インスタンスのクォータ表示方法によって異なります。
  3. **所要時間**：時刻情報のある消費レコードまたはエラーレコードの応答時間を表示します。ストリーミングリクエストでは、初回応答時間（FRT）やスループットが追加で表示されることがあります。
  4. **詳細**：レコードをクリックすると詳細ダイアログが開きます。ログの種類と実際に記録されたフィールドに応じて、リクエスト ID、モデルマッピング、エラーまたは返金理由、トークンの詳細、課金明細、キャッシュ／音声／画像の使用状況、ストリーム状態などが含まれる場合があります。すべてのブロックがすべてのレコードで表示されるわけではありません。
  5. 管理者は、詳細でチャネルリトライチェーン、リクエストの変換、課金経路、チャージ監査、管理操作の監査も確認できる場合があります。
</Callout>

<Callout type="warn">
  * **特定のレコードが見つからないのはなぜですか？**
    消費ログが書き込まれるかどうかは、プラットフォームの「System Settings」→「Operations」→「Log Maintenance」→「Record Quota Usage」スイッチで制御されます。Root がこの設定を無効にすると、新しい消費レコードが生成されないことがあります。エラーログもエラーログのスイッチと記録可能なエラー種別に依存します。すべての失敗レスポンスが Error レコードを生成するわけではありません。ユーザープロフィールの「IP アドレスを記録」設定は、消費ログとエラーリクエストログにリクエスト IP を保存するかどうかのみを制御します。ログイン、管理監査、チャージなど他のログは、それぞれの監査プロセスに従って IP を記録することがあります。
</Callout>

## タスクリスト

* 「Task Logs」には「Drawing Logs」と「Asynchronous Task Logs」が含まれます。

1. 「Drawing Logs」：Midjourney の描画タスクログを記録します。
2. 「Asynchronous Task Logs」：テキストから動画、画像から動画、音声生成などの非同期タスクを記録します。

## 描画ログ

* 左サイドバーの「Task Logs」→「Drawing Logs」をクリックするか、`/usage-logs/drawing` にアクセスすると、Midjourney の描画タスク記録を表示できます。
* 一般ユーザーは自分のタスクのみを表示できます。Admin/Root は「All」画面で管理範囲内のタスクを表示でき、チャネルと送信結果も確認できます。

描画ログは、次の条件で絞り込めます：

1. 日付範囲
2. Midjourney タスク ID
3. チャネル ID（Admin/Root のみ）

<img alt="描画ログページ" src="02-drawing-logs.webp" />

<Callout type="info">
  1. 一覧には、送信時刻と状態、チャネル ID（Admin/Root のみ）、操作タイプ、タスク ID、所要時間、送信結果、進捗、画像、プロンプト、失敗理由が含まれます。画像をクリックするとプレビューが表示され、プロンプトをクリックすると全文が表示され、失敗理由をクリックすると完全なエラーメッセージが表示されます。
  2. 描画の状態には、Not Started、Queued、In Progress、Success、Failed、Window Waiting が含まれます。
  3. 描画の状態は、上流タスクをバックグラウンドでポーリングすることで更新されます。ポーリング間隔が存在するため、タスクの状態が遅れることがあります。バックエンドが対応する上流タスクデータを取得した際、概ね 1 時間以上前に送信され、まだ完了していない Midjourney タスクは失敗としてマークされます。
</Callout>

## タスクリスト（非同期タスクログ）

* 左サイドバーの「Task Logs」→「Asynchronous Task Logs」をクリックするか、`/usage-logs/task` にアクセスすると、非同期タスクログを表示できます。一般ユーザーは自分のタスクのみを表示でき、Admin/Root 画面ではチャネル ID とユーザーも表示されます。
* 動画、音楽などの非同期 API は、リクエスト送信時に最終結果を即座に返しません。送信に成功すると、Uter は公開アクセス可能なタスク ID を返し、タスクレコードを保存します。その後、バックエンドが上流サービスをポーリングして、状態、進捗、結果を更新します。

### タスクの絞り込み

タスクログは、次の条件で絞り込めます：

1. 日付範囲
2. タスク ID
3. チャネル ID（Admin/Root のみ）

### 一覧と結果

タスク一覧には、送信時刻と完了時刻、チャネル、ユーザー、タスク ID、プラットフォームと操作、所要時間、状態、進捗、詳細が表示されます：

* Suno のタスクが成功して音声アドレスが返された場合、詳細列で音声をプレビューできます。
* 一部の動画タスクは成功時にプレビュー項目が表示されます。同じアカウントのログインセッションまたは API キーを用いて `/v1/videos/{task_id}/content` をリクエストし、完了したタスクの動画コンテンツを取得することもできます。この API はタスクの所有権を検証し、タスクが未完了または現在のユーザーに属さない場合はコンテンツを返しません。
* その他の失敗したレコードでは、詳細列に失敗理由が表示され、クリックすると完全な情報を確認できます。

## タスク状態とバックエンド処理

非同期タスクログでは、次の状態値を使用します。プラットフォームのアダプターによっては、上流の状態での大文字小文字の区別やプラットフォーム差異が保持される場合があるため、API の戻り値は実際のタスクリコードに基づいて判断してください。

| 状態 | 意味 |
|---|---|
| `Not Started` | タスクレコードは作成されていますが、処理は開始されていません。 |
| `Queued` | 上流に送信され、今後の処理を待っています。 |
| `In Queue` | 処理キューに入っています。 |
| `In Progress` | 処理中です。 |
| `Success` | 完了しました。結果を参照または取得できます。 |
| `Failed` | 処理に失敗しました。失敗理由はタスクレコードに書き込まれます（上流から提供された場合）。 |
| `Unknown` | 未知の状態に対する内部定義のフォールバック値です。 |

<img alt="タスクリストページ" src="03-task-logs.webp" />

<Callout type="info">
  タスク状態はバックグラウンドのポーリングで更新されるため、送信直後の新しいタスクでは状態が延迟する場合があります。デフォルトでは、非同期タスクは約 15 秒ごとにポーリングされます。ポーリングは `UPDATE_TASK` が有効で、かつ未完了のタスクがある場合にのみ実行されます。非同期タスクのタイムアウトしきい値は `TASK_TIMEOUT_MINUTES` で制御され、デフォルトは 1440 分です。`0` に設定するとタイムアウト処理は無効になります。
</Callout>

### 失敗・タイムアウト・返金

タスクが失敗の終了状態に入った後、送信段階で事前減算されたクォータがあった場合、システムは通常、成功した返金時に返金処理を試み、`Refund` ログを記録します。返金に成功すると、タスクレコード内の返金待ちクォータはクリアされ、ユーザーとチャネルの累積使用量が減少します。リクエスト数がこのことによって巻き戻されることはありません。

<Callout type="warn">
  次のような状況では、ページの状態と残高が一時的に不一致になることがあります：

  1. タスクに事前減算されたクォータがなかった場合（`quota = 0`）
  2. 資金源からの返金に失敗し、システムが再試行または手動照合のためにタスクのクォータを保持する場合

  * 返金を調査する際は、ウォレット残高または残りのサブスクリプションクォータ（および有効な API キーのクォータ）と、一般的な利用ログの「Refund」レコードの両方を確認してください。「Failed」という状態だけで返金が完了したかを判断しないでください。
</Callout>

## API リファレンス

### ログクエリ用 API

コンソールではなく API を利用する場合、次の読み取り専用 API を呼び出せます。これらの API も認証と権限の制限の対象であり、一般ユーザーの結果は現在のアカウントに厳密に限定されます。

| データ | 管理者 API | ユーザー API | 時刻パラメータの単位 |
|---|---|---|---|
| 一般的なログ | `GET /api/log/` | `GET /api/log/self` | 秒（`created_at`） |
| ログ統計 | `GET /api/log/stat` | `GET /api/log/self/stat` | 秒 |
| Midjourney 描画 | `GET /api/mj/` | `GET /api/mj/self` | ミリ秒（`submit_time`） |
| 非同期タスク | `GET /api/task/` | `GET /api/task/self` | 秒（`submit_time`） |

ログとタスクの一覧 API はページネーションパラメーター `p` と `page_size` を使用します。ページ番号は `1` から始まります。正の整数を通常どおり使用した場合、`page_size` が `100` を超えた場合、`100` に切り詰められます。ユーザーログの総件数も、インスタンス内部のクエリ上限の影響を受けます。タスクの返却データには、キー、上流タスク識別子、または課金コンテキストを含む可能性があるプライベートフィールドは含まれません。

さらに、`GET /api/log/token` は API キーと併用して、そのキーの最近のログを読み取れます。この API は読み取り専用のトークン認証を使用します。キーが存在すること、明示的に無効化されていないこと、その所有ユーザーが有効であることを確認しますが、キー有効期限やクォータ超過を理由にクエリを拒否することはありません。最大で最近 `1000` 件のレコードを返します。

タスク一覧 API の一般的なクエリパラメーターは次のとおりです：

| 範囲 | メソッドとパス | 一般的なクエリパラメーター |
|---|---|---|
| 現在のユーザー | `GET /api/task/self` | `p`、`page_size`、`task_id`、`start_timestamp`、`end_timestamp`。加えて `platform`、`action`、`status` も受け付けます。 |
| Admin/Root | `GET /api/task/` | ユーザー API のパラメーターに `channel_id` が加わり、`platform`、`action`、`status` で絞り込めます。 |

<Callout type="info">
  タスク API の `start_timestamp` と `end_timestamp` は Unix タイムスタンプの秒単位です。Midjourney 描画 API の時刻パラメータはミリ秒単位です。
</Callout>

### 非同期生成とタスクの API

インスタンスでは、設定されたチャネルとアダプターに応じて、次の非同期生成および上流タスククエリ API が提供されます。送信・クエリ API は通常 API キー認証を使用します。動画コンテンツのプロキシは API キーとログインセッションの両方に対応し、タスクの所有権検証を行います。Midjourney の画像プロキシは例外として、API キーは必要ありません。以下の `/api/task` 一覧 API は、ログインユーザーまたは管理者の権限を使用します。実際の認証方法は API の要件に従います。

| API | パス | 説明 |
|---|---|---|
| OpenAI 動画生成 | `POST /v1/videos` | OpenAI 互換の非同期動画生成タスクを作成します。成功時にタスク識別子を返します。 |
| OpenAI 動画タスククエリ | `GET /v1/videos/{task_id}` | 動画生成タスクの状態、進捗、結果情報をクエリします。 |
| 動画コンテンツ取得 | `GET /v1/videos/{task_id}/content` | 完了した動画コンテンツをストリーミングで返します。システムはタスクの結果に基づいて上流からコンテンツを取得するか、保存されたデータ URL をデコードします。 |
| 動画リミックス | `POST /v1/videos/{video_id}/remix` | 既存動画に基づいて新しい Remix の非同期タスクを送信します。 |
| 既存の動画生成 | `POST /v1/video/generations` | 既存の動画生成パスと互換があり、非同期動画タスクを作成します。 |
| 既存の動画タスククエリ | `GET /v1/video/generations/{task_id}` | 既存の動画生成タスクの状態と結果をクエリします。 |
| Kling テキストから動画 | `POST /kling/v1/videos/text2video` | Kling 形式を使用してテキストから動画タスクを送信します。システムはまずリクエスト形式の変換を行います。 |
| Kling 画像から動画 | `POST /kling/v1/videos/image2video` | Kling 形式を使用して画像から動画タスクを送信します。 |
| Kling タスククエリ | `GET /kling/v1/videos/text2video/{task_id}` `GET /kling/v1/videos/image2video/{task_id}` | Kling のテキストから動画、または画像から動画タスクの結果をクエリします。 |
| 即夢公式 API | `POST /jimeng/` | 即夢の公式 API 形式と互換があり、`Action` や `Version` などのパラメーターでタスク送信とクエリ操作を区別します。 |
| Suno タスク送信 | `POST /suno/submit/{action}` | Suno の音楽生成タスクを送信します。タスクの種別は `action` パラメーターで決まります。 |
| Suno タスククエリ | `POST /suno/fetch` `GET /suno/fetch/{id}` | Suno のタスク一覧、または指定したタスクの状態と結果をクエリします。 |
| Midjourney タスク送信 | `POST /mj/submit/{action}` `POST /{mode}/mj/submit/{action}` | `imagine`、`describe`、`blend`、`change`、`simple-change`、`edits`、`video`、`action`、`modal`、`shorten` などのタスク操作に対応します。 |
| Midjourney タスククエリ | `GET /mj/task/{id}/fetch` `GET /mj/task/{id}/image-seed` `POST /mj/task/list-by-condition` | タスク状態、画像シード、または条件によるタスク一覧をクエリします。`{mode}` プレフィックス付きのパスにも対応します。 |
| Midjourney 画像プロキシ | `GET /mj/image/{id}` `GET /{mode}/mj/image/{id}` | Midjourney タスク ID に基づいて生成済み画像を取得またはプロキシします。 |
| Midjourney 拡張操作 | `POST /mj/insight-face/swap` `POST /mj/submit/upload-discord-images` | 顔の入れ替えや Discord 画像のアップロードなどの拡張機能を提供します。 |

## データダッシュボードとの関係

* ログは詳細な記録であり、データダッシュボードは時刻、モデル、ユーザー、チャネルごとに集計した統計を提供します。
* それぞれの絞り込み範囲、更新タイミング、統計方法は異なる場合があります。
* 新しいリクエストはまずログに現れ、グラフのデータは集計または更新が必要な場合があります。

<Callout type="info">
  呼び出しを調査する際は、まず時刻、モデル、リクエスト ID、上流リクエスト ID を用いて一般的なログでリクエストを特定することをお勧めします。非同期リクエストの場合は、送信 API が返した `task_id` を記録し、その後で最終的なタスク状態と失敗の詳細をクエリしてください。タスクが長時間変化しない場合は、チャネルの利用可否、タスクのポーリングスイッチ、タイムアウト設定、および該当する「Refund」ログを確認してください。
</Callout>
