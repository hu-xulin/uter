# UTER Design Compliance Audit
## UTER Design System 3.0 全项目设计规范合规审计指令

**审计对象：** Uter 项目完整前端代码库  
**审计标准：** UTER Design System 3.0  
**审计类型：** 全项目、全量、独立、证据驱动的合规审计  
**审计阶段：** Audit Only，不在本阶段直接修改被审计代码

---

# 1. 审计目标

对 Uter 项目进行一次全面设计规范合规审计，验证当前代码、组件、页面及最终浏览器渲染结果是否严格符合 UTER Design System 3.0。

不得仅根据现有设计 Token 文件判断合规。

必须同时检查：

1. 设计 Token 定义。
2. Token 实际引用情况。
3. CSS 和 Tailwind 实现。
4. 基础组件。
5. 业务组件。
6. 全部业务页面。
7. Light / Dark 主题。
8. PC Web 和 H5。
9. 实际浏览器渲染结果。
10. WCAG 2.2 AA 适用要求。
11. 自动化质量门禁。
12. 设计系统展示页。

审计目标是发现实际不符合规范的问题，而不是证明项目已经符合规范。

不得为了通过审计而降低标准。

# 2. 审计安全要求

## 2.1 固定审计基线

开始审计前：

- 获取当前 Commit SHA。
- 检查 Git 工作区状态。
- 记录当前分支。
- 记录未提交修改。
- 记录未跟踪文件。
- 确认依赖及包管理器。
- 固定本次审计使用的代码基线。

审计期间不得让代码版本发生不可追踪的变化。

不得覆盖用户未提交的修改。

## 2.2 只审计，不直接修改

本阶段只允许：

- 阅读源码。
- 执行静态扫描。
- 执行测试。
- 启动本地开发环境。
- 使用浏览器检查页面。
- 生成截图。
- 生成审计报告。
- 在独立审计目录保存检查产物。

禁止直接修改被审计项目代码。

如发现问题，先记录完整证据和修复建议，等待进入独立整改阶段。

# 3. Phase 1：项目与页面资产盘点

必须完整识别：

- 所有前端应用。
- 所有路由。
- 所有页面。
- 所有布局。
- 所有基础组件。
- 所有业务组件。
- 所有主题入口。
- 所有 Token 文件。
- 所有全局 CSS。
- 所有第三方 UI 组件。
- 所有设计系统展示页面。

输出：

1. 路由清单。
2. 页面清单。
3. 组件清单。
4. Token 文件清单。
5. 主题文件清单。
6. 样式文件清单。
7. 第三方组件清单。

无法访问或无法运行的页面必须单独列出。

# 4. Phase 2：Token 合规审计

检查全部 Token：

## 4.1 Typography

- 字体家族是否为 Inter + 思源黑体。
- 是否存在未授权字体。
- 是否完整包含十档字号。
- 是否包含四级页面标题。
- 是否包含三档 Mono 字号。
- 是否包含配套行高。
- 常规 UI 文本是否小于 12px。
- PC 正文是否使用 14px 基准。
- H5 输入文字是否至少 16px。

## 4.2 Color

检查：

- 品牌色阶。
- Slate 中性色。
- 文字颜色。
- 页面表面。
- 边框。
- 状态色。
- 图表色。
- Syntax 色。
- Terminal 色。
- Light / Dark 配对。

检查所有 Token 的实际引用。

不得只验证 Token 是否存在。

## 4.3 Spacing

- 是否遵循 4px 基础网格。
- 是否存在未登记的间距。
- 是否存在大量任意 padding / margin。
- 是否有语义间距 Token。
- 页面 Gutter 是否统一。

## 4.4 Radius

检查七档圆角：

6、8、10、12、14、16、9999px。

发现其他圆角时，检查是否有经过批准的例外。

## 4.5 Shadow

检查五档 Elevation 和独立 Brand Glow。

确认普通卡片是否滥用 Shadow。

检查 Light / Dark 是否独立定义。

## 4.6 Motion

检查：

- Duration Token。
- Easing Token。
- 动画时长。
- 无限循环动画。
- Reduced Motion。
- 是否存在未登记动画。

# 5. Phase 3：代码静态合规审计

建立代码扫描工具，至少覆盖：

- CSS。
- SCSS（如果存在）。
- JSX。
- TSX。
- JavaScript。
- TypeScript。
- Tailwind CSS class。
- 内联 style。
- CSS-in-JS。
- 动态样式。

检查以下问题：

1. 未授权硬编码颜色。
2. 未授权字体。
3. 非标准字号。
4. 非标准行高。
5. 非标准间距。
6. 非标准圆角。
7. 非标准阴影。
8. 未登记透明度。
9. 重复组件样式。
10. 重复 Token。
11. 自定义主题变量。
12. 绕过统一组件的实现。
13. Light / Dark 不一致。
14. 无效或未使用 Token。
15. CSS 变量循环引用。

所有扫描规则必须有合理的允许列表。

Token 源文件、图表、第三方资产等合法例外不能被误报为违规。

同时也不能通过无限扩大允许列表规避审计。

每个问题必须输出：

- 文件路径。
- 行号。
- 问题类型。
- 实际代码。
- 对应规范章节。
- 风险等级。
- 修复建议。

# 8. Phase 6：浏览器视觉审计

使用 Playwright 对真实页面进行浏览器渲染检查。

建议视口：

- 1440px。
- 1280px。
- 1024px。
- 768px。
- 390px。

主题：

- Light。
- Dark。

根据页面功能检查：

- Default。
- Hover。
- Active。
- Focus。
- Disabled。
- Loading。
- Error。
- Empty。
- Long Content。

生成截图并记录：

- 页面。
- 视口。
- 主题。
- 页面状态。
- 截图路径。
- 差异结果。

使用视觉回归工具识别：

- 元素偏移。
- 字体变化。
- 尺寸异常。
- 颜色变化。
- 边框异常。
- 圆角异常。
- 布局溢出。
- 遮挡。
- 裁切。

截图差异不能直接等同于设计违规。

必须排除动态内容、时间、随机数据、字体加载和动画等噪声，并对真实差异进行人工复核。

# 9. Phase 7：无障碍审计

使用 axe-core 等工具执行自动化检查，并补充人工键盘验证。

至少检查：

- 普通文本对比度 4.5:1。
- 大号文字对比度 3:1。
- 必要 UI 边界 3:1。
- Focus Ring。
- 键盘操作。
- Label 关联。
- Accessible Name。
- 错误提示。
- 弹窗焦点管理。
- Focus Not Obscured。
- Touch Target。
- Reduced Motion。
- 色彩之外的状态表达。

必须根据实际渲染背景计算对比度。

Alpha 透明度必须先合成，再计算。

不得将 axe-core 零错误等同于完整 WCAG 合规。

# 11. Phase 9：问题评级

每个问题按照以下等级分类：

P0：严重问题

- 设计系统基础架构失效。
- 主题整体异常。
- 大范围无法识别的文本或控件。
- 关键交互不可用。

P1：高优先级问题

- 品牌色或语义色大范围不合规。
- 必要文字对比度不达标。
- 核心组件大量绕开统一实现。
- Light / Dark 关键组件缺失。
- 关键无障碍问题。

P2：中优先级问题

- 局部字体、字号、间距、圆角不一致。
- 普通组件状态不完整。
- 页面视觉层级不统一。
- 非关键响应式异常。

P3：低优先级问题

- 轻微视觉偏差。
- 不影响功能的局部细节。
- 文档和 Token 命名问题。

同时区分：

- PASS。
- FAIL。
- PENDING。
- N/A。

PENDING 不得计为 PASS。

N/A 必须附带理由。

1. 所有适用页面均已完成审计。

5. 所有强制文字对比度检查通过。
