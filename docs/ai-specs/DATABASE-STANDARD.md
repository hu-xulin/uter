# DATABASE-STANDARD
# Uter 数据库设计与数据一致性规范

**项目：** Uter  
**文档类型：** 数据库工程标准  
**适用范围：** 所有持久化数据、数据库操作和数据迁移  
**规范级别：** 强制执行

---

## 1. 规范目标

保证数据库结构合理、数据准确、事务完整、并发安全，并且能够追溯和恢复。

数据库设计必须以真实业务需求为依据。

## 2. 基本原则

1. 数据结构必须表达明确业务含义。
2. 核心数据必须有明确所有权。
3. 重要数据变更必须可追溯。
4. 关键业务操作必须保证一致性。
5. 数据库操作必须考虑并发。
6. 迁移必须可验证。
7. 不得随意删除历史数据。
8. 不得未经授权修改生产数据。

## 3. 命名规范

表名、字段名、索引名和约束名应遵循项目已有约定。

命名必须：

- 含义清晰。
- 保持一致。
- 避免模糊缩写。
- 避免不同表对同一业务概念使用不同名称。

不得为追求统一而无条件重命名已有数据库对象。

## 4. 数据类型

### 金额

涉及金额时必须明确：

- 币种。
- 存储单位。
- 精度。
- 舍入方式。
- 计算规则。

禁止直接使用不安全的浮点数处理资金计算。

### Token

必须明确：

- Token 数量类型。
- 输入与输出统计。
- 缓存 Token 统计。
- 计费单位。
- 计费精度。

### 时间

必须明确：

- 时间存储格式。
- 时区策略。
- 创建时间。
- 更新时间。
- 业务发生时间。

### 状态

状态字段必须有清晰定义。

禁止使用含义不明确的数字或字符串状态。

## 5. 索引与约束

根据实际查询和业务约束设计：

- 主键。
- 唯一索引。
- 普通索引。
- 组合索引。
- 外键或等价完整性约束。

必须评估索引对写入性能的影响。

不能只根据单个查询盲目增加索引。

## 6. 事务规范

涉及多个相关数据变更时，必须明确事务边界。

特别关注：

- 订单状态。
- 账户余额。
- 余额流水。
- Token 消费记录。
- 计费结算。
- 退款。
- 任务状态。

事务必须尽量保持短小。

禁止在长事务中执行不可控的外部网络请求。

外部服务与数据库之间的一致性，应采用适合业务的幂等、Outbox、补偿或对账机制。

## 7. 余额专项规则

余额变化必须有可追溯的业务依据。

必须保证：

- 余额变更与流水记录的一致性。
- 重复操作不会重复入账。
- 并发扣款不会造成非法透支。
- 失败操作不会留下错误余额。
- 流水可以追溯来源。
- 余额异常能够通过对账发现。

不得仅通过直接覆盖余额字段实现资金操作。

## 8. 支付订单专项规则

必须考虑：

- 订单唯一性。
- 支付金额核验。
- 订单状态机。
- 重复通知。
- 并发通知。
- 通知验签。
- 订单超时。
- 主动查询。
- 对账恢复。
- 退款和冲正。

不能将第三方回调直接视为无条件可信的数据库更新指令。

## 9. Token 计费专项规则

必须确保：

- 用量记录具有明确来源。
- 计费依据可追溯。
- 重试不会造成重复扣费。
- 流式请求中断有明确处理。
- 计费结果与余额流水可关联。
- 价格变化不会错误覆盖历史计费依据。
- 精度和舍入规则一致。

必要时保存实际计费时使用的价格快照。

## 10. 并发控制

根据业务选择：

- 原子更新。
- 乐观锁。
- 悲观锁。
- 唯一约束。
- 幂等键。
- 事务隔离。

必须考虑：

- 丢失更新。
- 脏读。
- 不可重复读。
- 幻读。
- 死锁。
- 重复写入。

不能仅依靠应用层先查询再更新来保证并发唯一性。

## 11. 数据库迁移

每次 Schema 变更必须：

1. 明确变更目的。
2. 检查兼容性。
3. 设计迁移步骤。
4. 考虑旧版本代码。
5. 考虑数据回填。
6. 考虑索引构建。
7. 验证迁移结果。
8. 制定恢复方案。

禁止未经授权直接在生产数据库执行迁移。

迁移脚本不得依赖不可重复的人工操作。

## 12. 数据删除

删除数据前必须判断：

- 是否存在关联数据。
- 是否有审计要求。
- 是否影响订单和流水。
- 是否需要保留历史记录。
- 是否需要软删除。
- 是否涉及法律或合规保留要求。

禁止级联删除重要资金和计费历史记录，除非经过明确业务与合规设计。

## 13. 备份与恢复

必须明确：

- 备份策略。
- 恢复策略。
- 恢复验证。
- 数据保留周期。
- 恢复点目标。
- 恢复时间目标。

备份存在不等于恢复能力已经验证。

## 14. 测试要求

必须根据实际数据库类型执行：

- Schema 测试。
- Migration 测试。
- 事务测试。
- 并发测试。
- 唯一约束测试。
- 幂等测试。
- 数据一致性测试。
- 回滚测试。

## 15. 完成定义

数据库修改必须满足：

- Schema 合理。
- 约束完整。
- 事务边界明确。
- 并发风险可控。
- 迁移可验证。
- 测试通过。
- 兼容性已评估。
- 数据恢复风险已披露。

---

**Uter 的余额、支付、订单和 Token 计费数据必须优先保证准确性与可追溯性。**
