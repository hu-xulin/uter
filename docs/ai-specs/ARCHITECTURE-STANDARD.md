# ARCHITECTURE-STANDARD
# Uter 系统架构规范

**项目：** Uter  
**文档类型：** 系统架构与模块设计标准  
**适用范围：** 后端、前端、Go Modules、AI Relay、数据库及基础设施  
**规范级别：** 强制执行

---

## 1. 规范目标

建立稳定、清晰、可扩展、可维护的系统架构。

AI 必须理解现有架构后再进行修改，不得为了实现单项功能而破坏整体架构。

## 2. 架构基本原则

### 2.1 单一职责

每个模块必须具有清晰的职责。

不得将不相关的业务逻辑集中到一个模块中。

### 2.2 高内聚、低耦合

模块内部职责应保持一致。

模块之间通过明确接口协作，避免直接依赖其他模块的内部实现。

### 2.3 依赖方向明确

必须建立合理的依赖方向。

禁止：

- 循环依赖。
- 不必要的跨层调用。
- 业务模块直接操作不属于自己的内部状态。
- 为方便开发绕过公共接口。
- 将基础设施细节扩散到业务层。

### 2.4 遵循现有技术栈

新增实现必须优先遵循仓库已有技术选型。

更换框架、数据库、状态管理或核心组件必须进行影响分析。

## 3. 架构事实来源

AI 必须从真实仓库确认：

- 实际目录结构。
- 实际 Go Modules。
- 实际前端框架。
- 实际数据库。
- 实际缓存。
- 实际消息或任务机制。
- 实际部署方式。
- 实际 API 入口。
- 实际依赖关系。

不得将规划中的架构误认为已经实现的架构。

## 4. 模块边界

每个模块必须明确：

- 模块名称。
- 模块职责。
- 对外接口。
- 内部实现。
- 数据所有权。
- 依赖模块。
- 被依赖模块。
- 测试边界。

模块之间不得随意共享可变内部状态。

## 5. 后端架构要求

在现有架构允许的前提下，建议区分：

- API / Transport Layer。
- Application / Service Layer。
- Domain / Business Layer。
- Repository / Data Access Layer。
- Infrastructure Layer。

职责要求：

### API 层

处理：

- HTTP / RPC 输入。
- 参数校验。
- 身份和权限上下文传递。
- 响应结构。
- 错误映射。

不得集中实现复杂业务规则。

### Service 层

负责：

- 业务流程编排。
- 事务协调。
- 多模块调用。
- 业务结果处理。

### Domain 层

负责：

- 核心业务规则。
- 状态转换。
- 计费规则。
- 业务约束。

### Repository 层

负责：

- 数据读取。
- 数据写入。
- 查询封装。
- 持久化细节。

### Infrastructure 层

负责：

- 外部服务。
- 缓存。
- 消息机制。
- 第三方 SDK。
- 文件和网络资源。

不得为了形式化分层而无意义地增加抽象。

## 6. 前端架构要求

必须明确：

- 页面与路由边界。
- 业务组件边界。
- 公共组件边界。
- API 请求层。
- 状态管理。
- 表单管理。
- 错误处理。
- 权限控制。
- 样式组织。
- 类型定义。

禁止：

- 页面中重复实现大量公共逻辑。
- 在 UI 组件中直接混入复杂数据访问逻辑。
- 绕过统一 API 客户端。
- 在多个地方维护相同业务状态。
- 未经分析引入新的全局状态管理方案。

## 7. AI Relay 架构要求

必须明确：

- 请求入口。
- 身份鉴权。
- API Key 校验。
- 模型映射。
- 渠道路由。
- 上游请求。
- 响应转换。
- Token 统计。
- 计费结算。
- 日志和追踪。
- 重试与超时。
- 故障隔离。

计费逻辑不得与不受控的上游请求代码混杂。

## 8. 数据所有权

每类核心数据必须明确负责模块。

例如：

- 用户账户数据。
- 支付订单。
- 余额流水。
- Token 使用记录。
- API Key。
- 模型配置。
- 渠道配置。

其他模块应通过定义好的服务或接口访问，不得随意绕过数据所有权边界。

## 9. 外部服务集成

第三方服务必须通过明确的适配层接入。

必须考虑：

- 超时。
- 重试。
- 错误转换。
- 限流。
- 熔断。
- 日志脱敏。
- 版本兼容。
- 服务不可用。

禁止让第三方 SDK 的数据结构直接成为整个系统的公共业务契约，除非经过明确设计。

## 10. 架构变更管理

以下变更必须先完成架构影响分析：

- 模块合并或拆分。
- 核心依赖调整。
- 数据库选型变化。
- 认证架构变化。
- 支付架构变化。
- 计费架构变化。
- Relay 核心链路变化。
- 公共接口不兼容修改。

重大决策应记录 ADR。

ADR 至少包含：

- 背景。
- 问题。
- 可选方案。
- 最终决策。
- 决策理由。
- 影响范围。
- 迁移方案。
- 回滚方案。

## 11. 架构图与文档

架构发生变化时，应同步：

- 系统上下文图。
- 模块关系图。
- 关键调用链。
- 数据流图。
- 关键业务时序图。

文档必须与实际代码一致。

## 12. 完成定义

架构修改必须满足：

- 职责清晰。
- 依赖合理。
- 无不必要循环依赖。
- 关键接口稳定。
- 相关测试通过。
- 架构文档同步。
- 兼容性风险已披露。

---

**任何 AI 不得仅为降低当前开发难度而牺牲 Uter 的长期架构质量。**
