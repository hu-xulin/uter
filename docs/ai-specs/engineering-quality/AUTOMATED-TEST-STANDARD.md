# Uter 全面自动化测试与问题修复规范

**文件名：** `UTER-AUTOMATED-TEST-STANDARD.md`  
**项目名称：** Uter  
**文档类型：** 全仓库自动化测试、缺陷修复、回归验证规范  
**适用对象：** AI Coding Agent、开发人员、测试工程师  
**执行模式：** 实际测试 + 发现问题直接修复 + 回归测试  
**默认提交权限：** 不允许擅自 Commit、Push、Merge 或部署

---

# 1. 测试目标

本规范要求对 Uter 项目执行真实、完整、可重复的自动化测试。

目标不是简单执行一次测试命令，而是建立完整的质量验证流程：

1. 固定源码基线。
2. 检查完整仓库。
3. 识别所有独立模块。
4. 检查现有 CI/CD 测试结果。
5. 建立隔离测试环境。
6. 实际执行全部可运行测试。
7. 增加关键业务缺失的测试。
8. 发现 Bug 后直接修复代码。
9. 对修复进行回归测试。
10. 执行静态分析、安全扫描和覆盖率统计。
11. 形成完整测试报告。

**所有测试必须以实际执行结果为准，不允许通过静态推测、模拟输出或未经验证的结果代替测试。**

---

# 2. 执行原则与权限

## 2.1 允许直接修复

自动化测试过程中发现问题后，允许直接修改代码。

包括：

- 业务逻辑错误。
- 并发问题。
- 数据库问题。
- 支付问题。
- Token 计费问题。
- API 问题。
- 前端问题。
- Electron 问题。
- 安全漏洞。
- 测试本身的缺陷。

修复时必须：

1. 确认失败原因。
2. 判断是否为真实产品缺陷。
3. 定位根因。
4. 修改实现。
5. 增加或完善测试。
6. 重新执行失败测试。
7. 执行相关回归测试。

如果失败来自测试环境、外部服务或测试用例本身，必须明确区分，不能随意修改产品代码。

## 2.2 不允许的操作

未经明确授权：

- 不得 Commit。
- 不得 Push。
- 不得 Merge。
- 不得发布。
- 不得部署生产环境。
- 不得操作真实支付资金。
- 不得修改生产数据库。
- 不得覆盖用户已有的未提交修改。
- 不得擅自删除已有测试。
- 不得降低原有测试断言。
- 不得屏蔽失败结果。

# 3. 第一阶段：测试基线与环境检查

## 3.1 固定 Commit SHA

测试开始前记录：

| 信息 | 记录内容 |
|---|---|
| Repository | 仓库地址 |
| Branch | 当前分支 |
| Commit SHA | 完整 SHA |
| Working Tree | clean / dirty |
| Go Version | 实际版本 |
| Node Version | 实际版本 |
| Bun Version | 实际版本 |
| Package Manager | 实际版本 |
| OS | 实际环境 |
| Start Time | 测试开始时间 |

测试报告必须说明测试对应的源码版本。

修复产生的新代码必须单独记录相对于基线的变更。

## 3.2 检查工具链

检查实际项目所需：

- Go。
- Node.js。
- Bun。
- npm / pnpm / yarn（按项目实际使用情况）。
- Git。
- 数据库。
- Redis。
- Docker（如项目需要）。
- 浏览器自动化工具。
- Electron 构建环境。
- 安全扫描工具。

不得擅自替换项目指定的包管理器或升级工具链。

## 3.3 环境隔离

测试环境必须与生产环境隔离。

优先使用：

- 独立测试数据库。
- 独立 Redis。
- 独立测试配置。
- 独立环境变量。
- 模拟支付服务。
- 模拟上游 AI 服务。
- 本地 Mock Server。
- 临时文件目录。

禁止测试程序意外连接生产数据库或真实支付接口。

测试前必须检查数据库连接字符串、支付配置和上游服务地址。

如果无法确认环境安全，不得执行可能产生真实资金、生产数据修改或外部副作用的测试。

## 3.4 测试数据管理

测试数据必须可重复创建和清理。

要求：

- 测试用户独立。
- 测试订单独立。
- 测试余额独立。
- 测试 API Key 独立。
- 测试数据库可重置。
- 测试文件可清理。
- 不依赖不确定的历史数据。
- 不依赖固定生产账号。

禁止在测试结束时误删用户原有数据。

# 4. 第二阶段：检查现有 CI/CD 测试结果

检查仓库已有的 GitHub Actions 或其他 CI 系统。

必须实际核对：

- Workflow 文件。
- 最近运行记录。
- 成功与失败状态。
- 失败日志。
- 测试报告。
- 覆盖率报告。
- 构建产物。
- 安全扫描产物。
- 运行环境。
- 执行时间。
- 使用的 Commit SHA。

重点识别：

- CI 是否真正执行测试。
- 是否存在只执行构建、不执行测试的流程。
- 是否存在失败但被忽略的步骤。
- 是否存在允许失败的关键检查。
- 是否存在跳过关键测试的条件。
- 是否存在不同分支使用不同测试标准。
- 是否存在覆盖率结果未上传。
- 是否存在扫描结果未保存。
- 是否存在使用浮动版本依赖的问题。

必须区分：

- CI 已成功。
- CI 已失败。
- CI 未执行。
- CI 被跳过。
- CI 执行不完整。
- CI 结果无法获取。

不能把 CI 显示绿色等同于项目没有 Bug。

# 5. 第三阶段：Go 后端全面测试

## 5.1 识别全部 Go Module

扫描所有 `go.mod`。

每个独立 Go Module 必须分别执行：

- 依赖检查。
- 编译。
- 单元测试。
- 静态分析。
- 必要时竞态检测。
- 覆盖率统计。

不得只测试根目录模块。

## 5.2 基础测试

在每个模块实际支持的情况下执行：

```bash
go version
go env
go mod verify
go test ./...
go vet ./...
go build ./...
```

如果项目存在特定构建标签、生成步骤或测试环境要求，必须按照实际项目配置执行。

不得因为某个模块无法测试就跳过其他模块。

## 5.3 竞态检测

执行：

```bash
go test -race ./...
```

重点覆盖：

- 并发余额扣减。
- 支付回调。
- 任务调度。
- 缓存更新。
- 全局配置。
- 用户状态。
- 模型供应商状态。
- 多 Goroutine 共享数据。

如果 race 检测不支持当前运行平台或环境，必须记录具体原因。

## 5.4 覆盖率

执行：

```bash
go test -cover ./...
```

对于适合生成覆盖率文件的模块，执行：

```bash
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

必须分别记录：

- 语句覆盖率。
- 核心模块覆盖率。
- 关键业务路径覆盖情况。
- 未覆盖的高风险逻辑。

不能只给出全仓库一个百分比。

# 6. 第四阶段：支付系统自动化测试

**支付测试属于最高优先级。**

所有支付测试必须使用模拟支付服务或官方沙箱。

不得为了测试而真实扣款。

## 6.1 支付创建测试

测试：

- 正常创建订单。
- 缺少用户 ID。
- 缺少金额。
- 非法金额。
- 零金额。
- 负金额。
- 超过金额上限。
- 非法币种。
- 无效支付渠道。
- 重复请求。
- 重复订单号。
- 已关闭订单。
- 已过期订单。

## 6.2 支付签名测试

测试：

- 正确签名。
- 错误签名。
- 签名缺失。
- 签名被篡改。
- 时间戳过期。
- Nonce 异常。
- 证书错误。
- 公钥错误。
- 商户号不匹配。
- AppID 不匹配。

必须验证非法请求不能触发订单状态变化或资金到账。

## 6.3 支付回调测试

必须覆盖：

| 场景 | 预期结果 |
|---|---|
| 正常支付回调 | 订单成功到账一次 |
| 重复回调 | 不重复到账 |
| 并发重复回调 | 只到账一次 |
| 错误签名 | 拒绝处理 |
| 金额不一致 | 拒绝处理 |
| 商户号错误 | 拒绝处理 |
| 订单不存在 | 不到账 |
| 订单已关闭 | 按业务规则拒绝或进入异常处理 |
| 订单已退款 | 不重复到账 |
| 伪造成功状态 | 不到账 |
| 数据库写入失败 | 可恢复 |
| 回调应答失败 | 重试不重复到账 |

## 6.4 支付幂等测试

重点测试：

- 相同通知重复提交。
- 相同订单不同请求并发提交。
- 相同交易号重复处理。
- 不同交易号绑定同一订单。
- 不同订单使用相同交易号。
- 服务重启后再次收到回调。

验证数据库约束、事务和幂等机制是否共同有效。

## 6.5 支付故障注入

必须模拟：

- 支付成功后数据库连接中断。
- 数据库提交失败。
- 回调处理超时。
- 网络中断。
- 支付渠道响应超时。
- 支付渠道重复通知。
- 订单状态更新失败。
- 余额更新失败。
- 充值流水写入失败。
- 对账任务执行失败。

重点验证支付成功但系统未到账的恢复机制。

## 6.6 退款测试

测试：

- 正常退款。
- 重复退款请求。
- 超额退款。
- 部分退款。
- 退款失败。
- 退款回调。
- 退款回调重复。
- 退款与充值并发。
- 退款状态与订单状态一致性。

## 6.7 支付账本一致性

测试：

- 余额增加是否准确。
- 充值流水是否唯一。
- 订单金额与到账金额是否一致。
- 赠送余额是否单独记录。
- 退款是否正确冲减。
- 并发充值是否丢失更新。
- 重复回调是否重复增加余额。

每个场景都必须检查数据库最终状态，而不是只检查 API 返回值。

# 8. 第六阶段：AI Relay 与 Token 计费测试

## 8.1 请求转发

测试：

- 正常模型请求。
- 不存在的模型。
- 不可用供应商。
- 无效 API Key。
- 上游返回 4xx。
- 上游返回 5xx。

- 网络断开。
- 客户端取消。
- 请求体非法。
- 超大请求体。
- 并发请求。
- 模型映射错误。

## 8.2 流式响应

测试：

- 正常 SSE。
- 正常结束标志。
- 流式中断。
- 客户端断开。
- 上游中断。
- Usage 最终数据缺失。
- Usage 最终数据完整。
- 重复结束事件。
- 错误事件。
- 长时间无响应。

## 8.3 Token 计量

测试：

- Input Tokens。
- Output Tokens。
- Cached Input Tokens。
- Reasoning Tokens。
- Image Tokens。
- Audio Tokens。
- Tool Calls。
- 不同模型的 Usage 格式。
- 缺失 Usage。
- Usage 为零。
- 非法 Usage。
- 超大 Usage。
- 流式 Usage。

验证不同计费项目不会重复计算。

## 8.4 价格计算

测试：

- 正常输入价格。
- 正常输出价格。
- 缓存价格。
- 模型倍率。
- 用户倍率。
- 不同供应商价格。
- 价格变更。
- 历史订单价格。
- 小数精度。
- 极大金额。
- 极小金额。
- 余额不足。

## 8.5 扣费一致性

测试：

- 请求成功后正常扣费。
- 请求失败不错误扣费。
- 流式中断按业务规则计费。
- 重试不会重复扣费。
- 并发请求不会出现负余额。
- 预扣费和实际费用能够正确结算。
- 退款或补偿不会重复入账。

每项测试都应检查余额和账本最终结果。

# 13. 第十一阶段：安全测试与依赖扫描

## 13.1 Go 安全扫描

按实际工具可用性执行：

```bash
go vet ./...
govulncheck ./...
```

可补充：

- Staticcheck。
- Gosec。
- 其他适合 Go 项目的静态安全分析工具。

每个 Go Module 应单独检查。

## 13.2 前端依赖扫描

检查：

- npm audit。
- pnpm audit。
- Bun 对应的依赖审计能力。
- OSV Scanner。
- 其他适用的漏洞扫描工具。

# 15. 第十三阶段：自动修复机制

## 15.1 测试失败分类

每个失败必须判断属于：

1. 产品代码 Bug。
2. 测试用例错误。
3. 测试环境故障。
4. 外部依赖不可用。
5. 配置错误。
6. 数据准备错误。
7. 平台兼容性问题。

## 15.2 修复流程

发现产品代码 Bug 后：

1. 保存失败日志。
2. 确认复现条件。
3. 定位代码。
4. 分析根因。
5. 评估影响范围。
6. 修改代码。
7. 增加回归测试。
8. 重跑失败测试。
9. 执行关联模块测试。
10. 执行必要的完整测试。

## 15.3 禁止虚假修复

不允许：

- 删除失败测试。
- 降低测试断言。
- 将真实错误改为忽略。
- 使用 Skip 隐藏失败。
- 关闭安全检查。
- 关闭竞态检测。
- 将失败步骤设置为允许失败。
- 修改预期结果迁就错误实现。
- 用 Mock 掩盖本应测试的核心逻辑。
- 仅修改测试报告而不修改代码。

对于外部服务难以覆盖的场景，可以使用 Mock，但必须同时保留必要的真实协议、集成或沙箱验证。

## 15.4 修复记录

统一使用问题 ID：

`UTER-TEST-0001`

每项记录：

- 问题 ID。
- 失败测试。
- 失败命令。
- 原始日志。
- 复现条件。
- 根因。
- 修改文件。
- 修改内容。
- 新增测试。
- 回归结果。
- 剩余风险。

如果同一问题已在代码审查中登记，应复用对应问题 ID，并关联测试记录，避免重复统计。

## 15.5 修复次数与停止条件

对于无法立即修复的问题：

- 允许进一步定位和验证。
- 不得无限重复相同失败命令。
- 每次尝试必须有明确的诊断目的。
- 多次修复仍失败时，保留日志和现场。
- 涉及高风险架构调整时，可以先提交技术方案，等待明确决策。

不得为了完成任务而实施未经验证的重大重构。
