**适用对象：** AI Coding Agent、开发人员、代码审查人员  
**执行模式：** 全面审查 + 允许直接修改代码 + 修复验证  
**默认提交权限：** 遵循根 `AGENTS.md` 的用户授权；Uter 当前工程修复任务仅允许在唯一非 `main` 工作分支 Commit/Push/创建或更新 PR，不得创建第二分支、合并或部署

# 1. 项目目标与执行原则

## 1.1 项目目标

对 Uter 项目进行一次完整、系统、可追溯的代码审查，覆盖整个代码仓库，包括：

- Go 后端及所有独立 Go Module。
- 前端 Web 应用。
- Electron 桌面端。
- API 接口与鉴权系统。
- AI 模型中继及供应商管理。
- Token 计量、余额扣减及计费系统。
- 微信支付、支付宝支付及其他支付渠道。
- 数据库、缓存、任务队列及定时任务。
- 用户、管理员、权限与账户系统。
- CI/CD、部署配置及环境变量。
- 第三方依赖及软件供应链。
- 日志、监控、异常处理及安全机制。

本次任务不是只生成一份静态审查报告，而是要求：

1. 获取完整源码。
2. 固定审查基线。
3. 建立全仓库文件覆盖清单。
4. 实际逐项检查代码。
5. 识别潜在 Bug、安全漏洞和架构缺陷。
6. 对确认的问题直接修改代码。
7. 执行针对性测试和回归验证。
8. 形成完整审查报告及修复记录。

## 1.2 核心执行原则

### 原则 A：完整性

不得仅检查主要目录或入口文件。

必须识别所有源码目录、独立模块、服务、脚本、配置和测试文件。

不得因为代码量大而自动缩减审查范围。

### 原则 B：真实性

所有审查结论必须有真实代码证据。

必须区分：

- 已确认问题。
- 高概率问题。
- 潜在风险。
- 设计缺陷。
- 尚未验证的问题。

不得把推测描述成已经确认的 Bug。

### 原则 C：允许直接修复

发现明确的问题后，可以直接修改代码，不需要仅输出修复建议。

修复前应分析影响范围，尽量采用最小必要修改。

不得为了快速通过测试而删除测试、降低断言、绕过鉴权或屏蔽错误。

### 原则 D：可追溯

每个问题必须有唯一 ID。

每项修复必须记录：

- 问题 ID。
- 文件路径。
- 行号或代码符号。
- 原始问题。
- 根因。
- 修改内容。
- 修改理由。
- 修复前后行为差异。
- 测试证据。
- 遗留风险。

### 原则 E：安全边界

允许修改本地工作区代码，但未经明确授权：

- 不得 Commit。
- 不得 Push。
- 不得 Merge。
- 不得发布。
- 不得修改生产环境。
- 不得直接操作生产数据库。
- 不得擅自更换生产密钥、支付商户配置或域名配置。

# 2. 第一阶段：获取源码与固定审查基线

## 2.1 获取完整代码

首先检查当前工作区：

- Git 仓库是否完整。
- 是否存在未提交修改。
- 当前分支。
- 当前 Commit SHA。
- 是否存在子模块。
- 是否存在未初始化的 Git Submodule。
- 是否存在 Git LFS 文件。
- 是否存在多个独立 Go Module。
- 是否存在工作区外的本地依赖。

如果已经有本地仓库，优先使用现有仓库，不要重复克隆或覆盖用户修改。

如果通过 GitHub 获取源码，应确认仓库及分支的访问权限，并记录实际获取的 Commit SHA。

## 2.2 固定审查基线

审查开始时记录：

| 信息 | 要求 |
|---|---|
| Repository | 实际仓库地址 |
| Branch | 当前审查分支 |
| Commit SHA | 完整 SHA |
| Working Tree | clean / dirty |
| Go Version | 实际版本 |
| Node/Bun Version | 实际版本 |
| Package Manager | 实际使用的包管理器 |
| OS | 执行环境 |
| Start Time | 审查开始时间 |

审查期间不得静默切换基线。

如果审查期间代码发生变化，必须记录变化来源，并区分原始基线和后续修改。

## 2.3 保护用户现有修改

如果工作区存在用户尚未提交的修改：

1. 先检查修改内容。
2. 记录原始文件状态。
3. 不得覆盖用户已有改动。
4. 通过独立分支、独立 Worktree 或其他隔离方式实施修复。
5. 不得擅自清理工作区或执行破坏性 Git 命令。

建议优先使用独立 Git Worktree 进行修复。

# 3. 第二阶段：全仓库结构扫描

## 3.1 建立完整文件清单

扫描整个仓库，识别：

- 源代码。
- 测试代码。
- 配置文件。
- 数据库迁移。
- API 定义。
- 文档。
- 构建脚本。
- 部署文件。
- CI 配置。
- 第三方依赖。
- 自动生成代码。
- 示例代码。
- 开发工具脚本。

建立文件覆盖清单。

建议记录以下字段：

| 字段 | 说明 |
|---|---|
| File Path | 文件路径 |
| File Type | 文件类型 |
| Module | 所属模块 |
| Review Status | 待检查 / 已检查 / 已修复 / 已排除 |
| Risk Level | 风险等级 |
| Issue IDs | 关联问题 |
| Notes | 备注 |

## 3.2 识别项目模块

特别检查：

- 根目录。
- 后端服务。
- 每个 `go.mod` 所在目录。
- 前端应用。
- Electron 应用。
- 公共组件。
- 公共 SDK。
- 数据访问层。
- API 层。
- 任务系统。
- 支付模块。
- AI Relay 模块。
- 配置和部署模块。

每个独立 Go Module 必须单独审查和验证。

不能只在仓库根目录执行一次 `go test ./...`，然后认为所有 Go 模块均已覆盖。

## 3.3 文件覆盖要求

所有生产源码必须进入审查范围。

以下内容可以不进行逐行人工审查，但必须登记排除理由：

- 第三方依赖源码。
- 编译生成文件。
- 自动生成代码。
- 二进制文件。
- 纯资源文件。
- 与项目无关的历史归档。

对于生成代码，必须检查其生成工具、模板或源定义。

最终报告必须提供：

- 总文件数量。
- 已审查文件数量。
- 已修复文件数量。
- 排除文件数量。
- 未审查文件数量。
- 未审查原因。

不能把文件数量统计等同于审查质量。关键模块必须进行逻辑级审查。

# 4. 第三阶段：代码质量与架构审查

## 4.1 架构审查

检查：

- 模块职责是否清晰。
- 是否存在循环依赖。
- 是否存在重复业务逻辑。
- 是否存在不合理的跨层调用。
- 是否存在过度耦合。
- 是否存在不合理的全局状态。
- 是否存在错误的单例设计。
- 是否存在并发安全问题。
- 是否存在资源泄漏。
- 是否存在不可恢复的初始化失败。
- 是否存在服务关闭时的资源清理问题。

重点检查：

- HTTP Server 生命周期。
- 数据库连接池。
- Redis 连接。
- Goroutine 生命周期。
- Context 传递。
- 后台任务退出机制。
- 服务启动顺序。
- 优雅关闭。

## 4.2 Go 代码审查

所有 Go Module 均检查：

- 错误处理。
- Panic 使用。
- Context 超时与取消。
- Goroutine 泄漏。
- Data Race。
- Mutex 使用。
- Channel 阻塞。
- WaitGroup 使用。
- 空指针风险。
- 类型断言。
- 整数溢出。
- 并发 Map 访问。
- 资源关闭。
- 文件句柄泄漏。
- HTTP Client 超时。
- SQL 操作。
- 事务边界。
- 日志敏感信息。

检查是否存在：

- 忽略错误返回值。
- 错误被错误包装或吞掉。
- 使用 Background 导致请求取消失效。
- 无限制创建 Goroutine。
- 无限制重试。
- 不可控的并发任务。
- 使用不安全的全局变量。
- 缺少超时控制的网络请求。

## 4.3 前端代码审查

检查：

- React 组件生命周期。
- Hooks 使用。
- useEffect 依赖。
- 状态更新。
- 异步请求竞态。
- 内存泄漏。
- 路由权限。
- 页面刷新。
- 错误边界。
- 表单校验。
- 数据缓存。
- API 错误处理。
- Token 存储。
- XSS 风险。
- 不可信 HTML 渲染。
- 敏感数据暴露。

特别检查：

- 登录后页面状态是否正确。
- Token 过期后是否正确处理。
- 多标签页登录状态是否一致。
- 用户切换是否清除旧状态。
- 请求失败是否导致错误的成功提示。
- 页面重复请求和无限请求。
- 分页、筛选和排序的数据一致性。

## 4.4 Electron 审查

检查：

- Main / Renderer 进程边界。
- Context Isolation。
- Node Integration。
- Preload API。
- IPC 权限。
- 外部 URL 打开。
- 文件系统访问。
- 本地存储。
- 自动更新。
- 安装包签名。
- 敏感配置存储。
- Renderer 到 Main 的输入验证。

禁止不必要地向 Renderer 暴露 Node.js 或系统权限。

# 5. 第四阶段：账户、鉴权和权限安全审查

重点检查：

## 5.1 用户认证

- 注册。
- 登录。
- 登出。
- Token 签发。
- Token 刷新。
- Token 过期。
- Session 管理。
- 多设备登录。
- 账户冻结。
- 账户删除。
- 密码或验证码验证。
- 第三方身份认证。

## 5.2 授权机制

检查：

- RBAC。
- 用户角色。
- 管理员权限。
- API 权限。
- 资源所有权。
- 租户隔离。
- 跨用户数据访问。
- 越权操作。
- IDOR。
- 水平权限提升。
- 垂直权限提升。

不能仅依赖前端隐藏按钮实现权限控制。

所有敏感操作必须由后端进行权限校验。

## 5.3 Token 安全

检查：

- JWT 签名算法。
- Secret 管理。
- Token 有效期。
- Refresh Token 轮换。
- Token 撤销。
- Token 重放。
- Cookie 安全属性。
- CSRF 防护。
- XSS 造成的 Token 泄露。
- 日志中是否记录完整 Token。

# 6. 第五阶段：支付系统专项审查

**支付模块属于最高优先级审查范围。**

必须检查所有支付渠道及其公共订单逻辑。

## 6.1 支付渠道

逐项检查仓库中实际存在的支付实现：

- 微信支付。
- 支付宝支付。
- 易支付。
- 其他已接入渠道。

不得因为某个渠道没有独立目录就忽略其公共支付逻辑。

## 6.2 支付订单模型

重点检查：

- 订单创建。
- 订单号唯一性。
- 用户与订单绑定。
- 支付渠道绑定。
- 订单金额。
- 订单币种。
- 订单有效期。
- 订单状态。
- 支付状态。
- 退款状态。
- 订单关闭。
- 订单重复创建。
- 订单取消。
- 订单恢复。

必须确认订单状态机不存在非法状态转换。

建议明确：

- Pending。
- Paying。
- Paid。
- Failed。
- Closed。
- Refunding。
- Refunded。

实际状态应以代码中的业务设计为准，不得为迁就文档而盲目增加状态。

## 6.3 支付签名与回调

检查：

- 签名生成。
- 签名验证。
- 证书验证。
- 平台公钥验证。
- 回调来源验证。
- 时间戳验证。
- Nonce 验证。
- 金额校验。
- 商户号校验。
- AppID 校验。
- 订单号校验。
- 交易状态校验。
- 重复通知处理。
- 通知应答。

特别确认：

1. 不可信请求不能直接修改订单为 Paid。
2. 不能只凭前端跳转结果认定支付成功。
3. 不能仅凭订单号判断支付成功。
4. 必须验证真实交易金额和订单应付金额。
5. 必须验证交易归属及支付渠道。
6. 重复回调不得重复充值。
7. 伪造签名不能触发到账。
8. 退款通知不能错误地恢复充值余额。

## 6.4 支付与数据库一致性

重点检查：

- 支付成功但数据库写入失败。
- 数据库已到账但回调应答失败。
- 重复回调。
- 并发回调。
- 订单重复处理。
- 充值记录与余额不一致。
- 订单金额与充值金额不一致。
- 支付渠道交易号重复。
- 事务回滚。
- 事务提交失败。

特别检查是否存在：

**支付成功 → 数据库保存失败 → 系统无法自动恢复到账**

必须评估是否具备：

- 主动查单。
- 定时对账。
- 支付结果补偿。
- 幂等处理。
- 失败任务重试。
- 人工对账入口。
- 完整支付流水。

## 6.5 支付金额安全

必须检查：

- 金额精度。
- 浮点数运算。
- 分与元的换算。
- 币种处理。
- 最小充值金额。
- 最大充值金额。
- 优惠金额。
- 赠送金额。
- 实际到账金额。
- 退款金额。
- 订单金额篡改。

涉及资金的金额计算优先采用整数最小货币单位或可靠的定点数方案。

不得使用不可靠的浮点数直接处理资金。

## 6.6 充值账本与余额

检查：

- 余额增加。
- 余额扣减。
- 充值记录。
- 消费记录。
- 退款记录。
- 赠送余额。
- 冻结余额。
- 余额过期。
- 并发扣费。
- 负余额。
- 重复入账。

确认是否具备可追溯的账本机制。

对于余额变化，必须能够追踪：

- 原始余额。
- 变化金额。
- 变化后余额。
- 业务来源。
- 关联订单。
- 操作时间。
- 操作主体。

不能仅依靠直接更新用户余额而缺少对应流水。

## 6.7 支付回调跨域与域名

结合 Uter 实际部署结构，检查支付回调地址与业务域名的关系。

重点确认：

- 支付创建接口。
- 支付同步跳转 URL。
- 支付异步通知 URL。
- 回调域名。
- 回调路由。
- HTTPS。
- 反向代理。
- Host 校验。
- 域名配置。
- 回调处理服务。

如果涉及 `uter.cc` 与 `uter.ai`，必须明确两个域名分别承担的角色，并验证支付结果通过后端可靠传递。

不得依赖用户浏览器跳转传递可信支付结果。

# 7. 第六阶段：AI Relay 与 Token 计费审查

这是 Uter 的核心业务模块。

## 7.1 模型中继

检查：

- 上游供应商。
- 模型映射。
- 模型别名。
- API Key。
- 请求转发。
- 请求协议兼容。
- 流式响应。
- 非流式响应。
- 超时。
- 重试。
- 供应商故障切换。
- 错误转换。
- 上游限流。
- 并发控制。

重点检查：

- 上游返回失败但用户被扣费。
- 上游成功但系统未计费。
- 流式响应中途断开。
- 客户端取消请求。
- 上游请求超时。
- 重试导致重复请求。
- 不同模型使用错误价格。
- 请求与响应模型映射错误。

## 7.2 Token 计量

检查：

- Input Tokens。
- Output Tokens。
- Cached Input Tokens。
- Reasoning Tokens。
- Image Tokens。
- Audio Tokens。
- Video Tokens。
- Tool Calls。
- 模型特定计费项目。

不能假定所有模型都使用相同计费规则。

必须检查供应商返回的 Usage 是否被正确解析。

特别关注：

- 流式响应最终 Usage。
- 非流式响应 Usage。
- 缺失 Usage。
- Usage 为零。
- Usage 字段兼容性。
- Cached Tokens 重复计算。
- 输入输出 Token 计量错误。

## 7.3 价格体系

检查：

- 上游成本。
- 用户售价。
- 模型倍率。
- 输入价格。
- 输出价格。
- 缓存价格。
- 供应商差异。
- 用户等级。
- 价格配置更新。
- 历史订单价格快照。

必须确认价格变更不会错误地影响已经创建或已经完成的交易。

## 7.4 扣费安全

检查：

- 预扣费。
- 实际计费。
- 余额不足。
- 并发扣费。
- 失败退款。
- 部分响应计费。
- 重试计费。
- 流式中断计费。
- 计费补偿。
- 账本一致性。

必须保证同一业务请求不会因重复处理而重复扣费。

# 8. 第七阶段：数据库、缓存和任务系统审查

## 8.1 数据库

检查：

- Schema。

# 11. 第十阶段：问题分级与修复机制

## 11.1 严重程度

| 级别 | 定义 | 处理要求 |
|---|---|---|
| P0 Critical | 资金损失、严重数据泄露、远程代码执行、核心系统完全失效 | 立即处理 |
| P1 High | 支付绕过、越权、重复扣费、严重数据不一致 | 优先修复 |
| P2 Medium | 核心功能 Bug、稳定性、性能和可靠性问题 | 本次审查中修复 |
| P3 Low | 一般逻辑、边界条件、维护性问题 | 评估后修复 |
| P4 Info | 优化建议、非直接缺陷 | 记录建议 |

另外标注：

- Security。
- Financial。
- Data Integrity。
- Availability。
- Performance。
- Maintainability。

## 11.2 问题 ID

统一格式：

`UTER-CR-0001`

例如：

- UTER-CR-0001：支付回调缺少金额校验。
- UTER-CR-0002：充值处理缺少幂等保护。
- UTER-CR-0003：AI 流式请求中断后扣费异常。

问题 ID 不得重复。

## 11.3 直接修复流程

每个确认问题按以下流程处理：

1. 定位问题代码。
2. 获取完整上下文。
3. 分析根因。
4. 确认影响范围。
5. 设计最小修复方案。
6. 修改代码。
7. 增加或完善测试。
8. 执行针对性测试。
9. 执行必要的回归测试。
10. 检查是否引入新的问题。
11. 记录修复证据。

不得只修改表面症状而不处理根因。

## 11.4 修复风险控制

以下情况必须先进行影响评估，必要时暂缓直接修改：

- 数据库不可逆迁移。
- 生产数据结构变化。
- 支付协议兼容性变化。
- 账户体系迁移。
- 余额账本重构。
- 影响历史数据的批量操作。
- 可能导致现有用户无法登录的修改。

可以先在隔离环境中实现和验证，不得直接对生产数据执行。

如果修复需要真实商户、第三方账号或生产环境才能验证，应标记为待验证，不得伪造通过结果。
