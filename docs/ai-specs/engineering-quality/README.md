# Uter Engineering Quality Engine
## 统一工程质量管理与自动化执行系统实施规范

**项目名称：** Uter  
**系统名称：** Uter Engineering Quality Engine（UEQE）  
**实施性质：** 全仓库工程质量体系建设  
**执行方式：** WorkBuddy 自动检查、设计、实施、测试、修复及验证  
**目标架构：** 双质量引擎 + 自动修复引擎 + 统一调度与质量门禁

---

# 第一部分：项目目标与实施原则

## 1.1 项目目标

在 Uter 项目中建立一套完整、可持续运行的自动化工程质量管理系统。

系统必须具备以下能力：

1. 自动识别和维护整个 Uter 仓库的工程结构。
2. 自动执行全仓库代码审查。
3. 自动执行全仓库自动化测试。
4. 自动执行安全扫描、依赖检查和代码质量检查。
5. 自动识别缺陷并进行风险分级。
6. 对允许自动修复的问题，由 AI 自动分析和修复。
7. 自动为修复内容补充测试。
8. 自动执行修复后的相关测试及回归测试。
9. 修复验证完成后，复用项目唯一非 main 工作分支 Commit、Push，并创建或更新该分支现有 Pull Request；禁止创建第二分支。
10. 自动生成完整的审查报告、测试报告、修复报告及质量汇总报告。
11. 支持 GitHub Actions 自动触发、定时审计及人工触发。
12. 能够随着 Uter 代码结构和业务模块变化持续扩展。

最终形成完整的工程质量闭环：

**代码变更 → 自动审查 → 自动测试 → 缺陷识别 → AI 自动修复 → 修复验证 → 唯一工作分支 → Commit → Push → Pull Request → 人工审核 → 人工合并。**

不得将其实现为几个互不关联的脚本，也不得只建立文档而不实现实际执行能力。

## 1.2 总体架构

建立统一的 Uter Engineering Quality Engine，内部由五个核心部分组成：

### A. Quality Orchestrator

统一调度中心，负责：

- 获取 Git 仓库状态。
- 确定本次执行的 Commit SHA。
- 识别代码变更范围。
- 读取项目模块清单。
- 调用 Code Review Engine。
- 调用 Testing Engine。
- 根据审查结果调用 Auto-Fix Engine。
- 调用 Quality Gate。
- 生成统一报告。
- 记录执行状态及历史结果。

### B. Code Review Engine

独立代码审查引擎，负责：

- 静态代码审查。
- 业务逻辑审查。
- 架构合理性审查。
- 安全审查。
- 数据库一致性审查。
- 支付与资金安全审查。
- AI Relay 与 Token 计费审查。
- 前端和交互逻辑审查。
- 并发、性能及稳定性审查。
- 第三方依赖及供应链审查。

### C. Testing Engine

独立自动化测试引擎，负责：

- 单元测试。
- 集成测试。
- API 测试。
- 数据库测试。
- 支付回调测试。
- AI Relay 测试。
- Token 计费测试。
- 前端组件测试。
- E2E 测试。
- 回归测试。
- 并发及压力测试。
- 测试覆盖率统计。

### D. Auto-Fix Engine

AI 自动修复引擎，负责：

- 接收已确认的缺陷。
- 分析缺陷根因。
- 制定修复方案。
- 在隔离工作区执行修复。
- 增加或更新测试。
- 执行修复验证。
- 执行相关回归。
- 生成修复报告。
- 复用项目唯一非 `main` 工作分支；禁止创建第二分支。
- Commit、Push。
- 自动创建 Pull Request。

### E. Quality Gate

统一质量门禁，负责：

- 汇总代码审查结果。
- 汇总自动测试结果。
- 汇总安全扫描结果。
- 检查覆盖率。
- 检查修复状态。
- 检查是否存在阻断性缺陷。
- 决定是否允许创建 PR。
- 为 PR 提供完整的质量证据。

**重要：** Code Review Engine 与 Testing Engine 必须保持规则、执行记录和报告的独立性，但共享模块清单、缺陷编号、风险等级及质量门禁。

# 第二部分：实施前的仓库审计

## 2.1 首先检查真实仓库

在修改任何文件之前，必须先完整检查当前 Uter 仓库。

不得假设仓库结构、编程语言、模块数量、测试框架或 CI 配置。

检查范围：

- Git 根目录。
- 当前分支。
- 当前 Commit SHA。
- 工作区是否干净。
- 是否存在未提交修改。
- 是否存在未跟踪文件。
- 是否存在 Git 子模块。
- 所有 Go Module。
- Go Workspace。
- Web 前端。
- Electron 项目。
- 移动端项目（如果仓库实际存在）。
- 数据库迁移。
- API 定义。
- 支付模块。
- AI Relay 模块。
- Token 计费模块。
- 任务调度模块。
- 认证及授权模块。
- 缓存及消息系统。
- GitHub Actions。
- Docker、部署及基础设施配置。
- 现有测试、测试工具及覆盖率配置。
- 现有工程规范和 Agent 指令文件。

需要特别检查：

- AGENTS.md
- README.md
- go.mod
- go.work
- package.json
- pnpm-workspace.yaml
- turbo.json
- .github/workflows/
- Dockerfile
- docker-compose.yml
- Makefile
- 现有 CI 配置
- 现有代码审查及测试规范

只检查实际存在的文件，不得为了匹配上述清单而凭空创建无意义的模块。

## 2.2 固定审查基线

每次完整执行必须固定一个 Commit SHA。

报告至少记录：

- Repository。
- Commit SHA。
- Branch。
- Execution ID。
- 执行时间。
- 执行环境。
- Go 版本。
- Node.js 版本。
- 包管理器及版本。
- 操作系统。
- 已识别模块。
- 工作区状态。

审查期间代码版本不得发生变化。

如发现基线之后出现新的代码变更，应结束当前执行并重新建立基线，不能混合不同 Commit 的测试结果。

## 2.3 保护现有工作区

必须遵循：

1. 不覆盖用户已有的未提交修改。
2. 不执行 git reset --hard。
3. 不执行 git clean -fd。
4. 不删除用户已有分支。
5. 不擅自修改现有 Git 配置。
6. 不覆盖已有工作流和工程规范。
7. 不修改生产环境配置。
8. 不读取、打印或提交真实密钥。
9. 不在主分支直接进行自动修复。

如果当前工作区不干净，先记录变更并采用独立 Git Worktree 或其他隔离方式实施。

无法安全隔离时，停止可能破坏工作区的操作并报告。

## 3.2 根目录 AGENTS.md

创建或更新根目录 AGENTS.md。

AGENTS.md 是 AI Coding Agent 的工程执行入口。

必须明确要求：

1. 开始任务前读取工程规范。
2. 先检查真实仓库结构。
3. 不允许假设不存在的模块。
4. 修改前确认 Git 基线。
5. 不覆盖用户已有修改。
6. 修复必须附带测试。
7. 不允许以测试通过代替代码审查。
8. 不允许以代码审查通过代替测试。
9. 所有缺陷必须有证据。
10. 所有修复必须有验证记录。
11. 不允许虚构测试结果。
12. 不允许将未执行的测试标记为通过。
13. 未经授权不得合并或部署。

# 第四部分：Code Review Engine

## 4.1 核心能力

Code Review Engine 必须能够进行两类审查：

**第一类：确定性审查**

使用静态分析、编译检查、Lint、依赖扫描、漏洞扫描及规则检查。

**第二类：AI 深度审查**

使用 AI 分析业务逻辑、架构、状态流转、边界条件及跨模块问题。

不能仅依赖 AI 阅读代码，也不能仅依赖静态扫描。

## 4.2 全仓库审查范围

### A. 架构与模块

- 模块职责是否清晰。
- 是否存在循环依赖。
- 是否存在重复实现。
- 是否存在不合理耦合。
- 是否存在无效代码。
- 是否存在隐藏的全局状态。
- 模块之间的接口是否稳定。
- 错误处理是否统一。
- 日志和异常处理是否合理。

### B. 身份认证与权限

重点检查：

- 登录流程。
- 注册及账号创建。
- OTP 验证。
- Token 生成与刷新。
- Session 生命周期。
- 权限校验。
- 用户身份一致性。
- API 越权。
- IDOR。
- 重放攻击。
- 认证绕过。
- 敏感信息泄露。
- Webhook 身份验证。

### C. 支付系统

作为最高优先级审查区域。

覆盖实际存在的：

- 微信支付。
- 支付宝支付。
- 易支付。
- 其他支付渠道。

重点检查：

1. 签名生成和验签。
2. 支付金额校验。
3. 币种校验。
4. 商户身份校验。
5. 订单状态机。
6. 重复回调。
7. 并发回调。
8. 重复入账。
9. 回调伪造。
10. 回调重放。
11. 异步通知处理。
12. 同步跳转处理。
13. 主动查询。
14. 订单超时。
15. 退款流程。
16. 退款状态同步。
17. 数据库事务。
18. 支付成功但数据库写入失败。
19. 数据库成功但回调响应失败。
20. 多实例并发。
21. 订单与余额一致性。
22. 支付金额与实际到账金额一致性。
23. 日志及敏感字段保护。

必须检查支付流程的完整状态机，不能只检查某个支付接口。

### D. 余额及 Token 计费

重点检查：

- 余额计算。
- Token 用量统计。
- 输入 Token。
- 输出 Token。
- Cached Token。
- 不同模型的价格。
- 模型价格同步。
- 预扣费。
- 实际扣费。
- 余额返还。
- 请求失败退款。
- 并发扣费。
- 幂等性。
- 负余额。
- 精度及舍入。
- 计费记录与请求记录一致性。
- 账单可追溯性。

涉及金额的计算不得使用不可靠的浮点运算方式。

### E. AI Relay

重点检查：

- 上游渠道选择。
- API Key 管理。
- 请求转发。
- 模型映射。
- 上游错误处理。
- 流式响应。
- 超时。
- 重试。
- 熔断。
- 限流。
- 并发控制。
- 渠道切换。
- 价格同步。
- 缓存更新。
- 多实例一致性。
- 日志脱敏。
- 用户与渠道隔离。

### F. 数据库

重点检查：

- SQL 注入。
- 事务边界。
- 索引。
- 唯一约束。
- 外键及关联一致性。
- 数据竞争。
- 并发写入。
- 锁。
- 死锁。
- 迁移兼容性。
- 数据丢失。
- 重复数据。
- 软删除。
- 分页性能。

### G. 任务系统

重点检查：

- 任务创建。
- 任务状态。
- 任务调度。
- 重复执行。
- 任务超时。
- 任务取消。
- 失败重试。
- 并发执行。
- 死锁。
- 任务恢复。
- 多实例调度一致性。

### H. Web 前端

重点检查：

- 路由。
- 登录状态。
- 权限。
- 页面状态。
- 数据请求。
- 错误处理。
- 加载状态。
- 表单校验。
- XSS。
- CSRF。
- SSR/CSR 一致性（如果存在）。
- 内存泄漏。
- 无效重渲染。
- 可访问性。
- 响应式布局。

### I. Electron（如果存在）

重点检查：

- 主进程和渲染进程隔离。
- IPC 权限。
- preload。
- Node.js 权限暴露。
- 外部链接。
- 本地文件访问。
- 自动更新。
- 安装包安全。
- 签名及构建配置。

### J. 第三方依赖与供应链

重点检查：

- 依赖漏洞。
- 恶意依赖。
- 过期依赖。
- 依赖混淆风险。
- 锁文件一致性。
- 依赖来源。
- 许可证风险。
- GitHub Actions 第三方 Action 固定版本。
- CI 密钥暴露。
- 构建脚本安全。

## 4.3 缺陷分级

统一使用以下等级：

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 严重资金损失、重大安全漏洞、数据破坏或系统级事故 | 立即告警，暂停自动修复和 PR 自动发布，人工决策 |
| P1 | 高危安全问题、支付错误、余额错误、关键业务不可用 | 隔离修复，充分回归，必须人工审核 |
| P2 | 重要功能错误、明显业务逻辑缺陷、较高性能风险 | 可以自动修复和创建 PR，正常人工审核 |
| P3 | 一般缺陷、兼容性、体验及可维护性问题 | 可自动修复并创建 PR |
| P4 | 优化建议、低风险技术债 | 记录并按需处理 |

风险分级不能仅由 AI 自行决定。应结合影响范围、可利用性、资金影响、数据影响和可恢复性进行判断。

## 4.4 审查结果要求

每个问题必须提供：

- Issue ID。
- 严重等级。
- 文件路径。
- 行号或代码范围。
- 问题描述。
- 根因。
- 触发条件。
- 影响范围。
- 风险分析。
- 复现步骤。
- 证据。
- 修复建议。
- 是否允许自动修复。
- 对应测试要求。

无法确认的问题必须标记为待验证，不得作为已确认 Bug。

# 第五部分：Testing Engine

## 5.1 测试目标

Testing Engine 必须验证：

- 现有功能是否正常。
- 业务逻辑是否符合预期。
- 修复是否真正解决问题。
- 是否引入新的缺陷。
- 不同模块之间是否保持一致性。
- 高风险业务在异常情况下是否安全。

测试必须实际执行。

不能仅生成测试代码、测试计划或测试命令就宣称测试完成。

## 5.2 测试层级

### Level 1：静态检查

- 编译。
- 类型检查。
- Lint。
- 格式检查。
- 静态分析。
- 依赖漏洞扫描。
- Secret 扫描。

### Level 2：单元测试

覆盖：

- 核心业务函数。
- 计费逻辑。
- 金额计算。
- 订单状态。
- 权限验证。
- 模型映射。
- 请求处理。
- 错误处理。
- 边界条件。

### Level 3：集成测试

覆盖：

- API 与数据库。
- 认证与业务模块。
- 支付与订单。
- 订单与余额。
- AI Relay 与计费。
- 任务系统与数据库。
- 缓存与数据库。

### Level 4：端到端测试

根据实际技术栈和环境覆盖：

- 注册与登录。
- 用户账户。
- API Key。
- 模型调用。
- Token 消耗。
- 余额扣除。
- 充值。
- 支付回调。
- 账单查询。
- 任务流程。
- Web 前端关键路径。

### Level 5：异常与边界测试

重点覆盖：

- 空值。
- 非法参数。
- 超时。
- 网络中断。
- 重复请求。
- 重复回调。
- 并发写入。
- 数据库失败。
- 上游服务异常。
- 缓存失效。
- 部分成功。
- 部分失败。
- 任务中断。
- 重试。

### Level 6：并发及压力测试

针对实际关键模块设计：

- 并发登录。
- 并发扣费。
- 并发支付回调。
- 并发 API 请求。
- 上游切换。
- 任务并发。
- 数据库连接压力。
- 缓存压力。

压测应在隔离环境进行，不得对生产服务实施未经授权的压力测试。

## 5.3 支付专项测试

必须设计以下测试：

1. 正常支付成功。
2. 支付失败。
3. 支付超时。
4. 重复支付通知。
5. 并发支付通知。
6. 伪造签名。
7. 错误金额。
8. 错误订单号。
9. 错误商户号。
10. 订单已关闭。
11. 订单已退款。
12. 支付成功但数据库写入失败。
13. 数据库提交成功但通知响应失败。
14. 主动查询与异步回调同时到达。
15. 多实例处理同一个订单。
16. 退款通知重复到达。

必须验证最终余额只入账一次。

测试必须使用模拟渠道、沙箱或隔离测试环境，禁止通过真实支付产生未经授权的交易。

## 5.4 Token 计费专项测试

必须测试：

- 不同模型的价格。
- 输入与输出 Token。
- Cached Token。
- 零 Token。
- 极大 Token。
- 缺少用量字段。
- 上游返回异常用量。
- 预扣费。
- 实际扣费。
- 失败返还。
- 重试。
- 并发扣费。
- 重复结算。
- 价格变更。
- 历史账单一致性。

## 5.5 测试覆盖率

必须统计：

- 全仓库覆盖率。
- 各 Go Module 覆盖率。
- 核心业务模块覆盖率。
- 关键资金路径覆盖率。
- 前端核心模块覆盖率（适用时）。

覆盖率不能作为唯一质量指标。

不得通过排除关键文件、删除测试、降低断言或制造无意义测试来提高覆盖率。

对于已有覆盖率基线，优先保持或提高。

对于新增核心业务代码，必须提供有意义的测试。

没有覆盖率数据时，应明确报告 BLOCKED 或 NOT AVAILABLE，不得虚构百分比。

## 5.6 测试结果状态

统一使用：

- PASS：实际执行并通过。
- FAIL：实际执行但失败。
- BLOCKED：因环境、权限或依赖条件无法执行。
- SKIPPED：按明确规则跳过。
- NOT RUN：尚未执行。
- NOT APPLICABLE：经确认不适用。

每项测试必须记录命令、环境、耗时、结果和日志位置。

# 第六部分：Auto-Fix Engine

## 6.1 自动修复目标

建立 AI 自动修复闭环：

```text
发现缺陷
    ↓
确认问题
    ↓
分析根因
    ↓
制定修复方案
    ↓
建立隔离工作区
    ↓
修改代码
    ↓
增加或更新测试
    ↓
执行测试
    ↓
执行回归
    ↓
重新代码审查
    ↓
通过质量门禁
    ↓
Commit
    ↓
Push
    ↓
创建 Pull Request
```

## 6.2 自动修复原则

1. 先确认问题，再修改代码。
2. 不允许为了让测试通过而随意改变业务规则。
3. 不允许通过删除测试解决失败。
4. 不允许通过忽略错误掩盖问题。
5. 不允许修改无关代码。
6. 不允许无理由升级大量依赖。
7. 不允许修改生产密钥。
8. 不允许修改真实支付配置。
9. 不允许直接操作生产数据库。
10. 不允许在主分支直接修复。
11. 每项修复必须有对应测试。
12. 修复完成必须重新执行代码审查。

## 6.3 自动修复权限

用户已明确授权：

- 复用项目唯一非 `main` 工作分支；禁止创建第二分支。
- 在隔离环境中修改代码。
- 自动新增测试。
- 自动执行验证。
- 自动 Commit。
- 自动 Push。
- 自动创建 Pull Request。

用户未授权：

- 自动合并 Pull Request。
- 自动部署。
- 修改生产环境。
- 修改生产数据库。
- 修改真实支付商户配置。
- 修改真实密钥及生产凭证。

## 6.4 自动修复风险规则

| 风险等级 | 自动修复 | Commit/Push/PR | 后续要求 |
|---|---|---|---|
| P0 | 停止自动修复 | 不允许自动发布 | 立即人工决策 |
| P1 | 隔离环境允许修复 | 经专项验证后允许创建 PR | 必须人工审核 |
| P2 | 允许 | 允许 | 正常人工审核 |
| P3 | 允许 | 允许 | 正常人工审核 |
| P4 | 按需允许 | 允许 | 可批量整理 |

P1 必须设置额外保护：

- 不得自动合并。
- 必须人工审核。
- 不得将未通过验证的修复推送为可合并 PR。
- 如果只能生成补丁而无法验证，必须明确标记为待验证，不得冒充通过。

## 6.5 唯一工作分支规则（强制）

Uter 每个项目最多允许一个非 `main` 工作分支。所有问题均在该分支中按 Issue ID、Commit 和审计报告分别追踪，不通过创建多个分支隔离问题。

要求：

- 开始前枚举远端分支并检查现有 PR。
- 已存在唯一非 `main` 工作分支时必须复用，禁止创建第二分支。
- 不存在工作分支时，先取得用户明确授权再创建唯一工作分支。
- 若发现多个非 `main` 分支，停止推送和分支操作，报告并等待用户确定保留分支；不得自行删除或重写。
- 不得直接推送 `main`、force push、覆盖用户未提交修改或删除他人分支。
- 推送前检查远端 head SHA、工作区状态、暂存文件和变更范围。
- PR 应复用该唯一工作分支的现有 PR；创建前先检查是否已存在，避免重复 PR。

## 6.6 Commit 规范

使用清晰的 Conventional Commits 风格。

例如：

```text
fix(payment): prevent duplicate balance credit
fix(auth): validate session refresh state
fix(billing): correct token usage calculation
test(payment): add concurrent callback regression tests
```

一个 Commit 应尽量只处理一个明确的问题。

Commit 信息必须能对应 Issue ID 或缺陷编号。

## 6.7 Pull Request 规范

自动创建的 PR 必须包含：

### 标题

```text
[AI Fix][P2] Prevent duplicate payment credit
```

### 内容

```markdown
## Summary
修复内容概述。

## Related Issues
关联缺陷编号。

## Root Cause
问题根因。

## Changes
修改文件及具体内容。

## Tests
新增测试和实际执行结果。

## Regression
回归测试结果。

## Security Impact
安全影响。

## Risk Assessment
风险等级及影响范围。

## Remaining Risks
尚未解决的问题。

## Quality Gate
Code Review: PASS/FAIL
Automated Tests: PASS/FAIL
Security Scan: PASS/FAIL
Regression: PASS/FAIL

## AI Execution
Execution ID:
Base Commit SHA:
Fix Branch:
Commit SHA:
```

必须提供可核验的执行证据。

如果现有工作流已经承担相同职责，应优先整合，避免重复运行。

## 8.2 quality-check.yml

负责：

- PR 触发。

- 立即生成告警。

如果发现 P1：

- 生成高优先级问题报告。

- 未修复漏洞。
- 依赖风险。
- 密钥风险。
- 权限风险。
- 安全趋势。

## 8.7 GitHub 权限

采用最小权限原则。

默认只授予必要权限：

- contents: read
- pull-requests: read
- checks: write（确有需要时）
- issues: write（确有需要时）
- contents: write（仅修复发布任务）
- pull-requests: write（仅 PR 创建任务）

不要将所有权限授予每个 Workflow。

特别要求：

1. AI 自动修复任务与普通 CI 分离。
2. 不可信外部 PR 不得访问 Secrets。
3. 不得将生产凭证暴露给 AI。
4. 不得将 PAT 明文写入脚本。
5. 优先使用 GitHub App 或短期凭证。
6. 对第三方 GitHub Actions 固定到完整 Commit SHA。
7. 限制 Token 的有效期、仓库范围和权限。
8. 不允许普通 PR 工作流获得主分支写权限。

GitHub Actions 的权限必须根据实际执行操作配置，不能为了方便统一赋予 write 权限。

# 第十部分：统一质量门禁

## 10.1 通过条件

正常情况下，必须同时满足：

1. 代码审查已完成。
2. 没有未处理的 P0。
3. 没有未获人工批准的 P1。
4. 必需的自动化测试通过。
5. 关键资金路径测试通过。
6. 安全扫描没有未处理的阻断性问题。
7. 修复内容已经重新审查。
8. 没有未记录的失败项。
9. 所有 BLOCKED、SKIPPED 项均有原因。
10. 测试证据可以追溯。

注意：允许创建用于人工审核的 P1 修复 PR，但不得将其标记为可自动合并或质量完全通过。

## 10.2 两种通过状态

必须严格区分：

**Review Passed**

代表在当前审查范围和基线下，没有发现阻断性代码问题。

不代表代码绝对没有缺陷。

**Tests Passed**

代表当前实际执行的必需测试通过。

不代表未覆盖路径没有缺陷。

只有两者及其他必需安全门禁都满足，才能标记为：

**Quality Gate Passed**

## 10.3 失败处理

发生以下情况时，不允许自动创建宣称验证通过的修复 PR：

- 必需测试失败。
- 关键支付测试失败。
- 关键余额一致性测试失败。
- 安全扫描发现阻断性风险。
- 修复导致其他模块回归失败。
- 基线发生变化。
- 修复工作区与用户修改发生冲突。
- 无法确认修复效果。

可以生成诊断报告和补丁供人工处理，但必须准确标记状态。

# 第十一部分：安全与执行隔离

## 11.1 执行环境

推荐采用：

- GitHub Actions Runner：常规 CI。
- 独立 Runner / 容器：深度测试和自动修复。
- Git Worktree：修复隔离。
- 独立测试数据库：集成测试。
- Mock / Sandbox：支付和第三方服务测试。

不同任务之间必须隔离文件、环境变量和权限。

## 11.2 Secrets

严禁：

- 将 API Key 写入代码。
- 将数据库密码写入测试报告。
- 将支付密钥输出到日志。
- 将生产密钥传递给 AI。
- 将 Secrets 放进 PR 描述。
- 将密钥提交到修复分支。

自动化应使用专门的低权限测试凭证。

## 11.3 测试数据

测试必须使用：

- 独立测试数据库。
- 虚拟用户。
- 虚拟订单。
- 模拟支付结果。
- 测试 API Key。
- 可清理的测试数据。

不得使用真实用户资金和真实生产数据作为自动测试数据。

## 11.4 外部服务限制

无法访问的外部服务不得伪造测试结果。

应标记：

BLOCKED：缺少测试环境、权限或依赖。

并说明恢复测试需要什么条件。

- 可以按模块输出结果。

验收：

- 测试结果可追溯。
- 失败项可以定位。

验收：

- 原始问题得到解决。
- 新增测试能够验证问题。
- 原有测试没有回归。
