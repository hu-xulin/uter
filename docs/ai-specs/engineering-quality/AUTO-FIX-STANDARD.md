# Uter AI Auto-Fix Standard
## AI 自动代码修复与 Pull Request 管理规范

**项目：** Uter  
**规范编号：** UTER-ENG-003  
**版本：** 1.0  
**适用范围：** Uter 全部代码仓库、工程模块及自动化修复流程  
**执行主体：** AI Coding Agent、Auto-Fix Engine、GitHub Actions  
**关联规范：**
- CODE-REVIEW-STANDARD.md
- AUTOMATED-TEST-STANDARD.md
- QUALITY-GATE-STANDARD.md

---

# 1. 规范目标

## 1.1 核心目标

建立一套安全、可控、可追溯的 AI 自动代码修复机制，使 Uter 能够自动完成：

1. 接收代码审查发现的缺陷。
2. 确认缺陷是否真实存在。
3. 分析问题根因。
4. 制定修复方案。
5. 创建隔离修复环境。
6. 自动修改代码。
7. 自动增加或更新测试。
8. 执行相关测试和回归测试。
9. 重新执行代码审查。
10. 通过质量门禁。
11. 复用项目现有的唯一非 main 工作分支；禁止创建第二分支。
12. 自动 Commit。
13. 自动 Push。
14. 自动创建 GitHub Pull Request。
15. 生成完整修复报告。

最终实现：

**Issue Detection → Root Cause Analysis → Code Fix → Test → Regression → Re-Review → Quality Gate → Commit → Push → Pull Request**

## 1.2 基本原则

AI 自动修复必须遵循：

- 正确性优先于修复速度。
- 业务安全优先于代码简洁。
- 最小修改优先于大规模重构。
- 测试证据优先于 AI 自我判断。
- 隔离执行优先于直接修改主工作区。
- 可回滚优先于不可逆操作。
- 不确定时停止，不得猜测性修改。
- 不允许通过删除测试或降低检查标准掩盖问题。

# 2. 自动修复适用范围

## 2.1 允许自动修复的问题

在完成缺陷确认及风险评估后，可以自动处理：

### 代码质量问题
- 明确的逻辑错误。
- 空指针及异常处理问题。
- 边界条件错误。
- 资源未释放。
- 内存泄漏。
- 并发安全问题。
- 重复代码。
- 无效代码。
- 类型错误。
- 明确的性能问题。

### API 和业务逻辑
- 参数校验遗漏。
- 状态流转错误。
- 错误码不一致。
- 数据格式处理错误。
- 接口返回不符合既定契约。
- 明确的业务条件判断错误。

### 数据库
- SQL 查询错误。
- 缺少必要索引的明确问题。
- 事务边界错误。
- 数据竞争。
- 查询性能问题。
- 数据一致性问题。

涉及破坏性数据迁移时，必须额外审批。

### 认证与权限
- 权限检查遗漏。
- Session 校验错误。
- Token 生命周期处理错误。
- 明确的认证逻辑缺陷。
- 权限边界错误。

### 支付与计费
- 签名验证逻辑错误。
- 重复回调处理错误。
- 幂等性缺陷。
- 金额精度错误。
- 余额计算错误。
- Token 计费错误。
- 退款状态流转错误。

支付、余额及计费修复属于高风险领域，必须执行专项测试和额外审查。

### 前端
- 页面状态错误。
- 表单校验错误。
- API 调用错误。
- 权限展示错误。
- 页面崩溃。
- 内存泄漏。
- 明确的交互缺陷。

### 工程配置
- Lint 配置错误。
- 测试脚本错误。
- CI 配置错误。
- 依赖版本不一致。
- 明确的构建配置错误。

不得擅自修改生产部署配置。

## 2.2 默认禁止自动执行的操作

以下操作不得由 AI 自动执行：

- 自动合并 Pull Request。
- 自动部署生产环境。
- 修改生产数据库。
- 删除生产数据。
- 修改真实支付商户配置。
- 修改真实支付密钥。
- 修改生产环境 Secrets。
- 修改线上服务器权限。
- 修改域名 DNS。
- 修改真实用户余额。
- 直接执行不可逆数据迁移。
- 删除用户已有代码或分支。
- 强制覆盖远程 Git 历史。

如确实需要上述操作，必须另行取得明确授权。

# 3. 缺陷确认机制

## 3.1 缺陷来源

Auto-Fix Engine 可以接收以下来源的问题：

- Code Review Engine。
- Testing Engine。
- Security Scanner。
- CI Failure。
- 人工提交的 Issue。
- 人工确认的代码缺陷。
- 定时全仓库审计。

所有问题必须转换为统一的缺陷记录。

## 3.2 缺陷记录格式

每项缺陷必须包含：

| 字段 | 说明 |
|---|---|
| issue_id | 唯一缺陷编号 |
| title | 问题标题 |
| severity | P0-P4 风险等级 |
| module | 所属模块 |
| file | 文件路径 |
| line | 代码位置 |
| description | 问题描述 |
| root_cause | 初步根因 |
| reproduction | 复现步骤 |
| evidence | 相关证据 |
| expected_behavior | 预期行为 |
| actual_behavior | 实际行为 |
| fix_allowed | 是否允许自动修复 |
| required_tests | 必须补充的测试 |
| base_sha | 原始 Commit SHA |
| status | 当前处理状态 |

## 3.3 缺陷真实性判断

AI 必须先确认问题是否真实存在。

确认方式：

1. 阅读相关源代码。
2. 阅读调用链。
3. 检查相关数据结构。
4. 检查业务状态流转。
5. 检查现有测试。
6. 尽可能构造复现测试。
7. 确认问题触发条件。
8. 判断影响范围。

缺少证据的问题不得直接作为已确认 Bug 进行自动修复。

问题状态统一为：

- CONFIRMED：已确认。
- SUSPECTED：疑似问题。
- FALSE_POSITIVE：误报。
- NEEDS_REPRODUCTION：需要进一步复现。
- BLOCKED：缺少必要环境或权限。
- FIXED：已修复。
- VERIFIED：修复已验证。
- PR_CREATED：已创建 PR。
- CLOSED：已关闭。

# 4. 风险分级及自动修复权限

## 4.1 风险等级

| 等级 | 风险定义 |
|---|---|
| P0 | 严重资金损失、重大安全漏洞、数据破坏或系统级事故 |
| P1 | 高危安全问题、支付错误、余额错误、关键业务不可用 |
| P2 | 重要功能缺陷、明显业务逻辑错误、较高性能风险 |
| P3 | 一般功能缺陷、兼容性问题、代码质量问题 |
| P4 | 优化建议、低风险技术债 |

## 4.2 自动修复权限矩阵

| 等级 | 自动分析 | 隔离修复 | 自动测试 | Commit/Push | 创建 PR |
|---|---|---|---|---|---|
| P0 | 允许 | 禁止 | 允许诊断测试 | 禁止 | 禁止 |
| P1 | 允许 | 允许 | 必须 | 经专项人工批准后允许 | 经专项人工批准后允许 |
| P2 | 允许 | 允许 | 必须 | 允许 | 允许 |
| P3 | 允许 | 允许 | 必须 | 允许 | 允许 |
| P4 | 允许 | 按需允许 | 按需执行 | 允许 | 允许 |

P0 发现后：

1. 立即生成问题报告。
2. 发送告警。
3. 暂停自动修复发布流程。
4. 不得自动 Commit、Push 或创建 PR。
5. 等待人工制定处理方案。

P1 发现后：

1. 允许在隔离环境分析。
2. 允许编写修复方案。
3. 允许隔离修复和测试。
4. 必须经过专项人工审批才能推送和创建正式 PR。
5. 不允许自动合并。

**注意：P1 的人工审批是创建 PR 前的额外安全门槛，不是允许自动合并。**

# 5. 修复执行流程

## 5.1 标准流程

### Step 1：接收问题

读取缺陷记录，确认：

- 缺陷编号。
- 风险等级。
- 模块。
- 文件路径。
- 代码位置。
- 原始 SHA。
- 复现条件。
- 修复权限。

### Step 2：固定代码基线

记录：

- Repository。
- Base Branch。
- Base SHA。
- 当前工作区状态。
- 未提交修改。
- 未跟踪文件。
- 当前执行环境。

审查和修复必须基于明确的代码版本。

如果基线发生变化，必须重新评估修复方案。

### Step 3：分析根因

分析：

- 问题发生原因。
- 调用链。
- 影响模块。
- 影响数据。
- 业务影响。
- 安全影响。
- 是否存在连锁问题。
- 是否需要数据库迁移。
- 是否需要接口兼容处理。

不得只修改报错位置而忽略真正根因。

### Step 4：制定修复方案

修复方案必须说明：

- 修改目标。
- 修改文件。
- 修改原因。
- 可能影响的模块。
- 数据兼容性。
- API 兼容性。
- 回滚方式。
- 测试要求。

优先采用最小必要修改。

### Step 5：创建隔离环境

优先使用：

- Git Worktree。
- 独立临时目录。
- 独立容器。
- 独立测试数据库。

禁止直接覆盖用户当前工作区。

如果用户存在未提交修改，必须保留原始状态。

### Step 6：执行代码修复

修复要求：

- 只修改必要文件。
- 保持现有架构约定。
- 保持代码风格。
- 不引入无关依赖。
- 不修改无关业务。
- 不删除有效测试。
- 不通过忽略错误掩盖问题。
- 不降低安全检查标准。

### Step 7：增加测试

每项修复必须有对应验证。

测试应覆盖：

1. 原始问题复现。
2. 修复后的预期行为。
3. 边界条件。
4. 异常条件。
5. 相关业务回归。
6. 必要的并发场景。

优先补充自动化测试，而不是只进行人工验证。

### Step 8：执行测试

至少执行：

- 相关单元测试。
- 相关集成测试。
- 相关模块完整测试。
- 相关回归测试。
- 必要的静态检查。
- 必要的安全扫描。

关键业务必须执行专项测试。

### Step 9：重新代码审查

修复完成后必须再次执行 Code Review Engine。

检查：

- 是否真正解决问题。
- 是否引入新的缺陷。
- 是否修改了不相关逻辑。
- 是否影响其他模块。
- 是否引入安全问题。
- 是否破坏兼容性。

### Step 10：质量门禁

调用 QUALITY-GATE-STANDARD.md。

未通过门禁时：

- 不得标记为 VERIFIED。
- 不得自动发布为已验证修复。
- 可以生成诊断报告。
- 可以在安全范围内继续修复。
- 超过自动修复次数限制时停止并报告。

# 6. 自动修复重试机制

## 6.1 重试限制

默认允许最多 3 轮自动修复尝试。

每轮必须记录：

- 修复方案。
- 修改文件。
- 测试结果。
- 失败原因。
- 与上一轮的差异。

不得无限循环修改代码。

## 6.2 停止条件

出现以下情况立即停止：

- 连续修复失败。
- 测试持续失败且无法确定根因。
- 修复涉及未经授权的生产配置。
- 发现新的 P0。
- 修复影响范围明显扩大。
- 出现数据迁移风险。
- 存在不可恢复的数据风险。
- 需要真实支付交易验证。
- 无法安全隔离用户修改。
- 远程分支发生冲突且无法安全处理。

停止后必须输出诊断报告。

# 7. Git 分支与版本控制

## 7.1 唯一工作分支规则（强制）

Uter 项目最多允许一个非 `main` 工作分支。所有审计、缺陷修复、测试补充、文档更新和质量门禁修复必须集中在该分支及其现有 PR 中。

- 开始工作前枚举远端分支并检查现有 PR。
- 若唯一非 `main` 工作分支已存在，必须复用该分支；禁止创建第二分支。
- 若不存在非 `main` 分支，必须先报告并取得用户明确授权后，才可创建唯一工作分支。
- 若发现两个或更多非 `main` 分支，停止创建分支和推送；不得自行删除、重写或覆盖任何分支，须由用户确定保留分支。
- 每个问题使用独立 Issue ID / Commit / 报告追踪，不以创建多个分支隔离问题。
- 不直接修改或推送 `main`，不 force push，不覆盖用户未提交修改，不删除他人分支。
- 推送前核对分支 head SHA、工作区状态、暂存文件和远端是否发生并发更新。

## 7.3 Commit 规范

采用 Conventional Commits。

格式：

`<type>(<scope>): <description>`

示例：

`fix(payment): prevent duplicate balance credit`

`fix(auth): validate session refresh state`

`fix(billing): correct token usage calculation`

`test(payment): add concurrent callback regression tests`

Commit 必须清楚说明实际修改内容。

## 7.4 Commit 前检查

执行：

- git status。
- git diff。
- git diff --check。
- 检查敏感文件。
- 检查 Secrets。
- 检查无关文件。
- 检查测试报告。
- 检查质量门禁。

不允许提交：

- `.env` 中的真实密钥。
- 私钥。
- 支付证书。
- 生产数据库凭证。
- 测试生成的大型临时文件。
- 无关个人配置。

# 8. 自动 Push 与 Pull Request

## 8.1 Push 权限

用户已明确授权 AI：

- 复用项目唯一非 `main` 工作分支；不得创建第二分支。
- 自动 Commit。
- 自动 Push。
- 自动创建 Pull Request。

必须使用最小权限的 GitHub App 或短期凭证。

不得把长期高权限 PAT 明文写入代码或日志。

## 8.2 PR 创建条件

必须满足：

1. 缺陷已确认。
2. 修复已完成。
3. 必需测试通过。
4. 相关回归通过。
5. 修复后审查完成。
6. 质量门禁通过。
7. 无未授权的敏感文件修改。
8. P1 已取得专项人工审批。

## 8.3 PR 标题

格式：

`[AI Fix][P2] Prevent duplicate payment credit`

示例：

`[AI Fix][P3] Fix frontend loading state`

## 8.4 PR 描述模板

```markdown
## Summary
修复内容概述。

## Related Issues
关联缺陷编号。

## Severity
P0/P1/P2/P3/P4。

## Base
Base Commit SHA。

## Root Cause
问题根因。

## Changes
修改文件及具体内容。

## Tests Added
新增或修改的测试。

## Test Results
实际执行结果。

## Regression
回归测试结果。

## Security Impact
安全影响。

## Compatibility
接口及数据兼容性。

## Rollback
回滚方案。

## Remaining Risks
尚未解决的问题。

## Quality Gate
Code Review: PASS/FAIL
Automated Tests: PASS/FAIL
Security Scan: PASS/FAIL
Regression: PASS/FAIL

## AI Execution
Execution ID:
Fix Branch:
Commit SHA:
```

不得将未执行的测试标记为 PASS。

## 8.5 PR 创建后的行为

创建 PR 后：

- 更新缺陷状态为 PR_CREATED。
- 保存 PR URL。
- 保存 Branch 和 Commit SHA。
- 保存测试报告。
- 保存审查报告。
- 记录剩余风险。
- 等待人工审核。

**AI 不得自动合并 PR。**

# 9. 安全控制

## 9.1 权限隔离

不同任务应使用不同权限：

- 普通代码审查：只读权限。
- 自动测试：只读源码和测试环境权限。
- 自动修复：隔离工作区写权限。
- 自动 Push：独立修复分支写权限。
- PR 创建：Pull Request 创建权限。

不应将所有权限授予所有 Workflow。

## 9.2 Secrets 管理

严禁：

- 打印密钥。
- 提交密钥。
- 在 PR 中暴露密钥。
- 向 AI 提供生产密钥。
- 将生产凭证用于自动化测试。

只使用专门的测试凭证和最小权限 Token。

## 9.3 第三方依赖

如果自动修复需要升级依赖：

- 先检查漏洞和兼容性。
- 说明升级原因。
- 尽量单独提交。
- 执行完整相关测试。
- 检查许可证。
- 检查锁文件。
- 不允许无理由大范围升级。

# 10. 修复记录与报告

每轮修复必须生成报告。

推荐结构：

```text
reports/
└── auto-fix/
    └── <execution-id>/
        ├── auto-fix-report.md
        ├── auto-fix-report.json
        ├── changes.patch
        ├── test-results.json
        ├── review-results.json
        └── execution.log
```

报告至少包含：

- Execution ID。
- Issue ID。
- 风险等级。
- Base SHA。
- Fix Branch。
- Commit SHA。
- 修改文件。
- 修复前问题。
- 根因。
- 修复方案。
- 测试新增内容。
- 实际测试结果。
- 回归结果。
- 审查结果。
- 安全扫描结果。
- 质量门禁结果。
- PR URL。
- 遗留风险。

报告不得包含密钥、密码或其他敏感信息。

# 11. Auto-Fix Engine 状态机

建议统一状态：

```text
RECEIVED
   ↓
TRIAGING
   ↓
CONFIRMED
   ↓
PLANNING
   ↓
ISOLATING
   ↓
FIXING
   ↓
TESTING
   ↓
REGRESSION
   ↓
REVIEWING
   ↓
QUALITY_GATE
   ↓
VERIFIED
   ↓
COMMITTING
   ↓
PUSHING
   ↓
PR_CREATED
   ↓
WAITING_FOR_HUMAN_REVIEW
```

异常状态：

- REJECTED
- FALSE_POSITIVE
- BLOCKED
- FAILED
- NEEDS_HUMAN_APPROVAL
- CANCELLED

状态必须持久化，避免任务中断后无法恢复执行记录。

# 12. 验收标准

Auto-Fix Engine 必须通过以下验收：

1. 能够接收 Code Review Engine 的缺陷。
2. 能够确认缺陷真实性。
3. 能够生成根因分析。
4. 能够创建隔离工作区。
5. 能够修改代码。
6. 能够新增测试。
7. 能够实际运行测试。
8. 能够执行相关回归。
9. 能够重新执行代码审查。
10. 能够根据风险等级执行权限控制。
11. 能够识别并复用项目唯一工作分支，且能阻止创建第二分支。
12. 能够自动 Commit。
13. 能够自动 Push。
14. 能够自动创建 PR。
15. PR 中包含完整测试和修复证据。
16. P0 能正确阻断。
17. P1 能正确触发人工审批。
18. 不会自动合并。
19. 不会自动部署。
20. 不会覆盖用户未提交修改。

必须至少完成一次真实、低风险的端到端自动修复及 PR 创建演练。

只生成脚本或配置文件不算验收通过。

---

# 13. 最终执行要求

AI Coding Agent 必须：

- 阅读本规范。
- 遵守代码审查规范。
- 遵守自动化测试规范。
- 遵守质量门禁规范。
- 在隔离环境执行修复。
- 对修复进行真实验证。
- 根据授权自动 Commit、Push 和创建 PR。
- 保留完整执行证据。

**最终原则：允许 AI 自主修复，但不允许 AI 自主决定将未经人工审核的代码合并或部署到生产环境。**
