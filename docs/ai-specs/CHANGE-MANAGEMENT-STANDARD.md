# CHANGE-MANAGEMENT-STANDARD
# Uter 工程变更管理规范

**项目：** Uter  
**文档类型：** 工程变更与版本管理标准  
**适用范围：** 所有代码、配置、数据库、API 和架构变更  
**规范级别：** 强制执行

---

## 1. 规范目标

建立可追溯、可审查、可验证、可恢复的变更管理机制。

AI 必须保证每次修改都有明确目的、合理范围和完整证据。

## 2. 变更基本原则

1. 每次变更必须有明确目标。
2. 变更范围必须与任务匹配。
3. 不覆盖用户未提交的修改。
4. 不混入无关变更。
5. 重要变更必须进行影响分析。
6. 变更必须可审查。
7. 变更必须可验证。
8. 必要时必须提供回滚方案。

## 3. 变更分类

建议分为：

- FEATURE：新增功能。
- BUGFIX：缺陷修复。
- REFACTOR：重构。
- SECURITY：安全修复。
- PERFORMANCE：性能优化。
- DATABASE：数据库变更。
- API：接口变更。
- CONFIG：配置变更。
- DOCUMENTATION：文档变更。
- BUILD：构建和工程配置变更。

## 4. 变更前检查

开始修改前必须：

- 检查 Git 状态。
- 记录当前分支。
- 记录基线 Commit SHA。
- 检查未提交文件。
- 识别用户已有修改。
- 确认目标文件。
- 评估影响范围。

不得直接重置、清理或覆盖用户现有工作区。

## 5. 变更范围控制

每项任务必须明确：

- 目标文件。
- 允许修改的模块。
- 可能涉及的关联模块。
- 明确禁止修改的范围。

如果开发中发现必须扩大范围：

1. 说明原因。
2. 评估风险。
3. 更新任务计划。
4. 保留变更证据。

不得无理由扩大修改范围。

## 6. Git 分支管理

AI 自动修复和功能开发应在独立分支或隔离 Worktree 中进行。

建议分支命名：

- `feature/<description>`
- `fix/<description>`
- `security/<description>`
- `refactor/<description>`
- `ai-fix/<issue-id>-<description>`

不得直接向受保护主分支提交代码。

不得使用 force push 覆盖远端历史。

## 7. Commit 规范

建议使用 Conventional Commits：

- feat
- fix
- refactor
- perf
- test
- docs
- build
- ci
- security

Commit 信息必须说明实际变更内容。

不得将未完成或未经验证的工作描述为已完成。

## 8. Pull Request 规范

PR 至少应包含：

- 标题。
- 变更目的。
- 需求或问题来源。
- 基线 SHA。
- 修改文件。
- 核心实现说明。
- 测试结果。
- Quality Gate 结果。
- 安全影响。
- 兼容性影响。
- 未解决风险。
- 回滚说明。

不得伪造测试证据。

## 9. 数据库变更

数据库迁移必须独立识别。

必须评估：

- 新旧代码兼容性。
- 数据回填。
- 迁移顺序。
- 锁表风险。
- 索引构建。
- 回滚限制。
- 生产数据影响。

AI 不得未经授权操作生产数据库。

## 10. 配置变更

配置变更必须说明：

- 配置名称。
- 默认值。
- 是否必填。
- 是否涉及敏感信息。
- 生效范围。
- 兼容性。
- 回滚方法。

不得提交真实 Secrets。

## 11. 质量门禁

提交 PR 前必须通过 Uter Engineering Quality Engine。

至少检查：

- Code Review。
- Automated Testing。
- Security。
- Dependency & Supply Chain。
- Coverage。
- Business Critical。
- Auto-Fix Verification。
- Change Integrity。

实际门禁以 QUALITY-GATE-STANDARD 为准。

## 12. 自动提交权限

在用户已经授权的范围内，AI 可以：

- 创建独立分支。
- 创建隔离 Worktree。
- 修改代码。
- 添加测试。
- 执行质量检查。
- 创建 Commit。
- Push 独立分支。
- 创建 Pull Request。

必须满足：

- 不覆盖用户未提交修改。
- 不直接推送主分支。
- 不使用 force push。
- 不提交真实密钥。
- 不绕过质量门禁。

## 13. 禁止操作

未经额外明确授权，AI 不得：

- 自动合并 PR。
- 部署生产环境。
- 修改生产数据库。
- 修改真实支付配置。
- 修改生产 Secrets。
- 修改 DNS。
- 操作线上用户余额。
- 执行不可逆的数据操作。

## 14. 回滚机制

重要变更必须明确：

- 回滚触发条件。
- 回滚范围。
- 回滚方式。
- 数据恢复方式。
- 回滚后的验证方法。

数据库变更应特别注意：代码回滚不代表数据库能够安全回滚。

## 15. 变更追溯

每项变更应能追溯到：

- 原始任务。
- 基线 SHA。
- 分支。
- Commit。
- PR。
- 测试报告。
- Quality Gate 报告。

## 16. 完成定义

变更只有满足以下条件才算完成：

- 目标已实现。
- 修改范围合理。
- 用户原有工作得到保护。
- 测试已执行。
- Quality Gate 已完成。
- 文档已同步。
- Commit / PR 信息可追溯。
- 未解决风险已披露。

---

**变更管理的核心目标是让每一次 AI 修改都可控、可审查、可恢复。**
