# DOCUMENTATION-STANDARD
# Uter 技术文档与知识管理规范

**项目：** Uter  
**文档类型：** 技术文档管理标准  
**适用范围：** 产品、架构、API、数据库、开发、运维和安全文档  
**规范级别：** 强制执行
**规范版本：** 1.0.0（统一版本登记）  
**规范状态：** Active  
**最后更新：** 2026-11-05  
**维护责任：** Uter Engineering Maintainers  
**版本追溯：** 以 Git 文件历史及对应 Commit SHA 为准  

---

## 1. 规范目标

保证 Uter 的技术文档与实际代码、配置、业务规则保持一致。

文档必须能够帮助开发人员和 AI 正确理解系统，而不是仅作为形式化记录。

## 2. 文档基本原则

- 真实。
- 准确。
- 可追溯。
- 易于查找。
- 结构统一。
- 及时更新。
- 避免重复。
- 避免过期。

禁止编写与实际代码不符的架构说明和操作指南。

## 3. 文档分类

建议统一管理：

- 产品需求。
- 功能说明。
- 系统架构。
- API 契约。
- 数据库设计。
- 安全规范。
- 开发规范。
- 部署与运维。
- 故障排查。
- 技术决策。
- 变更记录。

## 4. 文档命名

文件名应清晰、稳定。

建议：

- 使用英文名称。
- 使用大写连字符命名规范类文件。
- 使用小写连字符命名普通功能文档。
- 避免重复文档。
- 避免使用 final、new、latest 等不可靠后缀。

## 5. 文档结构

正式规范文档建议包含：

1. 标题。
2. 文档目标。
3. 适用范围。
4. 术语。
5. 规范内容。
6. 执行要求。
7. 验收要求。
8. 变更记录（必要时）。

功能文档应包含需求、流程、规则、异常和验收标准。

## 6. 代码与文档同步

以下变更必须检查文档是否需要更新：

| 代码变更 | 需要检查的文档 |
|---|---|
| 新增功能 | 产品需求、功能说明 |
| API 变更 | API 契约 |
| 数据库变更 | Schema、Migration 说明 |
| 架构变更 | 架构文档、ADR |
| 支付变更 | 支付流程和安全文档 |
| 计费变更 | 计费规则 |
| 配置变更 | 配置说明 |
| 部署变更 | 部署和运维文档 |
| 安全变更 | 安全规范和操作指南 |

不得机械地为每次代码修改增加文档；应判断是否产生了值得记录的知识变化。

## 7. 技术决策记录 ADR

重大技术决策应建立 ADR。

推荐格式：

- ADR 编号。
- 标题。
- 状态。
- 日期。
- 背景。
- 需要解决的问题。
- 备选方案。
- 最终决策。
- 决策理由。
- 后果与影响。
- 迁移和回滚方案。

ADR 应保持历史记录，不得通过覆盖旧决策抹去技术演进过程。

## 8. 文档准确性

AI 更新文档前必须核对：

- 实际代码。
- 实际配置。
- 实际 API。
- 实际数据结构。
- 实际部署方式。

不得将计划中的功能描述成已经上线的功能。

不得将未验证的配置描述为已经生效。

## 9. 文档维护

发现以下情况应处理：

- 文档过期。
- 文档冲突。
- 同一内容重复维护。
- 目录失效。
- 示例代码无法运行。
- 配置名称与实际代码不一致。
- 旧方案仍被描述为当前方案。

## 10. 示例与代码片段

文档中的代码示例应：

- 尽量可运行。
- 与当前技术栈一致。
- 不包含真实密钥。
- 明确必要环境条件。
- 说明省略内容。

## 11. 规范冲突

多份文档出现冲突时：

1. 识别冲突内容。
2. 确认适用范围。
3. 查明当前真实实现。
4. 判断是否存在过期规范。
5. 更新相关文档。
6. 记录必要决策。

不得简单地选择对当前开发最方便的规则。

## 12. 文档审查

文档变更应检查：

- 术语一致性。
- 链接有效性。
- 示例正确性。
- 目录结构。
- 版本和状态。
- 与实际代码的一致性。

## 13. 完成定义

文档只有在内容真实、结构清晰、链接有效、与实际实现一致时才算完成。

### 14.2 目录纪律

- `docs/` 常规禁止新增文件（AGENTS.md 约定）；`docs/ai-specs/` 是用户显式授权建立的规范库，属例外。再新增规范文档须用户显式要求。
- 方法论产出放 `.ai/`，工程文档放 `docs-dev/`，设计规范只进 UTER-DESIGN-SYSTEM-3.0.md 单文件——不得在各处散落平行版本。

### 14.3 文档与代码同步的硬性检查点

- i18n：改用户可见文案必须同步 7 份 locale 文件（web/src/i18n/locales/）并过 `check-i18n-keys`；prop/变量形式传 key 扫不到，须登记 `static-keys.ts`。
- 设计系统：改 Token/字号/颜色必须同步 UTER-DESIGN-SYSTEM-3.0.md 对应章节并重跑 `bun run lint:design:strict`；改动基线须走 `--write-baseline` 且只减不增。
- 密钥登记表类文档：secret 三件套相关文档有 3 处守卫同步，改登记表必须同步守卫。
- 品牌资产：换 logo 必 bump LOGO_ASSET_VERSION + 5 处 `?v=N` + 重生成 brandEmailLogoBase64——文档若提及 logo 必须与当前版本一致。
- 已废弃表述不得恢复：如「渠道同步每天/时刻」（实为每 10 分钟）、「字号阶梯 v1.1」（实为 v1.2）、「DreamRouterSyncHour」等。

### 14.4 ADR 现状

仓库尚无 `docs/adr/` 目录；重大决策目前记录在 UTER-DESIGN-SYSTEM-3.0.md、MEMORY.md 与提交信息中。建立正式 ADR 目录属新增文件，须用户显式授权。
