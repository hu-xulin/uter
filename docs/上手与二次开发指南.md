# URouters（u-routers）上手与二次开发指南

> 面向「没写过这个项目、甚至没怎么写过 Go/React」的读者。
> 目标：读完能看懂目录、能追出一次请求的全部调用关系、能自己动手加一个接口或一个上游渠道。
> 本文所有路径均相对仓库根目录。

---

## 一、这个项目到底是什么

它是一个**大模型 API 网关**（AI Gateway / API 中转站），基于开源的 NewAPI / one-api 二次开发而来（Go module 名为 `github.com/QuantumNous/u-routers`）。

用一句话概括它干的事：

> 客户端拿**我们发的密钥**，按 **OpenAI / Claude / Gemini 的标准协议**发请求进来；
> 网关在内部**挑一个上游渠道**（OpenAI、Azure、Bedrock、Vertex、智谱、通义……），把请求**翻译成该渠道要的格式**发出去，拿到结果再**翻译回标准协议**返回；
> 全过程完成**鉴权、限流、模型映射、计费扣费、日志记录**。

因此它同时是一个「协议转换器」+「多租户计费系统」+「渠道调度器」。理解这三重身份，就理解了 80% 的代码。

**关键设计事实（决定你怎么读代码）：**

| 事实 | 含义 |
|---|---|
| **单二进制部署** | 前端 `web/` 构建成 `web/dist`，通过 Go 的 `//go:embed` 编译进可执行文件（`main.go:48`）。所以**改前端必须重新 `bun run build` 再编译 Go**，否则页面不变 |
| **两端共用一套 HTTP 服务** | 管理后台接口在 `/api/*`，对外 AI 接口在 `/v1/*`，调试台在 `/pg/*`，任务在 `/mj`、`/video` |
| **一切围绕 `RelayInfo`** | 一次中继请求的所有上下文（用户、令牌、渠道、计费会话）都装在一个 `*relaycommon.RelayInfo` 结构体里，从头传到尾 |
| **适配器模式是扩展核心** | 每个上游厂商 = `relay/channel/<provider>/` 下一个实现了 `Adaptor` 接口的 struct。加厂商 = 加一个目录 + 注册一行 |

## 二、先跑起来（5 分钟）

```bash
# 1. 后端（会自动用 SQLite 建库 one-api.db，无需装数据库）
go run main.go
# 默认监听 :3000，首次访问会进「初始化向导」，创建 root 账号

# 2. 前端开发模式（热更新，代理到 3000 端口）
cd web && bun install && bun run dev -- --port 5173
# 打开 http://localhost:5173

# 3. 改完前端要出正式版（产物会被 Go 内嵌）
cd web && bun run build      # 产出 web/dist
go run main.go               # 再启动，即可看到新前端
```

`makefile` 里的常用命令：

| 命令 | 作用 |
|---|---|
| `make dev-api` | 用 Docker 起 postgres + 本服务（推荐正式开发环境） |
| `make dev-web` | 起前端开发服务器（5173） |
| `make dev` | 两个一起 |
| `make start-api` | `go run main.go` |
| `make build-web` | `bun install` + `bun run build` |
| `make test` | 跑 Go 测试（主 module + `relaykit` module 各跑一遍） |
| `make reset-setup` | 重置初始化向导状态（忘记 root 密码时好用） |

```bash
curl http://localhost:3000/v1/chat/completions \
  -H "Authorization: Bearer sk-你的令牌" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}]}'
```

**注意环境变量**：`SQL_DSN` 为空 → SQLite；`postgres://` 开头 → PostgreSQL；其他 → MySQL。日志库可用 `LOG_SQL_DSN` 单独指向（支持 ClickHouse）。参照 `.env.example`。

## 四、后端主线：一次 AI 请求的完整调用链

以 `POST /v1/chat/completions` 为例，逐跳说明。

### 4.1 路径总览

```
router/relay-router.go:69   relayV1Router = router.Group("/v1")
router/relay-router.go:71-73  .Use(SystemPerformanceCheck, TokenAuth, ModelRequestRateLimit)
router/relay-router.go:85     httpRouter.Use(middleware.Distribute())
router/relay-router.go:98     POST /chat/completions → controller.Relay(c, RelayFormatOpenAI)
```

### 4.2 三个中间件做了什么

| 中间件 | 文件 | 职责 |
|---|---|---|
| `TokenAuth()` | `middleware/auth.go:361` | 从 `Authorization: Bearer` / `x-api-key` / `?key=` 取密钥 → `model.ValidateUserToken` 校验 → 检查用户状态、IP 白名单、分组与模型权限 → `SetupContextForToken` 把 `token_id / token_key / token_group` 等写入 `gin.Context` |
| `ModelRequestRateLimit()` | `middleware/model-rate-limit.go:169` | 按用户/分组统计模型请求数，超限返回 429（Redis 或内存实现） |
| `Distribute()` | `middleware/distributor.go:34` | 解析请求里的 `model`、`group` → 通过 `getModelRequest`（`:425`）→ 调 `service/channel_select.go:110 CacheGetRandomSatisfiedChannel` 选出一个可用渠道 → `SetupContextForSelectedChannel`（`:613`）把渠道 id / key / base_url / 模型映射写入 Context |

> **要点**：中间件阶段**只选渠道、不调用上游**。真正发请求在 `relay/` 里，而且**每次重试都会重新选渠道**。

### 4.3 controller.Relay：主干编排（`controller/relay.go:73`）

按顺序做这些事：

1. `helper.GetAndValidateRequest(c, relayFormat)`（`:114`）— 读请求体、按协议反序列化成 DTO 并做基础校验。请求体过大直接返回 413。
2. `relaycommon.GenRelayInfo(...)`（`:125`）— 创建本次请求的上下文 `RelayInfo`（`:649` 分流到 `GenRelayInfoOpenAI` 等）。
3. 敏感词检查（`setting.ShouldCheckPromptSensitive()`）+ `service.EstimateRequestToken`（`:150`）— 估算 prompt token 数。
4. `helper.ModelPriceHelper`（`:158`）— 结合模型倍率、分组倍率算出**预估额度** `priceData.QuotaToPreConsume`。
5. `service.PreConsumeBilling`（`:169`）— **预扣费**。免费模型会跳过。
6. 注册 `defer`（`:175`）— 只要后面出错，就 `relayInfo.Billing.Refund(c)` **退款**，并视情况收「违规费」。
7. **重试循环**（`:196`，次数上限 `common.RetryTimes`）：
   - `getChannel(c, relayInfo, retryParam)`（`:334`）→ 选渠道 + `SetupContextForSelectedChannel`
   - `service.PrepareTieredBillingForSelectedGroup`（`:205`）— 分层计费准备
   - 取回请求体（`:210`）→ 按 `relayFormat` 分发到具体 handler：
     - `relay.ClaudeHelper` / `geminiRelayHandler` / `relayHandler(c, info)`
     - `relayHandler`（`:38`）再按 `info.RelayMode` 分到 `TextHelper` / `ImageHelper` / `AudioHelper` / `EmbeddingHelper` / `RerankHelper` / `ResponsesHelper`
   - 失败 → `processChannelError`（`:241`）记录错误并可自动禁用渠道；`shouldRetry` 判断是否换渠道重试。

### 4.4 TextHelper：真正干活的地方（`relay/compatible_handler.go:25`）

**这是最值得精读的函数**，任何新协议的编排都可以照抄它的骨架：

```

:42   helper.ModelMappedHelper(c, info, request) 把用户的模型名映射成上游真实模型名
```

### 4.5 适配器：所有上游差异都被关在这一个接口里

接口定义：`relay/channel/adapter.go:17` 的 `Adaptor`。

| 方法 | 你要在里面做什么 |
|---|---|
| `Init(info)` | 从 RelayInfo 里读渠道配置，决定本适配器行为 |
| `GetRequestURL(info)` | 拼出上游完整 URL（用 `relaycommon.GetFullRequestURL`） |
| `SetupRequestHeader(c, req, info)` | 设置鉴权头（`Authorization` / `x-api-key` / `x-goog-api-key` …） |
| `ConvertOpenAIRequest(...)` | 把 OpenAI 格式的请求体改写成该厂商要的格式 |
| `ConvertClaudeRequest` / `ConvertGeminiRequest` | 同上，其它入口协议的转换 |
| `DoRequest(c, info, body)` | 发 HTTP（OpenAI 系一般调 `relay/channel/api_request.go:313 DoApiRequest`） |
| `DoResponse(c, resp, info)` | 解析回包、抽取 `usage`；流式走 `OaiStreamHandler` |
| `GetModelList()` / `GetChannelName()` | 渠道元信息 |

按类型分发在 `relay/relay_adaptor.go:50 GetAdaptor(apiType)`，一个 `switch` 表——**加新厂商时这里补一行**。

`relay/channel/` 下现有 40+ 个厂商目录，例如 `openai/`（最完整，可作范本）、`claude/`、`gemini/`、`aws/`、`vertex/`、`volcengine/`、`zhipu/`、`task/`（异步任务类，走 `TaskAdaptor` 接口）。

> 本仓库还有一个自定义厂商目录 `relay/channel/Urouters/`——它把 openai / claude / gemini 三个适配器组合起来，按入站协议分派，可作为「聚合型适配器」的参考。

### 4.6 计费与日志发生的位置

| 环节 | 函数 | 文件 |
|---|---|---|
| 预扣 | `service.PreConsumeBilling` | `service/billing.go:20` → `billing_session.go:377 NewBillingSession` |
| 结算 | `service.PostTextConsumeQuota` | `service/text_quota.go:395` |
| 结算落库 | `service.SettleBilling` | `service/text_quota.go:462` → `service/billing.go:51` |
| 失败退款 | `relayInfo.Billing.Refund(c)` | `controller/relay.go:180` |
| 消费日志 | `model.RecordConsumeLog` | `model/log.go:339` |
| 错误日志 | `model.RecordErrorLog` | `model/log.go:278` |
| 任务消费日志 | `service.LogTaskConsumption` | `service/task_billing.go:24` |

**记住这条纪律**：任何新写的转发路径，必须保证「预扣 → 成功则结算 / 失败则退款」成对出现，否则会出现用户额度不扣或白扣。

### 4.7 `relaykit/` 是什么

一个**独立的 Go module**（`relaykit/go.mod`），里面只有 DTO 和协议转换器：`dto/`、`types/`、`relayconvert/`、`reasonmap/`。

- **它不包含**：HTTP 发送、渠道调度、鉴权、计费、数据库。
- **它的价值**：OpenAI Chat/Responses ↔ Claude ↔ Gemini 的请求、响应、流式分片互转逻辑被隔离在纯函数里，**可以单独测试、单独复用**，也避免了 `relay/` 与宿主逻辑的循环依赖。
- **改协议转换逻辑时优先改这里**，而不是改 `relay/` 里的 handler。

## 五、后端支线：管理接口（增删改查）链路

管理后台的接口全部在 `/api/*`，入口是 `router/api-router.go:15 SetApiRouter`。

### 5.1 路由的组织方式

`/api` group 先挂一组全局中间件，再按业务切子 group：

```go
apiRouter := router.Group("/api")
apiRouter.Use(middleware.RouteTag("api"))
apiRouter.Use(gzip.Gzip(...))
apiRouter.Use(middleware.AccessTokenAudit())
apiRouter.Use(middleware.BodyStorageCleanup())
apiRouter.Use(middleware.GlobalAPIRateLimit())
```

然后：

| 子 group | 鉴权中间件 | 说明 |
|---|---|---|
| `/api/user/...` | `AdminAuth()` / `UserAuth()` | 管理端用 AdminAuth，改自己用 UserAuth |
| `/api/token` | `UserAuth()` + `TokenOperationAudit()` | 用户自己的 API 令牌 |
| `/api/channel` | `AdminAuth()` + `RequirePermission(...)` | 渠道，细粒度权限表见 `router/channel-router.go` |
| `/api/option` | `RootAuth()` | 系统设置 |
| `/api/log`、`/api/group`、`/api/vendors`、`/api/models`、`/api/redemption` | `AdminAuth()` | 各自 CRUD |
| `/api/system-task`、`/api/system-info`、`/api/performance`、`/api/plugin/task` | `RootAuth()` | 运维 |

`router/channel-router.go` 用「权限路由表」的写法，值得学习：

```go
var channelPermissionRoutes = []permissionRoute{
    {method: http.MethodGet, path: "/", permission: authz.ChannelRead, handler: controller.GetAllChannels},
    ...
}
// 循环注册
for _, route := range channelPermissionRoutes {
    channelRoute.Handle(route.method, route.path,
        middleware.RequirePermission(route.permission), route.handler)
}
```

### 5.2 三个鉴权中间件

都在 `middleware/auth.go`：

- `UserAuth()`（`:100`）→ `authHelper(c, common.RoleCommonUser)`
- `AdminAuth()`（`:106`）→ `authHelper(c, common.RoleAdminUser)`
- `RootAuth()`（`:112`）→ `authHelper(c, common.RoleRootUser)`
- `RequirePermission(p)`（`:235`）→ 走 Casbin `authz.Can(...)`

凭据解析在 `classifyDashboardCredential`（`:158`）：先按内部登录 token 走 session 校验，否则按 PAT（个人访问令牌）走 `model.ValidateAccessToken`。

解析成功后写入 Context：`id` / `role` / `username` / `group` / `session_id` 等。

### 5.3 Controller 与 Model 的写法

- `controller/*.go`：文件名 = 业务域，函数签名统一是 `func Xxx(c *gin.Context)`。典型模式是「解析参数 → 调 model/service → `common.ApiSuccess(c, data)` 或 `common.ApiError(c, err)`」。
- `model/*.go`：GORM 结构体与数据访问函数放同一文件，例如 `model/user.go` 里既有 `type User struct` 也有 `GetAllUsers(...)`。全局句柄是 `model.DB`（`model/main.go:66`）。

常用工具函数：

| 函数 | 位置 | 用途 |
|---|---|---|
| `common.GetPageQuery(c)` | `common/page_info.go:41` | 解析分页参数 |
| `common.GetRequestBody(c)` | `common/gin.go:36` | 拿到可重复读的请求体 |
| `common.UnmarshalBodyReusable(c, &v)` | `common/gin.go:108` | 反序列化请求体 |
| `common.ApiSuccess(c, data)` | `common/gin.go:213` | 统一成功响应 |
| `common.ApiError(c, err)` | `common/gin.go:199` | 统一错误响应（支持 i18n） |
| `common.GetContextKeyInt(c, key)` | `common/gin.go:169` | 取中间件写入的值 |

Context 的 key 常量集中在 `constant/context_key.go`，例如 `ContextKeyUserId = "id"`、`ContextKeyUsingGroup = "group"`。

### 5.4 数据库初始化

`model/main.go`：

- `InitDB()`（`:186`）→ `chooseDB("SQL_DSN", false)`（`:140`）按 DSN 前缀选 SQLite / PostgreSQL / MySQL
- `migrateDB()`（`:320`）先跑定制迁移，再 `DB.AutoMigrate(&Channel{}, &Token{}, &User{}, ...)` —— **新增表必须把 struct 加进这个列表**，否则不会建表
- `InitLogDB()`（`:230`）日志库，`LOG_SQL_DSN` 为空则复用主库

## 六、前端：结构与如何调用后端

### 6.1 启动与路由

`web/src/main.tsx`：

1. `initializeFrontendCache()` → 2. `createAppQueryClient()`（`lib/query-client.ts`，500 时跳 `/500`）→ 3. `createRouter({routeTree})` → 4. `initSystemBranding()`（预取 `['status']`）→ 5. 渲染。

Provider 嵌套顺序：`QueryClientProvider > ThemeProvider > FontProvider > DirectionProvider > RouterProvider`。

路由目录 `web/src/routes/`，用 TanStack Router 的**文件路由**：

| 命名 | 含义 |
|---|---|
| `__root.tsx` | 根路由，`beforeLoad` 里做 setup 检查与 `bootstrapAuthentication` |
| `_authenticated/route.tsx` | 登录守卫，未登录重定向 `/sign-in` |
| `_authenticated/channels/index.tsx` | 需要登录的渠道页面 |
| `(auth)/sign-in.tsx` | 括号分组，不进入 URL |
| `chat/$chatId.tsx` | `$param` 是动态段 |
| `routeTree.gen.ts` | **自动生成**，不要手改 |

### 6.2 目录职责

| 目录 | 职责 |
|---|---|
| `features/` | **主要开发区**。一个业务域一个目录，内部自带 `api.ts` / `types.ts` / `constants.ts` / `components/` / `hooks/` / `lib/` |
| `components/` | 通用组件。`ui/` 是 shadcn 基础件，`data-table/` 是统一表格（先读它的 README） |
| `stores/` | Zustand：`auth-store` / `notification-store` / `system-config-store` / `pricing-preferences-store` |
| `hooks/` | 跨业务通用 hook |
| `lib/` | 无 React 依赖的基建：`http-client.ts`（axios 实例）、`api.ts`、`auth-session.ts`、`query-client.ts` 等 |
| `context/` | 主题、字体、方向、布局等 Provider |
| `i18n/` | i18next 初始化 + `locales/*.json`（key 就是英文字面量） |

`features/` 下现有 28 个子目录：`about、auth、channels、chat、dashboard、errors、home、keys、legal、model-pricing、models、performance-metrics、playground、pricing、profile、rankings、redemption-codes、security、setup、subscriptions、system-info、system-settings、system-update、task-plugins、usage-logs、users、wallet`。

### 6.3 后端调用入口：`web/src/lib/http-client.ts`

**这是前端最需要先读懂的文件。**

```ts
export const api = axios.create({
  baseURL: '',                 // 空 = 走同源相对路径
  withCredentials: true,
  headers: { 'Cache-Control': 'no-cache, no-store' },
})
```

关键机制：

1. **baseURL 为空** —— 开发时由 `rsbuild.config.ts` 的 proxy 把 `/api`、`/v1`、`/mj`、`/pg` 转发到 `http://localhost:3000`；生产时前端与后端同源。
2. **token 自动注入**（`:147`）—— 请求拦截器从 `useAuthStore` 取 `accessToken`，写成 `Authorization: Bearer <token>`。涉及一次性凭证（`singleUseAuthorization` / `X-Security-Proof`）时改用 `getFreshAuthHeaders()`。
3. **401 自动刷新重放**（`:99`）—— 遇到 401 先 `refreshAuthentication()`，成功后用新 token 重放原请求；仍失败则提示会话过期并跳 `/sign-in`。
4. **GET 去重**（`:61`）—— 相同 URL + 参数的并发 GET 会复用同一个 in-flight Promise（可用 `disableDuplicate` 关闭）。
5. **SSE 不走 axios** —— 流式对话用 `sse.js` 的 `SSE` 类（见 `features/playground/hooks/use-stream-request.ts`）。

**接口定义的组织约定**：项目**没有**全局 endpoint 常量文件，约定是**每个 feature 自带** `api.ts`（放请求函数）+ `constants.ts`（放路径常量）+ `types.ts`（放类型）。跨 feature 通用的 `/api/user/*`、`/api/status` 聚合在 `lib/api.ts`。

### 6.4 Playground 流式对话是怎么走的

这是全项目最值得模仿的「前端 ↔ 后端实时流」实现：

```
routes/_authenticated/playground/index.tsx
  └─ <Playground/>                         features/playground/index.tsx
      └─ useChatHandler()                  features/playground/hooks/use-chat-handler.ts
          ├─ buildChatCompletionPayload()  lib/streaming/payload-builder.ts
          └─ useStreamRequest()            hooks/use-stream-request.ts
              └─ new SSE('/pg/chat/completions', { method:'POST', headers: await getFreshAuthHeaders(), payload })
                    ↓ 后端
router/relay-router.go:67  POST /pg/chat/completions
  → SystemPerformanceCheck → UserAuth → Distribute → controller.Playground
                    ↓ 上游回包逐块返回
SSE 'message' 事件 → onUpdate('reasoning'|'content', chunk)
  → useChatHandler 以 50ms 节流 flushStreamUpdates 增量写入消息
  → 收到 [DONE] 后 onComplete 收尾
```

> **重要区分**：前端 Playground 打的是 `/pg/chat/completions`（用**登录会话**鉴权）。
> 外部程序接入打的是 `/v1/chat/completions`（用 **API 密钥** `TokenAuth` 鉴权）。两者最终都进 `controller.Relay`，但入口和鉴权方式不同。

|---|---|---|---|

## 八、二次开发实战

### 场景 1：新增一个管理接口（CRUD）

假设要加「公告管理」：`GET /api/notice-list`、`POST /api/notice-list`。

**改动清单（按顺序）：**

**① Model** — `model/notice.go` 新增结构体与访问函数：

```go
type Notice struct {
	Id        int    `json:"id" gorm:"primaryKey"`
	Title     string `json:"title" gorm:"type:varchar(255)"`
	Content   string `json:"content" gorm:"type:text"`
	Enabled   bool   `json:"enabled" gorm:"default:true"`
	CreatedAt int64  `json:"created_at" gorm:"autoCreateTime:milli"`
}

func GetAllNotices(pageInfo *common.PageInfo) ([]*Notice, int64, error) {
	var notices []*Notice
	var total int64
	if err := DB.Model(&Notice{}).Count(&total).Error; err != nil {
		return nil, 0, err
	}
	err := DB.Order("id desc").
		Limit(pageInfo.GetPageSize()).Offset(pageInfo.GetStartIdx()).
		Find(&notices).Error
	return notices, total, err
}

func CreateNotice(n *Notice) error {
	return DB.Create(n).Error
}
```

**② 建表** — `model/main.go` 的 `AutoMigrate` 列表里加上 `&Notice{}`。

**③ Controller** — `controller/notice.go`：

```go
func GetAllNotices(c *gin.Context) {
	pageInfo := common.GetPageQuery(c)
	notices, total, err := model.GetAllNotices(pageInfo)
	if err != nil {
		common.ApiError(c, err)
		return
	}
	pageInfo.SetTotal(int(total))
	pageInfo.SetItems(notices)
	common.ApiSuccess(c, pageInfo)
}

func AddNotice(c *gin.Context) {
	var req model.Notice
	if err := common.UnmarshalBodyReusable(c, &req); err != nil {
		common.ApiError(c, err)
		return
	}
	if err := model.CreateNotice(&req); err != nil {
		common.ApiError(c, err)
		return
	}
	common.ApiSuccess(c, nil)
}
```

**④ 路由** — `router/api-router.go` 加两行（放在合适的位置，沿用已有 group）：

```go
apiRouter.GET("/notice-list",  middleware.AdminAuth(), controller.GetAllNotices)
apiRouter.POST("/notice-list", middleware.AdminAuth(), controller.AddNotice)
```

**⑤（可选）权限点** — 若要像渠道那样用细粒度权限，在 `service/authz/` 注册新 permission，再用 `middleware.RequirePermission(...)` 替换 `AdminAuth()`。

**⑥（可选）i18n** — `i18n/keys.go` + `i18n/locales/*.yaml` 补消息。

**⑦ 测试** — 同目录加 `notice_test.go`，`make test` 验证。

**⑧ 前端** — 新建 `web/src/features/notices/`，写 `api.ts`（用统一的 `api` 实例）、`components/`、并在 `web/src/routes/_authenticated/notices/index.tsx` 建页面；页面数据用 `useQuery`，唯一 `queryKey`，成功后在 `onSuccess` 里 `invalidateQueries`。最后 `bun run typecheck && bun run lint && bun run build`。

### 场景 2：接入一个新的上游厂商

1. 在 `constant/` 里加一个渠道类型常量（参考现有 `APITypeXxx`）。
2. 新建 `relay/channel/<provider>/adaptor.go`，实现 `channel.Adaptor` 全部方法。**最快的方式是复制 `relay/channel/openai/adaptor.go` 再逐方法改**。
3. 在 `relay/relay_adaptor.go:50 GetAdaptor` 的 switch 里加一个 `case`。
4. 在 `relay/relay_adaptor.go` 的 import 区补上包导入。
5. 在后台「渠道」页面新增该类型渠道，填 base_url 与密钥，用「测试」按钮验证。
6. 若该厂商模型名与标准名不同，用渠道的**模型映射**功能即可，无需改代码。
7. 若计费口径特殊（按秒、按张、按分辨率），需要改 `service/text_quota.go` 或任务类计费逻辑。

> 参考文档：`docs/channel-adaptor-map.md` 列出了渠道类型与适配器的对应关系。

### 场景 3：新增一个前端页面

1. `web/src/routes/_authenticated/<name>/index.tsx` 建文件（`createFileRoute('/_authenticated/<name>/')`），路由树会自动重生成。
2. `web/src/features/<name>/` 建业务目录：`api.ts` / `types.ts` / `constants.ts` / `components/`。
3. 数据获取用 `useQuery`，变更用 `useMutation`；错误统一交给 `handleServerError`。
4. 文案走 `useTranslation()` 的 `t()`，并在 `web/src/i18n/locales/*.json` 补 key（`bun run i18n:sync` 可辅助）。
5. **组件先检索再复用**：动手写 UI 前先看 `components/ui/`、`components/data-table/` 与相邻 feature，避免重复实现（这是 `web/AGENTS.md` 的强制要求）。
6. 收尾：`bun run typecheck`、`bun run lint`、`bun run test`，然后 `bun run build` + 重新编译 Go。

### 场景 4：想改「请求/响应协议转换」逻辑

**优先去 `relaykit/`**，而不是 `relay/channel/*`。那里是纯 DTO 与纯函数转换，改完跑 `cd relaykit && go test ./...` 即可验证，不用起整个服务。

只有当差异涉及「网络行为」（URL 拼法、鉴权头、分页拉取模型列表）时，才改 `relay/channel/<provider>/adaptor.go`。

## 九、调试与排错手册

| 症状 | 排查方向 |
|---|---|
| 前端改动不生效 | 忘了 `bun run build`；`web/dist` 是 Go embed 的来源 |
| 前端请求 404 | 检查 dev server 的 proxy 配置（`web/rsbuild.config.ts`），以及后端路由是否注册 |
| 接口 401 | 前端看 `useAuthStore` 里 `accessToken` 是否存在；后端看 `authHelper` / `TokenAuth` 日志 |
| 接口 403 | `RequirePermission` 的权限点未授予；看 `service/authz` 与角色配置 |
| 中继请求全部 503 | `SystemPerformanceCheck` 判定机器负载过高（`middleware/performance.go`） |
| 额度没扣 / 扣了没退 | 检查预扣与结算是成对出现；`controller/relay.go` 的 defer 是否被绕过 |
| 想追一次请求的完整过程 | 开 `DEBUG=true`；Go 侧看 `logger.LogDebug` 输出（`TextHelper` 会打印请求体），前端看 Network 面板的 SSE 事件流 |
| 想看某个渠道为什么失败 | 「日志」页面按渠道筛错误日志；错误由 `processChannelError` + `model.RecordErrorLog` 写入 |
| 数据库表没建 | 新 struct 是否加进 `model/main.go` 的 `AutoMigrate` 列表 |
| 忘记 root 密码 | `make reset-setup` |

**几个高频修改点速查：**

| 想改什么 | 改哪里 |
|---|---|
| 模型定价 / 倍率 | `setting/ratio_setting/`（运行期可在后台改） |
| 计费公式 | `service/text_quota.go`、`service/billing.go`、`service/tiered_settle.go` |
| 渠道选择策略 | `service/channel_select.go`、`service/channel_affinity.go`、`middleware/distributor.go` |

| 后端文案 | `i18n/locales/*.yaml` |
| 前端文案 | `web/src/i18n/locales/*.json` |
| 上游协议差异 | `relaykit/` + `relay/channel/<provider>/` |

## 十、学习路线（建议 3～5 天）

**第 1 天 — 跑通与会用**
`make dev` 起服务 → 走完初始化向导 → 建渠道 → 建令牌 → 用 curl 打通一次对话 → 在后台看「日志」页确认有记录。

**第 2 天 — 读主干**
按 `main.go` → `router/main.go` → `router/relay-router.go` → `middleware/distributor.go` → `controller/relay.go` → `relay/compatible_handler.go` 的顺序读一遍，在纸上画出调用链。目标：能回答「请求进来后第 3 步做了什么」。

**第 3 天 — 读适配器**
精读 `relay/channel/openai/adaptor.go` 的 8 个方法，再对比一个差异大的（如 `relay/channel/gemini/`），理解协议转换的抽象边界。顺手读 `relaykit/` 的一个转换函数。

**第 4 天 — 读前端链路**
`web/src/main.tsx` → `web/src/lib/http-client.ts` → `web/src/features/channels/` → `web/src/features/playground/hooks/use-stream-request.ts`。目标：能回答「点一下发送按钮，代码依次经过哪些文件」。

**第 5 天 — 动手写**
挑一个小需求（例如给渠道列表加一列、加一个只读的管理接口、加一个简单的上游适配器），完整走一遍「改代码 → 测试 → 构建 → 验证」。走完这一遍，你就真正上手了。

```
请求进来

      └─ relay/channel/<provider>/ → 每个上游一个 Adaptor 实现
      └─ relaykit/ → 纯协议转换（独立 module）
  model/    → GORM 读写，model.DB 是句柄
  common/   → 环境变量、Redis、缓存、日志、Gin 封装
  setting/  → 运行期可改的配置   constant/ → 编译期常量

前端
  web/src/routes/    → 文件路由（_authenticated 需登录）
  web/src/features/  → 业务主体，自带 api.ts / types.ts / constants.ts

  流式对话用 sse.js 的 SSE 打 /pg/chat/completions
  构建产物 web/dist 被 //go:embed 编进二进制
```
